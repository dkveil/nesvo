# Architecture

## Workspace shell

The desktop shell is one resizable sidebar and a conversation column. The navigation rail holds the sidebar toggle and the shell draws the product name in the title row at a fixed offset from the rail, so neither moves when the sidebar collapses. The sidebar carries a search row with the new-session action, the Inbox entry, the session list and a footer. The footer holds Settings and one usage ring per provider on the left, and the selected computer (opening Settings › Computers) on the right. Sessions are grouped by computer when more than one computer is known; each row shows one status dot (a spinner while it works, warning when it needs the operator, error, success, a neutral dot when idle and a hollow ring when its computer is offline, with the full status in a tooltip and in the accessible name), the title, the relative time of the last update or a warning-toned `Needs you`, the working-directory basename, a cloud mark for remote sessions and the provider mark, with workers nested under their parent. Provider marks are small inline SVG drawings in the current text colour, a ray burst for Claude Code and an interlaced knot for Codex, used wherever the app identifies a provider: session rows, usage rings and bars, the model picker, the composer and the session card. The header shows a breadcrumb of project chip, directory and session title and keeps the workflow status or session details button and the skills, files and context toggles at the right.

The native title bar is hidden. The sidebar title row and the main header form one borderless 40 px drag region; buttons, inputs, popovers, dialogs and the sidebar resize handle opt out of dragging. Windows and Linux keep the operating system's window controls through a transparent title bar overlay whose symbol colour follows the colour scheme, and the header reserves the overlay width from the `titlebar-area-*` environment values. macOS keeps inset traffic lights and the first row gains a left inset. Double-click maximize and snap behaviour stay native. The preload API is unchanged; macOS and Linux behaviour is configured but has not been verified on those systems.

Each usage ring shows the remaining share of the provider's most used reported window, coloured by level (at least 50% left, at least 20%, below 20%), with a tooltip that lists every window with its reset time and says when the limits were last checked. Stale observations fade with a warning dot, offline computers show the last observation in grey with an offline dot, a pending first read pulses, and unavailable data shows only a dashed track; none of these is drawn as zero. The session card, opened from the header and described under Workflow view, repeats the weekly limits as bars so they stay reachable while the sidebar is collapsed. Rows only appear when Nesvo has the data: the inbox and the new-thread screen show the computer and usage only, and there is no context bar because hosts do not report a context window. The card offers no push or pull request actions.

Settings is one large modal with a searchable left navigation, a breadcrumb and a close button. General shows the selected computer's connection and each provider's status with refresh and sign-in hints (moved from the Context sheet, which now keeps only session details). Appearance chooses the colour scheme: System (the default), Light or Dark. Electron main stores the choice in `appearance.json` in the user data folder and sets `nativeTheme.themeSource` before the window opens, so the window background and the caption symbols follow it. The renderer does not rely on `prefers-color-scheme`, which Chromium does not derive from `themeSource` on every Linux setup: main resolves the applied scheme from `nativeTheme.shouldUseDarkColors`, passes it to the preload as a launch argument and sends changes when the theme updates or the choice changes, and the renderer toggles a `dark` class on the root element before React renders (dark until told otherwise). The preload API gains `colorScheme`, `setColorScheme` and `onAppliedColorScheme`, validated by the shared contract. Computers, Phone access and Account and limits are the former dialogs and footer popover as pages; the usage rings keep their own popover.

The conversation is a 38 rem column. Operator messages are right-aligned bubbles and agent text has no frame; fenced code blocks in either are rendered as bordered blocks with the language and a wrap toggle, while the rest of the text stays plain. The docked composer reuses the new-thread composer's glass surface, model chip and round send button, with the computer, project and permission mode as chips below it. Side panels (files, saved diff and skills) share a 40 px header and borderless search on the app background, and inbox rows keep their decisions inline with rounded hover fills.

The sidebar defaults to 256 px and can be dragged, moved with the arrow, Home and End keys, or reset by double-clicking its edge, between 208 px and the window width minus 640 px. Collapsing hides it completely, moves focus to the header toggle and is available from either toggle or Ctrl+B. Collapsing and expanding animate the sidebar edge while its contents stay at full width and are clipped, and the conversation column follows; dragging, keyboard resizing and reduced motion stay instant. The open state and width are local view preferences stored in the renderer, like the last session and saved-diff location; the host remains authoritative for all session data. Compact widths keep the existing sheet navigation. The window follows the colour scheme chosen in Settings, by default the operating system's.

Keyboard navigation is renderer-only. Ctrl+Shift+P opens the command palette (commands and sessions) and Ctrl+P opens it in Go to session mode, ranked by a fuzzy match over title, folder, group and computer. The palette lists actions for the current session in a Current session group, and Tab or Right on a session result opens the same actions for that session, with Backspace returning to the list: Rename, Pin or Unpin, Move to group, Fork, Restart, Export as Markdown, Finish worktree (for worktree sessions), Open files, MCP servers, Archive or Unarchive and Delete. They reuse the menu handlers, so Restart, Finish worktree and Delete keep their confirmations; actions that need the conversation (files, MCP servers, finishing a worktree) open the session first. Rename opens a small dialog because the inline sidebar field may be hidden. Session rows and the header menu offer Delete as their last item. Alt+Up and Alt+Down move through the sidebar in its visible order, so collapsed groups, the search and the status filter apply; when the sidebar is closed they fall back to the session list with the status filter. Ctrl+J cycles through sessions that need the operator (an operation approval, a worker proposal or plan, a pending review, or a workflow waiting for a person or needing attention), Ctrl+Backquote returns to the previous session and Ctrl+1 to Ctrl+9 jump to a computer section, or with one computer to a root group. The sidebar status filter (All, Needs me, Running, Failed) is a local view preference. Shortcuts only navigate and open views: they never send, approve or decide. Ctrl shortcuts require Ctrl or Command without Alt, so AltGr text input is unaffected, and nothing fires during IME composition or while a dialog is open. The shortcut table in `shared/lib/keyboard-shortcuts.ts` feeds Settings › Keyboard shortcuts, the palette and tooltips.

Colours, surfaces, the glass composer and popovers, spacing and status colours are CSS custom properties in `styles.css`, consumed through Tailwind theme tokens rather than literal colours in components, and the interface uses the Inter variable font. The compact dark theme, glass surfaces and sidebar density are built from base shadcn components.

## New thread

New session opens a screen in the main area instead of a dialog: a heading with the chosen project folder (or "No project") below it, one composer and a row of chips. The chips are popovers for the provider and model (a provider rail built from the per-host status and a searchable list from each provider's reported catalog), the computer to run on (Local and connected SSH computers, with the existing Computers flow for adding one), the working directory (the existing input and host validation; an empty value means the host's isolated folder) and permissions (a segmented control limited to Read-only and Workspace edits, with Workspace edits disabled for Claude because Claude runs read-only analysis in Nesvo). Enter sends and Shift+Enter inserts a newline.

The first message creates the session through the existing create and send APIs with exactly the chosen provider, model, host, directory and mode; the trimmed first line of the message becomes the title, capped at 100 characters. No role is sent. A creation failure, such as an invalid directory, stays on the screen with the draft; a send failure after creation appears inside the new thread and never re-creates it. The composer offers the same `/` skill menu as a session. Its catalog comes from `discover-skills` with the chosen provider and folder on the chosen computer, resolved like `create-session` (an empty folder uses the host's shared workspaces root), so no session is created to list skills. The first message carries the selected skill ID and hash; `send-message` revalidates it against the created session before any provider turn, and a mismatch leaves the draft and selection inside the new thread with the error. Changing provider, computer or folder clears the selection. Attachments are not shown because the contracts and host do not provide them.

The model picker has a Reasoning column. Provider status reports effort support: Codex reports it per model from the `supportedReasoningEfforts` and `defaultReasoningEffort` fields of its `model/list` catalog, and the column lists exactly those values with the catalog default marked. The Codex default entry carries no efforts because Nesvo does not pass a model for it and the effective model depends on the user's Codex configuration. Claude Code reports `per-model` and the effort levels its installed CLI lists for `--effort` in `claude --help` (2.1.327 lists low, medium, high, xhigh and max), the same for every model; a CLI without the flag reports `unsupported` with a reason, and the column shows that reason and no choices. For Claude the column starts with Default, which passes no effort so the CLI and account defaults apply, because Claude Code does not report its default level. Claude effort is offered in new threads and session composers only; automations, workflow tasks, the workflow assistant and reviewer profiles keep rejecting it, and their pickers say so. A Codex model with efforts always sends an explicit effort, starting from the catalog default. `create-session` accepts an optional effort for a specific Codex model or any Claude Code model. For Claude the host confirms it against a fresh `--help` read before saving the session, refuses a level sent with a message that the last ready inspection did not list, and every turn checks it against the inspection the turn already makes; a CLI that no longer lists the level fails the turn visibly before the process starts, and a level chosen for that turn is reverted. The turn passes it as `--effort <level>`. For Codex the host confirms it against a fresh catalog read before saving the session and again before every turn, because the app-server accepts and echoes arbitrary effort strings. A withdrawn effort fails the run before any thread or turn starts. The session stores the effort; every turn passes it as `model_reasoning_effort` on `thread/start` or `thread/resume` and as `effort` on `turn/start`, and a thread response that reports a different effort fails the run before the turn starts.

The header breadcrumb shows a read-only Git branch chip after the project name, on the new-thread screen and in existing threads. It names the current branch, or the first seven characters of the commit when HEAD is detached, and shows nothing for a folder without a repository, an empty folder value (the host's isolated folder), an offline computer or a host that does not report `git-branch`. A failed, invalid or timed-out read also shows nothing and never raises an error message. The chip reads again after a short delay when the folder changes and when the window regains focus.

`read-git-branch` carries the raw folder string. The host does not touch the filesystem for it: the shared folder check (`apps/host/src/workspace/folder.ts`) runs in its own short-lived child process, verifies that the path is absolute and a directory and resolves it with `realpath`, and a second short-lived Node child process (`apps/host/src/workspace/git-branch.ts`) receives the resolved folder, finds `.git` upwards (directory or `gitdir:` pointer) and reads `HEAD` with a non-blocking, regular-file-only read capped at 4 KiB. Nothing is written. The parent keeps a two-second timeout and the host shutdown signal, kills the child and stops waiting when either fires, and caps the child's output, so a hung network filesystem can stall only a child. The folder check child has its own five-second bound and no process cap, so a read can take up to that long to fail when the folder is on a stalled mount. The folder is passed after `--` so it cannot be read as a runtime option. Reads share the existing limit of eight concurrent workspace requests, and at most four reader processes may be alive at once: a slot is released when the process actually exits, so readers that a hung mount keeps from dying make later reads fail instead of piling up. `HEAD` is checked to be a regular file before it is opened, and branch names containing control or formatting characters are not shown.

Host health lists the capabilities `scheduled-jobs`, `reasoning-effort` and `git-branch`. Electron records them per computer at synchronization and refuses a scheduled job command, an effort request or a branch read locally for a host that does not list the matching capability, because an older host rejects unknown fields without a request ID and the SSH client treats that as a protocol failure. Status from such a host defaults to Claude-style `unsupported` effort with an update reason and models without efforts, so the picker offers no effort.

## Interactive session worktrees

A connected host advertises `session-worktrees`. When its Git branch reader recognizes the selected folder, the new-thread setup offers Worktree and an optional branch name. The host resolves the folder to its Git repository root, allocates a session ID and creates a new branch from the current HEAD, using `nesvo/<slug>-<id8>` when no name is supplied. The provider starts at the root of the new checkout. The session document stores the source root, branch, starting commit and worktree state alongside its working directory. Existing sessions have no worktree record.

Interactive checkouts live in the host data directory under `session-worktrees/`. Workflow checkouts use their own `worktrees/` directory and removal API. Both use the same bounded Git executable and branch creation path. Session isolation keeps concurrent checkouts apart. A session worktree is its own folder for folder locks, so sessions in different worktrees of one repository run at the same time with separate result diffs. Workers still share their parent's directory boundary and follow the existing delegation and write-scope rules.

The session header shows the recorded branch with a worktree icon. Finish reads Git status and requires an operator action while the host has no active turn or workspace mutation. Keep records the session as finished and retains its checkout. Open pull request also retains it and opens the existing Pull requests view on the same computer, using the source repository and a search filtered to the recorded branch. Publishing the branch and creating the pull request are separate operator actions. Remove uses the registered checkout under the host's session-worktrees directory. It refuses uncommitted changes and local files unless the operator confirms their removal, and retains the branch. The removal lock keeps turns and PR checkouts from starting while Git removes the directory.

Finished worktree sessions retain history and saved results and cannot start new turns, including corrections and worker continuations. Queued messages are held. A kept checkout can be removed later. Reopening the client or restarting the host restores the recorded state without repeating any action. GitHub lookup uses the recorded branch and source repository even after removal.

A source checkout can list local files in its root `.worktreeinclude`. The file uses Git ignore syntax, including anchored paths, `**` and `!` exclusions. Every match must be absent from the source index. Both ignored and other untracked files can match, for example `.env` and `.env.local`. Nesvo skips symlinks, junctions, `.git` components and destination files that already exist. It copies at most 64 files and 8 MiB in total. The pattern file is limited to 64 KiB and the Git candidate list to 256 KiB. The worktree metadata records copied and skipped counts for the names read, with an incomplete flag if the scan was limited or the pattern file could not be read. Finish worktree shows these counts.

Finish worktree shows an optional setup action for a regular UTF-8 file named exactly `.nesvo/worktree-setup` in the recorded project checkout. Write the script as CommonJS JavaScript. Nesvo launches the host runtime with fixed argv `['--input-type=commonjs', '-']` and the shell disabled. It sends the validated file bytes on stdin and uses the new checkout root as the working directory. The script has a 64 KiB limit, a 30-second deadline and a 16 KiB output limit per stream. It runs only when the operator clicks Run setup script. The first run of each SHA-256 in the same Git common directory also requires approval. Approval persists on the host, and the host rechecks the hash when it receives a run request. The script runs with the host account's operating system permissions. The session can start turns while setup runs. Finishing or forking that checkout into a new worktree waits for setup to exit. The latest result and output are retained locally and can be viewed on demand.

Settings › Data › Worktree cleanup lists up to 100 on-disk managed checkouts per computer for sessions finished with Keep or for which no session was saved. The host records ownership before creating a checkout. Retained checkouts recorded in older session history are also eligible. Cleanup rechecks that no live session uses the checkout and that it is still registered with the recorded repository. The operator confirms removal and separately confirms discarding any tracked changes, untracked files or ignored local files. Removal leaves the Git branch and session history intact.

## Mobile companion

D66 adds an Expo React Native client in `apps/mobile-client` and a narrow opt-in HTTP/WebSocket gateway. The reusable gateway belongs to `apps/host/src/mobile`; Electron supplies its lifetime and an adapter to the existing ComputerManager. It routes to Local or an already-connected SSH host without creating another host runtime or database. Mobile and desktop share Zod contracts, session revisions and action identities; native views remain separate from the desktop component library.

The gateway is off at startup. Short-lived one-use pairing grants create revocable device tokens whose hashes are persisted atomically. HTTP uses Bearer authentication; an alternative WebSocket endpoint authenticates in a bounded first frame. The mobile app uses a bounded NDJSON HTTP event stream with redirects rejected because native WebSockets can follow redirects before exposing the connection to JavaScript. Public connections require TLS. Snapshot/event delivery subscribes before reading state and buffers intervening events; reconnect replaces the client view with authoritative state. The phone stores credentials in SecureStore, rejects external plaintext, suspends streams in the background and never replays mutations. [Mobile setup](mobile.md) describes the execution model, limits and deployment options.

## Idle provider inspection shutdown

Completed Codex metadata and bootstrap inspections close stdin and allow up to 300 ms for the actual process close event before the existing forced cleanup. This applies only to healthy RPC peers without pending requests. Active cancellation, Stop and run finalization keep their process-tree cleanup. Neither a successful termination command nor a missing PID substitutes for confirmed closure.

## Provider account usage

D65 adds a host-scoped, read-only `provider-usage` request with shared Zod contracts. A dedicated service coalesces concurrent requests and caches successful Claude observations for four minutes and Codex observations for 30 seconds. Unsuccessful reads back off from five minutes to one hour, report their next eligible check and reset the delay after success. Manual and post-turn refreshes share this host gate. It runs independently of session execution and joins the host's existing bounded probe lifecycle. Account metadata and quota observations stay in memory; they are not written to session history or offline computer snapshots.

Codex uses an owned app-server process for `initialize`, `account/read` with token refresh disabled, and `account/rateLimits/read`. Claude uses an owned, non-persistent control connection for `initialize` and `get_usage` with `skip_behaviors: true`, disabled hooks, strict empty MCP configuration and no tools. Neither path sends a user message or starts a model turn. Nesvo uses each installed provider's existing login without reading credential stores directly. Deadlines, bounded output, cancellation and confirmed process cleanup apply to both readers. Claude's usage command is experimental; unsupported versions return an explicit unavailable result.

Only reported windows become percentages. Native durations, reset timestamps, account labels and plans are preserved; malformed or unavailable data never becomes zero usage. Provider permission is retained only when explicitly reported and never inferred from a percentage or reset time. Usage data does not grant or block session permissions. Additional billing/credit balances are outside this stage.

Electron validates and routes the request to Local or the selected connected computer. An offline request fails without reconnecting automatically. Renderer observations are keyed by host, with generation checks against late responses. The visible application refreshes the selected computer every two minutes, after a finished turn and on demand, subject to the host cache. The rail shows remaining allowance in the most-used reported window. Details show every window, last check and reset time; observations become stale after five minutes, disconnection or a passed reset. Expiry never fabricates a refreshed allowance. The account icon opens both providers and remains available in compact layouts.

## Provider profiles

Each host stores its own provider accounts in SQLite. A profile has a stable ID, provider, label and absolute configuration directory. The host checks directory ownership using the host user’s UID or Windows SID and validates the canonical path before use. The application does not open credential files or write to the provider configuration directory. The CLI still owns its normal account and transcript files.

New sessions bind their provider account at creation. The default account inherits the host CLI environment with no added override. A named Claude Code profile supplies `CLAUDE_CONFIG_DIR`, and a named Codex profile supplies `CODEX_HOME`. Probes, provider launches and resume, skills, MCP discovery and conversation import use the selected profile. D65 usage observations are cached separately by provider and profile. Existing sessions and forks keep their original account. A same-provider worker inherits its parent's account, while a worker using another provider starts with that provider's default. Accounts referenced by sessions or group defaults cannot be removed.

Settings › Account and limits manages the selected computer's accounts and checks their sign-in and quota data. Desktop defaults are scoped by computer and provider. A group can prefill an explicit account or inherit the desktop default. Account metadata stays on its owning host except for the labels, configured paths and status data returned to the desktop. Conversation adoption keys the provider conversation ID by profile and resumes under that same profile. New workflow tasks use the provider defaults defined by the existing workflow flow.

## Turn usage

Each agent message carries `usage`, a `turnUsage` record with input, output and cached input tokens, cost in US dollars, `durationMs` and `source`. Every field is `null` when the provider did not report it and `source` is `provider-report` only when at least one field was reported; nothing is estimated and an unreported value is never zero. Messages saved before this record existed read back as `null`. The host copies the value from the adapter result onto the agent message when the run is finalized, so it is stored in the session document and survives restarts. A failed or stopped run keeps the usage only when the provider delivered its final result frame (Claude) or turn completion (Codex); a run that ended without one keeps `null`, including tokens received earlier in the turn.

`inputTokens` counts all input tokens of the turn and `cachedInputTokens` the part served from cache. Claude Code reports cache reads and cache writes separately from `input_tokens`, so the adapter adds them to form `inputTokens`. Claude's final `result` frame supplies `usage`, `total_cost_usd` and `duration_ms`; the dollar amount is the provider's own estimate of API-equivalent cost and is not a billed amount on a subscription account.

Codex app-server 0.167.0 sends `thread/tokenUsage/updated` notifications during a turn with a `last` and a cumulative `total` breakdown, and `turn/completed` carries the turn's `durationMs`. The adapter takes the change in `total` from just before the turn's first update to its last update, which is the turn's own consumption even on a resumed thread. The protocol reports no dollar cost for a turn, so Codex `costUsd` stays `null`; a separate thread usage request with credit and dollar estimates exists but is not used.

## Costs and budgets

D72 adds the `costs` host capability. SQLite schema v12 indexes one row per session and run from the stored agent messages. Migration fills the index from existing history. The host writes each new turn and its final provider-reported cost in the same transactions as the session snapshots. Running turns and any turns with missing cost contribute to the unknown-cost count. A reported zero remains a reported amount.

The Costs rail entry opens the report for one computer. The host groups current calendar day, week or month spend by the turn's start date in the requested IANA time zone, through the current day. Weeks begin on Monday. Reports include daily buckets, group totals by session, provider or directory, and up to ten sessions ordered by reported cost.

The host owns its budget rules and calculates their periods in its local time zone. Directory rules match the stored working directory exactly. When reported spend reaches a rule's limit, the next turn either starts with a durable budget warning or is refused before the request is recorded or sent to the provider. The same check applies to operator messages, queued turns, review corrections, worker turns, workflows and automations. Budget changes apply to subsequent turn starts. Unknown amounts are excluded from reported spend.

## Process boundaries

```text
React renderer (plain TypeScript, base shadcn)
  |
  | window.nesvo: session commands, health, subscriptions
  v
Sandboxed preload (narrow typed API)
  |
  | Electron IPC, caller checked by main
  v
Electron main (window and host process lifetime)
  |
  | utilityProcess messages, Zod commands/responses/events
  v
Node host (Effect scope and services)
  |
  v
SQLite (identity and versioned conversation snapshots)

Node host -> owned Claude Code CLI -> normalized text/activity/result
Node host -> owned Codex app-server over stdio -> text/activity/approval/result

Standalone Node entry -> JSONL transport -> the same host service
```

Bun installs dependencies, runs scripts and builds the standalone host. It is not a runtime requirement for a packaged desktop.
Electron provides its own embedded Node for the utility process. The standalone host uses Node 24.
The host imports no Electron code; its desktop transport adapter belongs to the desktop main process.

Effect owns the database, session service, capability probes and request stream lifetime. Finalizers cancel owned provider work before closing SQLite. In the embedded/stdio host, they run on normal shutdown and owner transport completion. The independent host below supplies a process-owned request stream instead of an individual client's stream.
SQLite uses a versioned bootstrap and transaction, WAL, foreign keys and a busy timeout. An unsupported newer schema is rejected before migration.
Schema v4 preserves host identity, provider threads and conversation snapshots. Earlier migrations retain provider modes and pending approvals; v4 adds parent/run relationships, worker scopes, delegation capability and proposals. Existing conversations default to delegation disabled. A snapshot atomically contains the user message, agent message, run ID, provider ID, state and revision. Accepting a worker commits both parent and child snapshots in one transaction before launch. Text is flushed in short batches and at termination. If final persistence fails, a bounded retry and unsaved snapshots prevent new messages from overwriting results. Restart marks unfinished runs and proposals interrupted and invalidates pending operation approvals.
SQLite remains on Node's built-in driver. Drizzle integration waits for stable support for this driver; no release candidate is installed. Database types would not replace public Zod request validation.

Schema v6 adds durable tool activity to session snapshots. Each item is identified by its run and native provider item ID, with normalized kind, title, paths, status and timestamps. Output and details are bounded; private reasoning and raw provider payloads are not persisted as activity. Text and activity updates share the existing batched persistence path. Terminal updates cannot regress to running. Stop and restart finalize unfinished items without inventing successful completion, and older sessions default to empty activity and unknown completion timestamps.

Activity retains the latest 100 entries per run and 300 per session. Run-specific markers identify omitted history, including wholly evicted runs; late updates cannot reinsert evicted entries during an active run. Output is limited to its last 4,000 characters, details to 2,000, and paths to ten. Known credential patterns and terminal control sequences are filtered; this is not a guarantee that arbitrary tool output contains no sensitive data.

## Independent host connections

D63/R1 adds a Linux daemon with one existing host runtime behind a process-owned request queue. Clients attach through a private Unix socket and a version/identity handshake. Client EOF removes reply routing and subscriptions; only daemon shutdown ends the owner queue and triggers provider cleanup. Transport request IDs are mapped per connection; semantic message/decision IDs are preserved. Pending operations keep their runtime budget after their client disconnects.

The same OS user owns the private socket, repositories, provider logins and data. No TCP port is opened. The bridge uses JSONL and never reconnects or replays commands automatically. The stable instance ID detects a mismatched database; it is not an authentication credential. Full startup, reconnect and resource-limit behavior is documented in [independent-host.md](independent-host.md).

D64/R2 and R3 add Computers in Electron main. Local keeps its owned utility process; each remote connection owns an OpenSSH child attached to the Linux bridge. OpenSSH requires an existing verified host key and public-key authentication. The renderer cannot supply shell commands. The daemon instance ID is pinned after its first verified handshake and persisted before the connection becomes available. [Linux host setup](ssh-host.md) describes installation and the generated systemd user unit.

Every desktop session and review carries a host ID separately from its native record ID. IPC validates that target, and command routing never depends on the selected conversation. Sidebar and Inbox aggregate all computers; workers, files, skills and decisions remain on the originating host. Local is the default for a new session. Provider availability is inspected independently per connected host.

Connection setup subscribes before fetching both authoritative snapshots, buffers intervening events and merges by revision before enabling commands. Generation checks reject late responses from replaced connections. Disconnect invalidates that connection without rewriting run statuses or replaying requests. The UI labels offline work as last known and disables mutations and live reads while retaining saved conversations and diffs.

Remote configuration and the bounded offline cache use separate atomic files under the desktop profile. Configuration records connection parameters and the host identity, never private key bytes or provider credentials. Cache save failures are visible but cannot prevent disconnection or removal. Reopening restores saved remote histories from the cache and then connects each saved computer automatically; synchronization reloads the host's current state. Removing a computer deletes its desktop registration and cache, not its remote data or running service. App shutdown terminates Local work and closes remote SSH children only.

## Session history windows

The host stores whole sessions, but nothing outside it receives a whole history by default. Contract revision 2 replaces full session payloads with session windows: the session metadata, `messageCount`, aggregated `usageTotals` and a contiguous newest suffix of messages. `list-sessions` returns summaries whose suffix holds the last two messages; SQLite extracts them with JSON functions, so listing does not parse every message. Command responses and `session-changed` events carry the same two-message tail. History is append-only after a turn starts: only messages of the current run change, and they are always inside that tail.

While a reply streams, the host emits `session-message-upserted` about every 75 ms instead of a snapshot. It carries the metadata, the index and body of the one changing message, and `baseRevision`, the revision of the previous event the host emitted for that session. Persistence saves that bump the revision without an event do not break the chain. A receiver applies an upsert only when its stored revision equals `baseRevision`; otherwise it keeps the metadata and a valid shorter suffix, and an open conversation reloads its newest page. Snapshots merge into a longer loaded window when their suffix overlaps it. The same merge function in the contracts package is used by the sync buffer, Electron main, the renderer and the mobile gateway.

`get-session` returns a window with the newest page (40 messages by default, at most 200 and about 4 million characters). `read-session-messages` returns the page before a message ID cursor, oldest first within the page, with the next cursor or null at the start. The renderer loads the newest page when a conversation opens, prepends pages from Show earlier messages or when the reader scrolls to the top, and pages backwards to reach a history search result. It keeps loaded windows for the four most recently opened conversations and trims the others to their summary tail.

Electron main keeps summaries for every session and windows for the eight most recently opened sessions per computer. The offline cache (version 2, at most 16 MB) stores both; the oldest saved windows are dropped first when it grows too large, and version 1 caches are converted to summaries on read. Offline conversations show their saved window and refuse earlier pages they do not have. The mobile protocol is unchanged: the gateway turns upserts into `session-changed` with its own window of up to 40 messages, and fills that window for the 16 most recently updated sessions when a phone synchronizes.

## Desktop resilience

Electron main opens the window before any host synchronizes; the renderer shows its loading state and applies the computer and snapshot events that follow. Local and SSH computers recover without operator action, but only by reading state: health, sessions and reviews. Requests that were in flight fail, and no command is resent.

- The local host is restarted after 1, 2, 5 and 15 seconds. After the fourth failed attempt the computer shows an error and Retry starts a new attempt. A connection that stayed up for at least a minute resets the attempt count.
- Saved SSH computers connect at startup, after a dropped link (2, 5, 15, 30 and 60 seconds) and after the system resumes, when connected links are probed with a health request. A failed manual Connect and an explicit Disconnect do not start automatic attempts. Identity mismatches and refused handshakes are permanent and wait for the operator.
- Health carries `contractRevision`. A host whose revision differs from the desktop's shows the `incompatible` state (Update required) with the direction of the mismatch and accepts no commands.
- Events that arrive while a connection synchronizes are coalesced per entity (session, review, scheduled job, job run, workflow run, workflow step, session groups), keeping the newest revision. A message upsert that follows a buffered snapshot or an upsert of the same message is folded into it. More than 4,096 buffered entities close the connection, which then reconnects.

Main writes rotating `main.log` and `host.log` files; see [development.md](development.md). IPC failures are logged; Zod validation errors reach the renderer as one short sentence. The renderer reports render failures, unhandled errors and dropped workspace events through a validated, size- and rate-limited channel. A crashed renderer reloads up to three times a minute before a dialog offers Reload, Open logs or Quit. Notification clicks restore and focus the window through the preload, and approval requests flash an unfocused window. Packaged builds use a menu without DevTools or reload (App, Edit and Window roles on macOS, none elsewhere). Permission checks allow notifications and the sanitized clipboard write used by Copy buttons; redirects and frame navigation are blocked like top-level navigation.

## Restart and recovery

D62 adds an exclusive owner for each host data directory. Electron takes its single-instance lock before creating a host. The host independently holds an exclusive transaction on a separate ownership.sqlite connection before opening the application database or reconciling sessions. The operating system releases this ownership when the process closes or dies; no stale PID file is deleted and no unknown process is killed. Effect keeps ownership until provider cleanup and database closure finish.

Reloading the renderer does not stop the host or replay requests. The renderer subscribes before loading authoritative history and merges by revision; review actions remain disabled while session or result loading failed or remains pending. Local navigation preferences restore the last session/Inbox and saved review ID/file. Missing or invalid preferences fall back safely. They do not store run status, permissions, commands or review decisions. Unsent drafts remain transient.

Optional interruption metadata records the run ID, reason and time on the session and agent message. Controlled host shutdown, unfinished records found at startup and unexpected provider disconnection have distinct reasons. Explicit provider errors remain failures, and operator Stop remains stopped. Partial output and prior interruption causes remain in history after a new turn. Incomplete outcomes never create successful reviews.

Startup reconciles unfinished sessions, activities, expired operation approvals and parent/worker proposals in one transaction. New proposals preserve the exact child run ID; legacy matching is conservative. A durably completed worker remains completed even when its parent did not receive the terminal event before shutdown. A resumed parent references saved reviews from its latest delegation group with actual children, even if that parent run never produced a review. Older parent dependencies are a fallback only when the latest group created no child. Current child review versions and writable fingerprints still participate in acceptance checks.

Continuation requires a new operator message and keeps the existing provider thread. The prompt explains the previous unconfirmed outcome and available worker state so that the provider can inspect current files before doing more work. Opening the app or pressing Continue conversation never sends a provider task. Already committed messages, worker decisions and review decisions are not replayed. Stable IDs and transactional correction preparation make retries idempotent, including after restart.

## Scheduled jobs

D68 adds host-owned scheduled jobs. Schema version 7 stores definitions in `scheduled_jobs` and their history in `scheduled_job_runs`, inside the same bootstrap transaction as earlier migrations; a failed migration rolls back completely and keeps the previous version. Runs are unique per job and scheduled time, manual runs per request ID, and deleting a job removes only its runs. Sessions gain nullable `scheduled_job_id` and `scheduled_job_run_id` links that become null when the job or run disappears, so sessions and reviews remain ordinary history. Each job keeps its latest 100 finished runs, ordered by recording time. A host accepts at most 20 jobs.

`ScheduledJobService` runs in the host scope, including the Linux daemon. One timer is armed for the earliest next run and capped at 2^31−1 ms; every change re-arms it, and the clock is injectable. A tick collapses every missed occurrence of a due job into a single decision with the shared schedule module. An occurrence more than two minutes late becomes one `skipped/missed` record; there is no catch-up. Otherwise an active run of the same job records `skipped/overlap`, and an operator command in the last ten minutes records `skipped/busy`. Work in other sessions never skips a run; the launched run waits for its own folder instead. Otherwise the run is claimed as `starting` in the same transaction that advances the next run time, and the launcher port is called only after commit. A launch refused as busy becomes `skipped/busy`.

Startup marks `starting` and `running` runs `interrupted` with reason `restart` inside the session recovery transaction and never relaunches them; the first tick then records anything missed while the host was down. Saving a changed schedule or time zone, or reactivating a job, computes the next run from the current time, so a paused job never accumulates missed runs. Saves, activation changes and deletions compare the expected revision. Run now records a manual run only when the scheduler is open and the job has no active run; otherwise it returns a busy error without a record. Health reports the `scheduled-jobs` capability.

The session launcher in `apps/host/src/scheduled-jobs/launcher.ts` turns a claimed run into one ordinary session on the same host, through the session service rather than IPC. It first resolves a set folder in a short-lived child process with a five-second bound, so a hung network folder cannot block the host at an unattended time, and applies the create-session rules: an empty folder gets a fresh workspace, a missing or inaccessible one fails the run as `failed/folder` without a provider process. Settings that the create-session schema rejects, such as an unsupported Claude model, fail the run as `failed/catalog`. A Codex effort is confirmed against the reported catalog as for an interactive session; a withdrawn effort fails the run as `failed/catalog` before any thread or turn, while a Codex that is not ready fails it as `failed`. A Codex model without an effort is not checked in advance, as in an interactive session, so a withdrawn model fails during the turn. If an operator command arrived within the idle window before a scheduled start, the run is `skipped/busy`. When the job folder is claimed by a conflicting run or operation (see Folder locks), the run stays `starting` and waits for the folder up to the job's `timeoutMinutes`; a folder that stays claimed until then records `skipped/busy` without a session. A job without a folder gets a fresh workspace and never waits. The session uses exactly the job's provider, model, effort and read-only mode, and the title is the job name followed by the local date and time of the scheduled occurrence (or of the manual start) in the job's time zone.

The session service takes an internal `origin` that is not part of the public create-session request, so Electron IPC, SSH and the mobile gateway still reject an `origin` field through the strict schema. The origin is a discriminated union: `operator` for interactive sessions and `scheduled-job` with the job and run IDs, which are stored in the session links and exposed as `scheduledJobId` and `scheduledJobRunId` in the session projection. The link columns are authoritative on read, so a deleted job or run also clears the projection. A scheduled-job origin always disables delegation, so Codex registers no worker tool. Provider arguments, permission modes, sandbox and approval policy are those of an interactive read-only session; no new flags reach either adapter.

The prompt is sent as the first message with a message ID derived from the run ID, so a repeated send in the same process returns the existing run. The run records its session and session run as `running`, then follows the session: a completed turn records `completed` with its review, which reaches the Inbox as an ordinary result acceptance; operator Stop records `stopped`; a host shutdown records `interrupted/restart`; a failed turn records `failed`. Operation approvals during a Codex run use the existing rows and count against the deadline. Each run has a host-owned deadline of `timeoutMinutes` from its start that calls the same Stop path as the operator and records `failed/timeout`; process-tree cleanup is the session's own, so on Windows descendants already orphaned from the provider's tree are not covered. A crash between session creation and the first message leaves the empty session, and startup marks the run `interrupted`; it is never sent later. If the first message is refused after the session was created, the empty session also stays and the run records `failed` or `skipped/busy` without a session link. If recording the started run fails, the deadline and the outcome tracking still apply. Manual Run now uses the same path. Sessions created by scheduled jobs are kept; deleting them together with old runs is not implemented yet.

The launcher checks the provider account limit before it resolves a folder or creates a session. It calls `ProviderUsageService.read()` for the job's provider on this host, so the existing cache and failure back-off apply, no new probe exists and no model turn is started. Only an observation with status `ready` that reports a window at or above 100% used with a reset time in the future stops a run. The run is recorded `unavailable/limit` with `resetAt` set to the latest reset among such windows, never has a session and does not count as a failure. Unavailable, stale, unsupported or failed observations, such as Claude Code's experimental usage read, launch the run: the host does not guess an allowance from any other percentage and never infers recovery from one (D65). A reset time already in the past does not stop a run, and neither does an observation whose provider reports `ordinaryUsageAllowed: true`, because that explicit signal outranks any percentage. The observation is the one the usage service cached, so it can be up to four minutes old for Claude Code and thirty seconds for Codex. Codex reports limits per group and the host does not map a job's model to a group, so an exhausted window in any reported group holds every Codex job until its reset; Claude Code limit windows are handled the same way.

A known reset time is remembered per provider in the launcher until it passes. Further runs of any job on that provider before then are recorded `unavailable/limit` with the same `resetAt` without another usage read. The memory is in-process only, so after a restart the first run reads usage again. During a run, Claude Code's stream event `rate_limit_event` with status `rejected` marks the run outcome as a limit: the session keeps its failed state and failure text, the scheduled run becomes `unavailable/limit` with the event's reset time when it reports one, and no review is created because only completed results reach the Inbox. Codex has no recognised in-run limit error shape, so for Codex only the pre-start check applies and an in-run limit still shows as `failed`. The repository holds no captured real Claude limit rejection; the `rejected` event shape is the one the adapter already parsed and is exercised only by a fixture, so it needs confirmation against a real account limit.

A scheduled job definition carries an optional `workflow` of `{ name, specPath }`, null by default so stored definitions and cached projections still parse, and a run records an optional `workflowRunId`. When a workflow is set the prompt may stay empty because the spec supplies the task; a job without a workflow still needs a prompt. When a workflow is set the launcher keeps the limit gate, the folder check and the operator-idle rule, then starts a workflow task in process through the same path as `start-workflow-task` instead of creating a session and sending the prompt, which is ignored. The task uses the job's provider, model and effort in `read-only` mode, `worktree` isolation when the folder is the top level of a Git repository and no isolation otherwise, and the other provider with its default model as the gate. A missing workflow, spec or invalid definition ends the run as `failed` with the `catalog` reason, and a project root that already has an active workflow run ends it as `skipped` with the `busy` reason. The run row records the author `sessionId` and the `workflowRunId`; `runId` stays empty because the session turns belong to the workflow run. The run finishes when the workflow run settles: `passed` is `completed`, `stopped` is `stopped`, `interrupted` is `interrupted`, and a failed or rejected run is `failed`. The launcher reads the stored workflow run once a second for that. The job timeout stops the workflow run, which ends the author turn, and records `failed` with the `timeout` reason. A workflow run interrupted while the host is running leaves the job run `interrupted` without a reason, because the operator can still resume it. A scheduled workflow checks the provider limit gate only before the start; a limit reached during the run is not remembered. The workflow's command and action steps run unattended with the repository's definitions, in the task worktree when the folder is a Git repository and in the project folder otherwise. Schema version 9 adds the nullable `workflow` JSON column to `scheduled_jobs` and the nullable `workflow_run_id` column to `scheduled_job_runs`, which becomes null when the workflow run is pruned. Schema version 10 renames everything the product used to call a pipeline: the tables `pipeline_runs` and `pipeline_steps` become `workflow_runs` and `workflow_steps`, the columns `pipeline_name`, `pipeline_run_id`, `pipeline_step_id` and `scheduled_jobs.pipeline` take their `workflow` names, the indexes are recreated under the new names, and the stored JSON documents are rewritten in the same transaction (`pipelineRunId`, `pipelineStepId` and the run's `pipeline` key, plus the `pipeline` message origin). The data folders `pipeline-specs` and `pipeline-evidence` are renamed to `workflow-specs` and `workflow-evidence` on the first start that finds them. The rename keeps no alias in the schema; a host older than version 10 refuses the database as unsupported. Schema version 11 adds the `assistant_changes` table described under the workflow assistant.

### Automations in the desktop

The desktop calls scheduled jobs Automations in every label, message and host-generated error that reaches the operator; identifiers, IPC channels, events and the database keep the `scheduled-job` names. An Automations row sits in the top sidebar group after Inbox and appears once any computer reports the `scheduled-jobs` capability. It opens the list in the main column; a job opens like a session with the breadcrumb `Automations / name`. The open list or job is part of the saved workspace location, like the last session or the Inbox. Connected computers without the capability keep their own sessions and show a short update note in the list instead of their jobs.

`useScheduledJobs` loads each connected, capable computer's jobs and the first page of runs per job after every synchronization, merges job changes by revision and run changes by ID, and drops jobs of removed computers. The list row shows the schedule, computer, folder, provider and model, the next run or Paused and the latest run with its reason; Run now and Pause or Resume appear on hover and focus. The detail adds the Active switch, Run now, Edit, Duplicate and Delete behind a confirmation, the next three planned times from the shared schedule module and the run history with trigger, time, duration, the linked session and the review state of its result. Run now reuses its request ID for a retry after an unconfirmed response, so a lost response cannot start a second run; a busy or missing-job refusal, or a manual run recorded since the attempt, starts the next click with a new ID. A list response replaces the jobs of its computer only if no newer list request started, keeps a newer job revision or a job changed after the request began, and does not bring back a job removed meanwhile. Stop on an active run uses the session Stop.

The editor is a right sheet that reuses the new-thread computer, folder and model pickers. A job stays on its computer, so editing fixes the computer. Editing keeps the saved model and effort while the provider has not reported its catalog or no longer lists the model, and says so instead of replacing them; a job deleted while its sheet is open cannot be saved. Access is a fixed read-only badge with the provider explanation. A prompt that starts with `/` is rejected with an inline message because the launcher sends prompts as plain text. Field errors appear after a field is left or a save is attempted; the schedule shows the next three occurrences in the chosen IANA zone from `Intl.supportedValuesOf`. A save sends the expected revision and a stale save offers a reload. A new job keeps its generated ID while the sheet is open, so a retried create after an unconfirmed response finds the saved job instead of creating another. Duplicates start paused.

Sessions created by a job are grouped under one collapsed `Automation · name` row per job in the computer's section of the sidebar and are left out of the session list. Inbox result rows from such sessions carry the same origin label without a new row type. While a job's session holds a folder, the composer of another session that waits for that folder and the Inbox show `Automation name is running · Stop` instead of the folder wait text. Run now is disabled only while that job runs. A failed Stop from these places is shown with the job. A job with a workflow is recognised through the `workflowRunId` of its runs: its author session keeps its place in the workflow tree of the sidebar, while the Inbox origin, the busy text and Stop treat it as the automation's, and Stop on such a run stops the workflow run instead of a session turn. The editor keeps the workflow, computer and folder of such a job fixed and hides the prompt.

### Automations on an unattended host

An automation belongs to the host that stores it. The desktop and the mobile gateway only read and command it; when no client is connected the host's own timer still fires the run, and a client that connects later reads the stored run, session and pending result like any other history. Connecting starts no scheduler and replays nothing: a run is claimed once, in the transaction that advances the next run time, and the unique run key refuses a second claim. A second desktop on the same data folder is refused by the existing ownership lock, so there is never a second scheduler.

A scheduled run is also recorded `skipped/busy` when an operator request arrived in the last ten minutes, so a connected, active client holds scheduled runs back; the same gate applies again just before the first message. Other running sessions do not hold a run back; it waits only for its own folder. A run launches only through the session launcher: the usage reader first, then the folder and catalog checks, then one ordinary read-only session on the same host with delegation off, and one first message whose ID is derived from the run ID. The usage reader never starts a model turn. An exhausted window with a reset ahead records `unavailable/limit` with the reset time and creates no session; unavailable usage launches. Claude Code can report a limit during a run, which records `unavailable/limit` too. Codex has no recognised in-run limit shape, so a limit reached during a Codex run shows as `failed`. Occurrences missed while the host was down collapse into one `skipped/missed` record with their count and never run later. A host that crashes between creating the session and sending the first message leaves an empty session, and the run becomes `interrupted/restart` at the next start and is not sent again.

The read-only mode is the safety assumption of an unattended run: nobody is present to answer an operation approval, so the launcher offers no write access. A provider that still asks for approval leaves the run waiting for the operator until its time limit. Process-tree cleanup on a time limit or Stop is the session's own; on Windows, descendants already orphaned from the provider's tree are not covered. The principal desktop scenario seeds the stored next run time in the isolated profile's database while the application is closed instead of using a test clock, because the production host entry point cannot inject a test clock.

D74 adds optional command arguments, the last check and a pending start to the scheduled job snapshot. Older job records parse without these fields. SQLite version 15 adds columns for these values and a private SHA-256 baseline hash, plus a per-job UTC day ledger of claimed starts independent of run history retention. The `scheduled-job-change-triggers` capability gates the new editor fields and decision route. Older desktops with strict capability validation need a desktop update when connecting to a host that advertises this capability.

For a conditional job, the timer advances the schedule before spawning a single check for the latest due occurrence. One process per job may check at a time. The check uses the host's bounded process runner with direct argv, an explicit folder and no command output logging. Pause, edit, delete and orderly shutdown cancel in-flight checks. The host atomically records the check result, any new hash and the decision to hold or claim a run. Failures preserve the last successful hash. An ask-first request retains its ID across restarts. Start or Skip consumes that exact ID in the same transaction as the run record, and repeat or stale decisions cannot start it again. An authorized Start bypasses the idle delay and still checks for an active run of the job, remaining daily capacity and the existing provider and session limits. Reconnect loads the host snapshot with its pending requests. Pending requests never resume themselves.

## Ownership

| Area                 | Owns                                                 | Must not own                                           |
| -------------------- | ---------------------------------------------------- | ------------------------------------------------------ |
| contracts            | Zod schemas, inferred data types, narrow desktop API | Runtime services, UI state, provider implementations   |
| desktop main/preload | Window, IPC boundary, child process lifetime         | Domain decisions or credentials in renderer            |
| renderer             | Presentation and operator interaction                | Effect, filesystem, process control or database access |
| host                 | Authoritative state, resources and provider adapters | UI components or Electron dependency                   |

Requests carry unique correlation IDs. Session events are separate from responses and carry monotonically increasing revisions. The renderer subscribes before loading history and merges only newer snapshots. Send acknowledges promptly; the main request loop never waits for model completion, so health, Stop and shutdown remain responsive. Duplicate message IDs do not launch a second turn.
The renderer cannot send arbitrary host requests. It can only call the API exposed by preload.
Main denies external window creation, renderer navigation and permission requests.

## Folder locks

The host serializes work per folder, not per computer. Every provider run claims its session folder, the canonical (`realpath`) directory the session works in; a session worktree is its own folder. A session in a writable mode (any mode other than `read-only`) claims its folder for writing, a `read-only` session claims it for reading. The claim follows the session's mode rather than the turn, because a writable session captures the workspace baseline for its result diff even for a read-only workflow turn. Two claims conflict when their folders are the same or one contains the other and at least one of them writes; nested folders conflict because the diff of the outer folder covers the inner one. Readers share a folder with readers. A reader and a writer never run in overlapping folders: the writer's diff and saved snapshot stay its own, and an analysis never describes a folder that another session is half-way through changing. Sessions in different folders, including two worktrees of one repository, run at the same time. The host sets no session count limit; manual sessions are unlimited and concurrency policy belongs to workflows.

A delegation group shares one claim key, so the parent and its workers do not conflict with each other; the existing worker rules (worker directories inside the parent, no overlapping writable workers, a writable parent delegating only read-only workers) keep the group consistent. Other sessions conflict with the group as with any run, and groups in different folders run in parallel. A worker is refused as `busy` when another session holds a conflicting claim on its directory.

Operations that change or verify a folder claim it exclusively for their duration: a pull request checkout claims the session folder, finishing a session worktree and removing an orphaned checkout claim the worktree, a fork claims its source folder, and a result decision claims the result folder and the folders of its worker results while it verifies their fingerprints. A worktree setup script claims the worktree against other sessions but not against its own session. Creating a session in a folder that is being removed is refused. Compaction claims the session folder for reading. Independently of folders the host refuses a run while it shuts down or while the session itself runs, refuses a workflow turn while a response is unsaved, and keeps creating and removing worktrees apart because both change the repository's worktree metadata.

A send to a session whose folder is claimed is refused as `busy` with `Waiting for <folder>, which <operation>.` A queued message waits instead: the host records the session as waiting in memory, and its session window and events carry `waitingFor` with the claimed folder, the operation and the claiming session, if any. The field is not stored; a change of the claim saves the session without touching its `updatedAt`, so clients receive a newer revision. Whenever a claim is released, the host goes through the waiting sessions in the order of their first queued message and starts each one whose folder is free through the ordinary send path. Releases are announced after the current call returns, so an operation that releases a claim and launches its follow-up run in one step cannot be overtaken. Workflow runners, automations and agent pull request reviews wait on the same release signal. A held entry never starts this way, so Stop, failures and restarts still hold queued work and nothing restarts after a host restart.

The composer of a session whose folder another session holds, or whose queued message waits, shows `Waiting for <folder>` with a link to the claiming session and queues new messages instead of sending them. The renderer derives the claiming session from running sessions on the same computer with overlapping folders and conflicting modes, and from the host's `waitingFor`; the host decides.

## Message queue

A message submitted while the session's own run is active, or while its folder is claimed (see Folder locks), joins that session's queue instead of being refused. The queue is a per-session FIFO of at most 20 entries saved in the session document, each with its message ID, text and optional skill selection; older documents default to an empty queue. When a session's own run completes normally in the live host, the host starts the oldest entry, or lets it wait for the folder, through the ordinary send path with the entry's ID as the message ID, so a retried start cannot launch a second turn. When the run ends any other way (Stop, a failure, an interruption or a host shutdown), every entry in that session's queue is marked held, and startup recovery marks all restored entries held, so a restart never starts queued work. Automatic starts take only an entry that is not held; a held entry at the front blocks them for that session, including after a new message's turn completes. Only Send now starts a held entry, and it can start any entry. New entries join the queue unheld; a new message does not release held entries. A failed automatic start leaves the entry at the front and records the reason on the session. Removing an entry that has already started is refused as not found. Editing a queued entry removes it and returns its text to the composer; the skill selection is not restored.

## Attachments

Operators paste, drop or pick up to ten files of any type in the session composer with the paperclip button (accessible name Attach files). Limits are per type, because each type travels differently: images 5 MB (the size the providers accept as native image input), PDF files 20 MB (Claude Code receives them base64-encoded inside one stream-json line) and every other file 50 MB (copied once into the data directory). A file over its limit is refused in the composer with the type's limit, and the host enforces the same limits. The renderer stages each file on the session's host as soon as it is added, through `stage-attachment` requests of at most 512 KB so a frame stays inside the 1 MB request limit of remote connections; SSH computers therefore receive the bytes through the existing host channel and never through a local path. The host appends sequential chunks to a partial file under `attachments/uploads` while hashing them, holds at most ten unfinished uploads, refuses a chunk while the previous chunk of the same upload is still being written, identifies the type by its magic bytes (PNG, JPEG, WebP, GIF, PDF; everything else is `application/octet-stream`, and the file name and extension are ignored) and moves the content once to `attachments/<sha256>.<ext>`. A message or queued entry references attachments by SHA-256, type, size and name; the bytes never enter the session document. Sending confirms that every referenced file is still present with its recorded size, and the turn re-reads and re-hashes the bytes before the provider starts. An attachment may carry an `offset` into the trimmed message text; pasting, dropping or picking a file in the composer inserts an atomic token at the caret (or the drop point) and records that position, while the strip above the field keeps previews, upload state and remove buttons, and removing either one removes both. Attachments without an offset follow the text, so older messages and clients that send none, such as the mobile client, behave as before.

Delivery depends on the type and the provider:

- **Images** use native image input. Claude Code receives base64 image blocks in one stream-json user message, interleaved at the recorded offsets (text, image, text); Codex receives `localImage` items pointing at the stored files in the same order. Hosts report image support per provider: Claude Code when its `--input-format` offers `stream-json`, Codex per model from the reported input modalities. The composer refuses images with the reported reason, and a host that receives images for a provider that cannot take them fails the turn visibly instead of dropping them.
- **PDF files** reach Claude Code as base64 `document` blocks at their position, with the same stream-json requirement. Codex has no document input, so it receives a PDF as a file reference.
- **Every other file** is copied read-only into `attachments/sessions/<session ID>/<first 16 hex digits of the SHA-256>/<sanitized name>` in the host data directory, and the provider prompt carries `[Attached file: <name> at <absolute path>]` at the file's position. The visible message keeps its clean text and shows a file token. Claude Code turns with references pass that session folder with `--add-dir`, so Plan can read it with Read, Glob and Grep, and deny edits there with an `Edit(//<folder>/**)` rule in `--disallowedTools`; a Claude Code version without both flags fails the turn visibly. Codex sandboxes read the whole file system in both read-only and workspace-write mode, so no extra root is added and write roots stay limited to the session directory.

Hosts advertise `message-attachments` (images), `inline-attachments` (offsets) and `file-attachments` (PDF and other files, and `locate-attachment`). The desktop strips offsets before sending to a host without `inline-attachments` and offers only images to a host without `file-attachments`. History renders placed attachments as inline tokens: an image token opens the preview, and a file token shows a file-type icon, the name and the size. The strip above a sent message keeps image thumbnails and files that have no visible position. Thumbnails load on demand with `read-attachment` (images only), are cached per window and open in a Dialog.

On the local computer a file token offers **Open** and **Show in folder**. The renderer calls `openAttachment` with only a session ID, an attachment ID and the action; it never sends a path. Electron main refuses other computers, resolves the stored copy through `locate-attachment` (the host checks that a message or queued entry of that session references the ID and materializes the copy if needed), accepts only a path inside the session attachment folders, and opens it with the system default application. Open is limited to an allowlist of document, image and media extensions; any other file, including scripts and programs, is reachable only through Show in folder. Files attached on an SSH computer stay on that computer.

When a deleted session is purged after its undo period, the host removes its `attachments/sessions/<session ID>` folder and every stored content file that no remaining session or queued entry references. Restoring a session within the undo period keeps all files. Staged files that are never sent stay in `attachments/` until a later cleanup.

## Session groups and housekeeping

D69 lets the operator organize sessions on each computer. Groups belong to the host that owns their sessions and live in the `session_groups` table (stable ID, parent, sibling order, name and optional new-session defaults); the host keeps a revision counter in `metadata` and publishes `session-groups-changed` with the complete list after every group change, so every window converges on the newest revision. Groups nest at most three levels deep; the host refuses cycles, deeper nesting, unknown parents and reused IDs with `invalid-request`, and creating a group with an ID that already holds the same name and parent returns the current list so a retried request is harmless. Deleting a group never deletes sessions: its sessions and subgroups move to its parent group, or to Ungrouped and the top level, in one transaction.

Sessions gain `groupId`, `order`, `pinned` and `archivedAt`; documents saved before these fields existed read as Ungrouped, unordered, unpinned and active. Moving and reordering rewrite the sibling order in the same transaction as the move, and the sidebar sorts by that order and then by the most recent update, so an untouched group keeps the previous list order. Renaming, pinning, moving and archiving keep the session's `updatedAt`, provider thread, permissions and running work unchanged; a running session can be renamed, pinned and moved, but archiving is refused as `busy` while the session or one of its subsessions runs. Workers, workflow-step sessions and automation runs follow their parent and cannot be moved, pinned or archived on their own. Archived sessions keep their history and can be restored.

Group defaults (folder, provider, model, permission mode and workflow) only pre-fill the new-session form when a session is started from that group; the new session is created in the group and receives the default workflow through the existing assignment call. Editing defaults never changes an existing session.

The sidebar shows, per computer, pinned sessions, the nested group tree and Ungrouped sessions, followed by automations and an Archived toggle. Group rows offer New session, New subgroup, Rename, Edit defaults, Move to, Move up, Move down and Delete in their menu; session rows offer Rename, Move to group (a searchable picker that can also create a group), Move up, Move down, Pin and Archive, from the row menu or a right-click. Sessions and groups can be dragged with a visible drop indicator; the menus are the keyboard alternative. Search expands groups that contain matches and includes archived sessions only while the archived section is open. Collapse state is a local view preference in `localStorage`. Hosts without the `session-groups` capability keep the previous flat list.

Each session shows its lifecycle on demand. Hovering a sidebar row (after a short delay) or its status dot, or focusing the row from the keyboard, shows the status followed by `Created <date, time> (<relative>)`, `Last activity <relative>` and, for archived sessions, `Archived <relative>`; the row's accessible description carries the same lines. The session details card and the Context sheet show Created and Last activity rows. Last activity is derived in the renderer from data hosts already publish: the latest of the session's `updatedAt` (which renaming, pinning, moving and archiving leave unchanged, so it marks the last message, status change or run end) and the creation or completion times of its newest messages, falling back to the creation time. Dates use a fixed English format independent of the system locale, so no host or contract change is involved.

Clean up… in the sidebar options menu and the command palette opens a dialog that lists top-level sessions on connected computers with the `session-groups` capability whose last activity is at least 7, 14 or 30 days old (14 by default), oldest first. Running, stopping and needs-you sessions, sessions with a running worker or workflow step, pinned and archived sessions, workers, workflow-step sessions and automation runs are never listed. Every listed session starts selected; Archive sends one ordinary `set-session-archived` request per session, so the host's `busy` rule still applies, and a toast offers Undo, which unarchives the sessions that were archived. Deleting stays a separate, explicit per-session action and the dialog offers no bulk delete.

### Deleting sessions

A host that advertises `session-delete` accepts `delete-session` and `restore-session`. Deletion applies to a top-level session together with its workers; workers, workflow sessions and automation runs cannot be deleted on their own. The host refuses it as `busy` while the session or one of its workers runs, waits for an operation approval or has a worker proposal or plan waiting for a decision. Schema v17 adds `session_tombstones` (session, root, deletion time, purge time, purge mark). Deleting inserts one row per affected session in one transaction, publishes `sessions-removed` with their IDs and returns the root, its title and the purge time 30 seconds later. Repeating the request during that period returns the same deletion. Tombstoned sessions disappear from session lists and reads, their reviews from the review list and their messages from history search, while the stored rows stay intact.

`restore-session` within the period removes the tombstones of the whole batch, saves each session again so its revision increases, publishes the sessions and re-publishes their reviews; after the purge time it fails as `not-found`. The purge timer belongs to the host, so a renderer reload keeps the undo period, and a host start purges every tombstone whose time has passed before it serves requests. Purging deletes the session's history entries and reviews, replaces its document with `null` and marks the tombstone; nothing is replayed and the provider transcript is untouched. Worktree checkouts are not removed by deletion and stay in the host's session-worktrees folder.

Costs keep the provider-reported spend of deleted sessions: the cost index rows remain so totals and budgets do not drop when history is deleted, and the top sessions list names such a session "Deleted session". Electron removes the sessions and their reviews from its per-host cache when the event or the response arrives. The renderer confirms the deletion with a destructive ConfirmDialog and then shows a Toast with Undo until the purge time.

## Context window

Each session stores `context`, the latest context fill the provider reported: `usedTokens`, `windowTokens` and `reportedAt`. Both numbers come from the provider; nothing is estimated, and a session whose provider reported nothing keeps `null`. Claude Code's final `result` frame lists the turn's API calls in `usage.iterations`; the last call's input, cache read, cache write and output tokens are the tokens in context, and `modelUsage` gives the `contextWindow` of the model named in the `init` frame. Codex app-server sends `thread/tokenUsage/updated` with `last.totalTokens` and `modelContextWindow`; the last notification of a turn is used. A turn without such a report keeps the previous value. A finished compaction replaces it with the provider's post-compaction count (Claude's `compact_boundary.post_tokens`, Codex's token update during the compaction turn) or clears it when none arrived, and Restart clears it.

The session details panel always shows the fill as used and window tokens. The composer toolbar shows it only from 80%, as a warning-tone Meter with the percentage and a Compact button beside it while the action is available; its tooltip lists the used and window tokens and when the provider reported them. Without a reported value nothing is shown, so an unknown fill never reads as zero.

## Compacting conversations

Compact conversation, Compact with instructions (Claude Code only) and Restart session are explicit operator actions with one shared definition used by the header and sidebar session menus and the command palette. They are disabled while the host runs any work, and Nesvo never sends them on its own or interprets typed text as these commands. A compaction requires an initialized provider thread and the current session revision, and it counts as active work: the session is `running` under a transient run ID until the provider confirms, Stop cancels it, and the previous run ID and status return afterwards. Budget refusals apply as for turns.

Claude Code compacts in the resumed session: the adapter sends `/compact`, followed by the instructions when given, as a stream-json user message to `claude --print --resume <id>`. Claude Code 2.1.327 answers with a `status: compacting` system frame, a `compact_boundary` system frame with `compact_metadata` (`trigger: manual`, `pre_tokens`, `post_tokens`) and a successful `result` with no turns; the boundary frame is the confirmation. Codex compacts with `thread/compact/start { threadId }` on the resumed thread (app-server 0.167.0). The request returns at once; the compaction runs as its own turn with a `contextCompaction` item, and the completed item followed by `turn/completed` is the confirmation. The resume uses the same experimental API setting as the session's turns. A Codex that does not know the method fails visibly with an update hint. Codex takes no instructions, so the host rejects them.

A confirmed compaction appends `{ index, at, instructions }` to the session's `compactions`, where `index` is the message count at that moment, and the conversation shows a "Conversation compacted" divider there. Whether instructions were given is recorded, not their text. Nesvo history is unchanged; only the provider's context is summarized. A provider failure or a missing confirmation leaves `compactions` as it was and fails the session with the provider's reason. The provider's cost of a compaction is not attributed to a message.

## Forking and restarting sessions

Fork creates a separate session on the same computer with the source model, reasoning effort and permission mode. Its header links to the source history at the recorded message. The new session has its own messages, queue and results. Workers and sessions owned by workflow or automation runs follow their owning run's controls. The default fork uses the source folder. A Git source also offers a fresh session worktree at the source HEAD. The operator can carry tracked edits by applying a binary-capable Git diff against that exact starting commit. The patch is limited to 8 MiB. Untracked files are carried only through `.worktreeinclude`.

Codex forks the saved thread with `thread/fork` before saving the Nesvo session. The adapter applies the source sandbox and verifies the returned policy and distinct thread ID. Claude Code advertises `--fork-session` in its CLI help. Nesvo saves the fork intent and uses `--resume <source-id> --fork-session --session-id <new-id>` on the first operator message. If the recorded source thread advanced in Nesvo before that message, the host refuses to fork from a different point. Later messages resume the new thread by its own ID. Unsupported native forks fail visibly.

Restart requires confirmation for the current session revision. It clears the provider thread ID, keeps the recorded model, mode, folder and conversation, and holds queued messages. A saved history divider marks the boundary. The next operator message starts a fresh provider thread. Automatic worker result context and dependencies are scoped to the current thread. Both commands refuse to change threads during active work. Reopening the host restores recorded thread state without starting provider work.

## Claude operation approvals

Claude Code asks for permission through the documented SDK host channel of the installed CLI. For interactive MCP calls in Plan and permission requests in Accept edits and Auto, when `claude --help` mentions `--permission-prompt-tool` and lists `host` among the `--permission-prompts` choices, the host starts the turn with `--input-format stream-json --permission-prompts host --permission-prompt-tool stdio`. It sends an `initialize` control request and the prompt as one user message on the process's own stdin and closes stdin after the result. The CLI sends every permission question as a `can_use_tool` control request on stdout. No socket, port, token or extra process is involved: the channel is the private stdio pipe of the process the host owns, so only that process can ask and only the host can answer. An older CLI without this channel keeps `--permission-prompts none` and the previous refusal behaviour.

Each request is validated with Zod and becomes an operation approval on the session, shown like a Codex approval in the conversation and the Inbox (Command, File or Tool approval) and kept distinct from worker approval and result acceptance. The approval ID is the CLI's request ID and carries a fingerprint, a SHA-256 of the tool name and the exact input. `respond-approval` must name the active run, the pending request and the same fingerprint, so a decision cannot be applied to another run, another request or changed input, and an answered request cannot be answered again. Allow once returns the unchanged input with `decisionClassification: user_temporary` and no `updatedPermissions`, so no rule is saved and the next call asks again. Deny returns `user_reject` with a fixed message, optionally followed by the operator's own message (Claude denials only, at most 2,000 characters). The desktop sends the fingerprint and message only to hosts that advertise `claude-approvals`.

Nothing is approved automatically. A request that is not answered within five minutes is denied with a message saying so. A request the CLI withdraws with `control_cancel_request` leaves the session. A malformed request or one whose details exceed 100,000 characters is denied without asking, other control requests receive an error reply, and a repeated request ID fails the run. Stop and host shutdown terminate the process and drop pending requests. Startup reconciliation clears pending approvals of unfinished runs and marks those runs interrupted, so a restart never replays a decision. Workflow assistant and verdict turns, structured-output turns, ephemeral turns and plan-first worker plans keep `--permission-prompts none`.

| Session mode   | Without asking (CLI semantics)                                                   | Asks the operator once                                                                              | Refused without asking                                                         |
| -------------- | -------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| `read-only`    | Read, Glob, Grep                                                                 | Every enabled MCP tool call with a supported host approval channel                                  | Edits, Bash and other tools outside Plan’s allowed set                         |
| `accept-edits` | Read, Glob, Grep, TodoWrite; edits inside the working folders                    | edits outside the working folders or to protected files, configured MCP tools without an allow rule | Bash and tools outside `--tools`; calls the CLI itself denies by rule or check |

## MCP servers and hooks

The host offers user-scope MCP servers automatically for interactive turns. Edit modes also use the CLI’s enabled user hooks. Plan and Read-only disable hooks because they can run commands outside an operation approval. Workers, workflow turns, automations and change checks, structured-output turns, forks, compaction and provider probes isolate both integrations.

The host reads Claude Code user and local MCP entries from the selected account’s `.claude.json`. It reads repository `.mcp.json` and project and local hooks under `.claude/` from the checkout root through the session folder. It selects only the user settings source, uses strict MCP configuration with an explicit server snapshot, and supplies only reviewed project hooks as process settings. The host writes the server snapshot and settings to a private, randomly named run directory under its data directory and passes only file paths to the provider. POSIX directory and file permissions are owner-only; Windows uses the enclosing user data ACL. The host removes the directory when the process ends, including on Stop and provider failure. Startup sweeps leftovers after claiming ownership of the data directory. Plan sets an MCP ask rule and uses the private stdio approval channel. If the CLI lacks this channel, Plan isolates MCP and the composer explains why.

Codex disables native project layers for the process and checks the reported layer stack before creating or resuming a thread. It reads repository `.codex/config.toml` and `.codex/hooks.json` along the checkout path and passes reviewed integrations as thread configuration over the private app-server stdio connection. This preserves the provider home, account and thread state and keeps credentials out of process arguments. The host verifies the inherited layer before creating or resuming a thread and rechecks the reviewed snapshot before the turn. Workspace edits retains the workspace-write sandbox and user approval reviewer. Read-only retains the read-only sandbox. If the app-server advertises the native MCP tool elicitation feature, the host applies and verifies a granular approval policy with MCP as its only approval category, requires prompts for every enabled MCP tool and forwards supported requests to the existing approval flow. Other Read-only versions isolate MCP and show the reason in the composer. Unsupported requests are declined visibly. Hook trust where available uses provider-reported hashes as process-local overrides and respects disabled hooks.

The repository notice shows definitions before Trust and marks added, changed and removed entries after drift. Not now dismisses the notice for the current definition set, and the MCP chip can reopen it. An interactive turn can proceed with the user integrations available in its mode while review is pending. The host stores trust by provider and canonical checkout root in SQLite (the mcp_repository_trust table, added in schema version 20). The host-keyed fingerprint covers full definitions, including commands, arguments, URLs, headers, environment values and hook settings. The host verifies it on Trust and checks definitions again before launch. Changed or unreadable definitions invalidate the grant.

The notice preserves shell expansion and control syntax and labels affected entries **Contains shell expansion**. It escapes control and bidirectional formatting characters. The host masks plain literal credential values only in recognized flags, assignments, environment variables, headers and URL credential positions. Ordinary shell assignments and opaque arguments remain visible. Commands outside the review parser's supported syntax or nesting limit appear in full with **Review the raw definition**.

**View raw definitions** displays the relevant JSON or TOML sections from each source file read by the host for that fingerprint. The view includes file paths and uses normalized formatting, the same credential rules and escaped control characters. Account configuration contributes only repository-scoped entries. The response is read-only and bounded. When a definition requires raw review, the desktop enables Trust after the source view loads and the host requires a review token bound to that session and fingerprint. Definitions that exceed the review limit stay paused. The grant covers configuration values. Referenced scripts can change independently.

Legacy selections remain readable in history. The legacy session MCP mutation returns an explicit error and session creation ignores its selection.

## Plan-first workers

D67 lets a parent propose a worker with `planFirst`. The operator still approves the worker; its first turn then runs with a read-only turn sandbox and must return a plan, and the proposal moves from `planning` to `plan-ready` with the bounded plan text and a `planRound` counter. The plan appears in the parent conversation with three decisions sent through `decide-worker-plan`: `accept` resumes the worker thread in the proposal's mode with the approved plan in its prompt, `correct` runs another read-only plan turn with the operator's correction, and `decline` marks the proposal declined, leaves the worker session idle and returns the declined result to the parent's tool call. A worker can revise its plan at most five times; a further correction is refused. The parent's delegation tool call keeps waiting until the worker finishes for real, so a plan never counts as a worker result, and plan turns save no review. The proposal mode was already checked against the parent's access when it was proposed, so the post-plan turn can never be broader than the parent allows. Parent Stop or host shutdown stops or interrupts a planning or plan-ready worker like a running one, and a host restart marks both states interrupted without continuing the worker. The action inbox does not list plan decisions yet; they are made on the worker card in the parent conversation.

## Claude adapter and P2 limits

## Codex adapter and approval boundaries

Codex uses its installed app-server over a private stdio connection, with existing CLI authentication. Model choices come from its model catalog rather than a hard-coded list. Each turn owns a process and resumes the persisted provider thread ID when continuing a conversation. The application never attaches to another running Codex process.
The native local tool executor remains enabled. The adapter disables unrelated plugin and delegation features in its own process and verifies the effective configuration. Read-only isolates hooks and requires an available tool approval channel for MCP. Internal operations isolate both. The adapter rejects ambiguous server names when it needs to construct an isolation override.

Read-only mode uses the provider's read-only sandbox and never grants elevated operations. It can run commands that read data; it is not the same tool allowlist as Claude. Supervised mode uses workspace-write with the provider's untrusted approval policy and user reviewer. Workspace edits may proceed without a prompt. Commands and file changes that the provider asks to approve become visible requests, with one-time accept or decline actions. This mode does not promise a prompt for every edit.

Decisions carry the Nesvo session ID, current run ID and provider request ID. The host accepts them only while that exact request is pending on the active run. Stop, completion and recovery invalidate requests. Persistence precedes forwarding an approval, and unsupported provider requests fail closed. Provider approval is separate from the later review inbox and does not accept a completed task.

## Turn inactivity watchdog

A Claude Code or Codex turn has no fixed duration. The adapter (`apps/host/src/providers/inactivity.ts`) fails a turn only after 15 minutes without any provider activity, with the message "<provider> turn stopped after 15 minutes without any activity from the provider." Activity is any output on the Claude Code stdout stream, including subagent messages, permission requests and partial text, or any notification and server request on the Codex app-server connection. A pending operator approval keeps the turn active, and so does a Codex parent waiting for worker decisions and results; the silence count starts again when the wait ends. A provider tool that runs without printing counts as silence, so a single quiet command longer than the limit fails the turn; 15 minutes stays above the default ten-minute maximum of a single Claude Code shell call. Stop, restart recovery and cleanup are unchanged. The only absolute bound is the 512 MiB ceiling on the total streamed output of one turn; individual lines and the assembled reply keep their existing limits. With `NESVO_TEST_MODE=1`, `NESVO_TEST_PROVIDER_INACTIVITY_MS` shortens the limit for host tests.

```text
                                    |
React decisions -> typed preload -> host decide-delegation
                                    |
                             persist parent + child
                                    |
                             launch owned worker
                                    |
                         child status/text/error -> parent tool result
```

The adapter validates the tool, namespace, call ID, thread and turn. The service limits all calls within one parent run to two proposals. Each proposal shows task, scope, relative directory, provider, model and mode. Only a matching session/run/proposal decision can accept or decline it. Acceptance creates and launches the visible child; stale decisions fail. Child results remain associated with their proposal and session IDs, including declined, stopped and failed outcomes.

Delegation never changes the parent's selected permissions. Workers use the existing Codex modes or Claude's read-only capabilities and cannot create children. Directories are canonicalized, checked inside the parent's root and revalidated at acceptance. If either worker can write, its directory must not overlap another worker's directory. A supervised parent can delegate read-only workers only; proposed writable children are rejected before publication and rechecked at acceptance. This avoids mixing parent and child edits in the parent's review snapshot before workspace isolation exists. Assignment text is not a security boundary; provider sandboxes still define actual permissions. Read-only workers can share a directory.

Stopping a child leaves its sibling and parent active. Stopping the parent cancels pending proposals and active children. Parent termination waits for child cleanup; shutdown cancels the whole group. Restart retains relationships and marks unfinished work interrupted without launching it. Several groups may be active when their folders do not conflict. A ten-minute native parent deadline includes operator waiting and child work; each conversation retains at most 100 proposals. Worker summaries passed back to the parent are capped at 12,000 characters with explicit truncation, while complete conversations stay available in the UI.

The workspace page composes conversation and delegation widgets through a React slot. Sidebar rows expose the parent/child tree, child views link back to their parent, and session details explain the actual delegation capability. No Effect or process API enters the renderer.

## Result review

Schema v5 adds a separate reviews table; full historical diffs are not copied with every session streaming update. A result records its session, run, independent content version, task, answer, captured diff and optional human decision. Review.revision orders status events; Review.version identifies the immutable content. Session.revision is never an acceptance token. The terminal session and result are committed in one SQLite transaction before either event is published. Recovery does not synthesize missing results from unfinished runs.

The narrow list-reviews and decide-review commands are available to the operator through validated IPC. Provider tools cannot call them. Decisions carry result ID, content version and an idempotent decision ID. A correction commits the decision, prepared session run and invalidation of older results together, then starts the same provider thread. Repeating its ID cannot spawn a second correction. A new result version starts pending; earlier decisions remain in history. The host rejects decisions on replaced versions or while a group is active.

Writable runs reserve their active slot before asynchronously capturing a baseline. Stop cancels this phase and cannot be followed by a late provider launch. After provider termination, the service captures the result state and saves a bounded unified diff. Filesystem reads never modify project files, Git objects or the index, and work without Git. Limits and excluded generated directories are explicit. Exact-byte hashes include paths, types and file modes; capture rejects symlinks, special files, concurrent mutations and incomplete reads. Binary changes and truncated patches remain unavailable rather than appearing clean. Accepting a writable result recaptures its directory and compares the recorded fingerprint. This checks the eligible files at decision time; it does not lock files against later outside edits.

Each version's diff describes its own turn, including a correction's incremental changes. Older diffs remain accessible. Read-only parent results link to the specific child results used for the summary instead of attributing child writes to the parent. Parent acceptance also checks writable dependency fingerprints. Accepting a parent does not accept its children. A child continuation supersedes dependent parent results; continuing a parent without new delegation supplies current child summaries and carries those references forward. A fresh delegation group establishes its own child references.

All successful new turns enter the prototype inbox. This stage does not add per-project review policy switches, automatic result submission tools, merge, background resumption or provider-specific skills. The optional policy/module settings remain a later product decision.

The action inbox is a projection of authoritative sessions and reviews. It lists pending operation approvals, current-run worker proposals and saved results with distinct action types. Every row links to the requesting session and exposes its decisions inline. Operation callbacks carry the row's session, run and request IDs; the page validates those IDs against current state independently of the selected conversation. Full versions and diffs are disclosures in the conversation, composed through a widget slot. A session link opens and scrolls to the exact request or result. The shared review decision feature preserves feedback drafts and the existing idempotent decision handling. No new host command or stored action record is introduced. History shows saved review decisions; transient operation approvals are not fabricated as historical records.

## Session history search

Each host indexes the title and the first 8,192 characters of every stored operator and agent message. SQLite triggers update the projection in the session transaction and cascade removals. Archived sessions remain searchable while they remain in stored history. The host probes FTS5 at runtime. With FTS5, results use BM25 relevance followed by creation time and a stable row ID tie-break. Without FTS5, search uses case-folded LIKE over the 4,000 most recent entries and scores contiguous matches first. Schema version 12 backfills existing documents in small batches between event-loop turns and resumes from a durable checkpoint.

`search-history` accepts up to 200 characters, treats punctuation as separators and searches for all resulting words. It sends a page of up to 100 snippets with UTF-16 match offsets and an optional next cursor within the first 10,000 matches. `truncated` covers further matches, incomplete backfill and fallback scan limits. Cursors page the current index and can shift when the history changes.

Desktop sends debounced, read-only queries to each connected computer with `history-search` and discards superseded responses. The palette groups the first page per computer and session, lists computers it could not search, and opens the matching session and message anchor.

## Session changes and code comments

On the pull request Code tab it offers **Send to agent** and **Add to review**; Send to agent is the default when the pull request is linked to a session, and Add to review is the existing GitHub line comment action, which runs only when the operator chooses it. ### Tracked repositories

A host that advertises `tracked-repositories` keeps a per-computer list of GitHub repositories. ## Workflows

The operator guide to the files, the graph editor, the assistant dock and the command line is [workflows.md](workflows.md); this section describes how the host and the desktop implement them.

Workflows run a task through ordered steps whose definitions live in files on the computer that runs the task; the host database will hold only run state, results and metrics. `packages/contracts/src/workflows/` owns the shared shapes: step definitions (`command`, `agent`, `human`, `action`; phases `plan`, `pre-done`, `pre-push`; timeouts from 1 s to 4 h; at most five retries; `needs` limited to `browser` and `env:NAME`), workflow definitions with 1–32 unique step names, task specs, definition sources with content hashes, catalog issues, step results and evidence, the structured agent verdict, run and step records, run pages and metrics. Human steps never retry and only agent steps name a skill; an agent step may omit instructions only when it names one. Gate results report `pass`, `fail` or `blocked`; actions report `done`, `error` or `blocked`. The agent verdict needs at least one evidence reference and converts to a JSON Schema without references for provider structured output.

Sixteen host commands cover definitions (list, validate, save, delete), task start and manual step runs, run history and detail, gate decisions (`accept`, `reject`, `fix`), recorded skips, the resolution of an `uncertain` step (`mark-done`, `run-again`), resume, Stop, worktree removal, bounded evidence reads and metrics. `workflow-run-changed` and `workflow-step-changed` carry revisioned records; main drops a record whose revision is not newer than the last one seen and resets that memory on every synchronization. Renderer access goes through `window.nesvo.workflows`, each method taking the desktop host ID first; preload and main validate with the shared schemas and main adds the host ID. `start-workflow-task` waits up to 60 seconds, the other commands 15 seconds.

Sessions gain nullable `workflowRunId` and `workflowStepId`, messages a nullable `origin`, and reviews a `reject` decision with a `rejected` status. The defaults keep stored sessions and the offline computer cache readable, but a newer host sends the new fields, so an SSH host, the desktop and the mobile client must be updated together. `create-session` accepts an optional worktree isolation request.

Schema version 8 adds the run and step tables (created under their pipeline names at the time and renamed to `workflow_runs` and `workflow_steps` by version 10) in the same bootstrap transaction as earlier migrations; a failed migration rolls back completely and keeps version 7. Each row keeps the validated JSON record in `document` next to the columns used for lookup, and both tables use a revision compare-and-swap, so a stale writer changes nothing. A run records its working directory and, separately, the source project root of the operator, which differs when the run is isolated in a worktree. Step rows are unique per run, step index and attempt, and deleting a run removes its steps. Sessions gain nullable `workflow_run_id` and `workflow_step_id` columns that become null when the run or step disappears; the session store writes them from the session document and drops a link whose target no longer exists. Runs page by update time, a project keeps its latest 100 finished runs, and interrupted or `needs-attention` runs are never pruned.

A pending step moves to `running` through a store helper that commits the state and its start time in its own transaction, and refuses to run inside another transaction or for a finished run, before the runner starts the process, so a crash leaves a record of the intent. A retry is a new attempt row, never a rewrite of an earlier attempt. At startup, inside the session recovery transaction and with plain SQL updates that do not parse stored documents, every `running` step is closed and runs in `planning`, `implementing`, `checking` or `fixing` become `interrupted`. A `running` action step becomes `uncertain` instead of `interrupted`, because its external effect may have happened, and its run becomes `needs-attention` with the reason "External action may have run." Runs waiting for a human keep their state. Nothing is replayed.

The host advertises the `workflows` capability. Until the engine is complete, it answers every workflow command it does not serve yet (worktree removal and metrics), and any isolated `create-session`, with `unavailable`. Main refuses workflow calls locally for computers whose host does not advertise the capability, except the two definition reads, which every host with the definition loader answers. The mobile gateway ignores workflow events.

### Workflow runner

`apps/host/src/workflows/runner.ts` is a host service with ports for the run store, the definition reader, a clock, event emission, the evidence store, a step executor per step type and an optional author port that a later stage implements for session-bound runs. `advanceRun(runId)` is the only operation that moves a run. Every caller first writes its intent to the store (a manual start inserts a `pending` run, Stop records the run as `stopped`, a finished step records its result, startup records a `pending` manual run that never began as `interrupted`) and then calls `advanceRun`. A pass reads the run and its steps from the database, decides one move, performs it and repeats until the move is to wait; nothing about the progress of a run is kept in memory between passes. Passes for one run are serialized: a call that arrives while a pass is scheduled or running only marks the run for one more pass, so any number of calls collapses into at most one extra pass, while different runs never wait for each other. The decision is a pure function of the run and step records.

The moves follow the run status. A `pending` manual run enters `checking` for its requested phase, and one `pending` step row per step of that phase is written in the same transaction. In `checking`, the pass evaluates the graph of the phase (`nextMove`, exported and pure). The outcome of a step comes from its latest attempt: `passed`, `done` and `skipped` are success, so a `human` or `agent` step skipped in a manual run routes as passed; `failed` and `error` are failure; `unreached` means the step will not run; any other state is no outcome yet. An edge has fired when its source has an outcome that matches its condition (`on any` matches both), is dead when the source has the other outcome or is `unreached`, and is open otherwise. A `pending` step is ready when every incoming edge has fired and every step that precedes it through any chain of edges has an outcome, so a step with several incoming edges waits for all of them, a step after an operator-skipped step still waits for the steps before that one, and a step without incoming edges is ready as soon as its phase begins. The moves are, in this order: a `blocked` step needs attention with its reason at once, while running steps finish and record their results; the first ready step in workflow order that the concurrency rule allows starts, and the pass repeats, so several steps can start in one pass; in an explicit graph a `pending` step with a dead incoming edge becomes `unreached` with a reason taken from the first dead edge in the workflow order of its source, `Not reached: "<step>" failed`, `Not reached: "<step>" passed` (an `on failure` edge from a step that succeeded) or `Not reached: "<step>" was not reached`, and its own outgoing edges die in turn; an `unreached` step none of whose incoming edges is dead any more, because resume retries its failed source or the operator skipped that source, gets a new `pending` attempt; a step that is `running`, `awaiting-human` or `uncertain`, or a ready step held back, means wait; an `interrupted` step needs attention so that resume can run it again, which only a restart during parallel steps can leave behind while the run is `checking`. When nothing is left to do the phase has settled: if any step is `failed` or `error`, the first one in workflow order applies its failure (`on_fail: stop` fails the run, `fix` needs attention with the failure), otherwise the phase passed and a manual run is `passed`. An `on failure` branch therefore runs before the failure takes effect and never turns it into a pass. The concurrency rule lets at most four `command` and `action` steps of a run run at once and starts an `agent` or `human` step only while no other `agent` or `human` step of the run is `running` or `awaiting-human`, because a run drives one author session and a gate binds to one result version. A `human` step and an `action` step never run at the same time either: a restart leaves a running action `uncertain` and keeps a run that waits for a human as it is, so an action in flight beside a gate could neither be resolved nor safely run again. While the run waits for a human decision, running steps finish but no new step starts. A workflow without `edges` is the implicit chain and behaves as before graphs: any active step means wait, one step runs at a time in workflow order, and the first failure ends the phase without starting later steps and without `unreached` rows. A phase is never begun and an author turn is never sent while a step of the run is still `running`, so a gate sent back to fix while a parallel command still runs sends its correction and re-runs the phase only after that command ended, and when a run reaches a terminal status, including `rejected`, the runner aborts its steps that are still running. `currentStepIndex` is set when a step starts, to the lowest index among the steps then running or waiting for a human. A session-bound run in `pending`, `planning`, `implementing` or `fixing` moves through the author port described under Workflow tasks and needs attention with "No author session on this host" while none is registered. `awaiting-human`, `needs-attention` and terminal runs wait. A pass never starts an `uncertain`, `interrupted`, `blocked`, `failed` or `error` step.

Before a step starts, its `needs` are checked: a missing `env:NAME` variable or a `browser` need makes the step `blocked` with a readable reason and no process. Otherwise the store commits the step as `running` with its start time in its own transaction, and only then does the executor start, so a crash always leaves the intent recorded. The executor's result is written to the step record in one transaction as soon as it ends, with the step state mirroring the verdict, and every write emits `workflow-run-changed` or `workflow-step-changed` with the incremented revision. Executors are registered per step type when the host composes the runner; `agent` steps follow Agent steps and `human` steps Human gates below. Only one manual run per project root is active at a time; a second start answers `busy`. Each running step has its own abort signal. Stop records the run as `stopped`, aborts every running process and records those steps as `interrupted`; shutdown waits for all of them. Host shutdown aborts running processes without writing a result, so the next startup closes those steps through the same store recovery as a crash: a command step becomes `interrupted` and an action step `uncertain`. Each running step process records its process ID, its spawn time and, on Linux, its kernel start time in its evidence folder until it ends; after a crash the next startup stops the process group of every record whose identity still matches, so a step that outlived its host cannot keep editing the project. Linux compares the exact start time; macOS and other POSIX systems compare the creation time reported by `ps` with the recorded spawn time within 3 seconds, so a reused process ID is skipped; `ps` reports local time, so a process started during the repeated hour of a daylight-saving change can be missed and is then left alone. On Windows the host's process job ends the step shell together with a crashed host, but processes the shell started leave that job and no record reaches them; containing them needs a native job object, so startup leaves them alone. After that recovery the host calls `advanceRun` for every unfinished run; the pass reconciles and starts nothing.

`command` and `action` steps run their body in the run directory through `sh -c` on POSIX and, on Windows, as a temporary batch script started with `cmd.exe /d /s /c` that begins with `@echo off` and `chcp 65001`, so every line of a multi-line body runs and the shell's own output is UTF-8 (other programs keep their own encoding); bodies follow batch-file rules, so `%%` is a literal `%`, an undefined `%NAME%` expands to nothing and loop variables are written `%%i`; the script folder is removed when the process ends and a crash can leave it in the temporary directory. They run in their own process group with the step timeout, descendant tracking on Linux and a bounded tail of 4 MiB for the combined output. The process uses the host environment without any variable whose name ends in `KEY`, `TOKEN`, `SECRET` or `PASSWORD` (alone or after `_`) and without inherited `NESVO_` variables, except variables the step names in `needs: [env:NAME]`. The runner adds `NESVO_RUN_ID`, `NESVO_STEP_NAME`, `NESVO_PHASE`, `NESVO_SPEC_PATH`, `NESVO_PROJECT_ROOT` (the operator's project, which differs from the working directory when the run is isolated), `CI=1`, `GIT_TERMINAL_PROMPT=0` and `NESVO_OUTPUT_<STEP>_<KEY>` in upper snake case for every output of a step that precedes it in the phase graph through any chain of edges, and of every step of an earlier phase, using their latest attempts; a step running in parallel never contributes, so the variables do not depend on timing. On the implicit chain of a workflow that lists its steps in phase order this is every earlier step as before; earlier phases now count by phase rather than by list position. When two outputs map to the same name, the step listed first wins. A command passes with exit code 0 and otherwise fails with the exit code, signal or timeout and the last part of its output in the summary. An action reports `done` or `error` the same way, and the last stdout line that is a JSON object becomes its outputs when it has at most 16 keys with valid names that the secret filter leaves unchanged and text values of at most 4000 characters; otherwise the outputs stay empty and the summary says why. The step executors still use their own process helper with the same rules (`apps/host/src/workflows/steps/process.ts`, which also reports the process ID for crash cleanup); moving them onto the shared owned-process helper is a separate change.

`apps/host/src/workflows/evidence.ts` keeps evidence in `<dataDir>/workflow-evidence/<runId>/<stepIndex>-<name>/` with folders created as 0700 and files as 0600, at most 4 MiB per step attempt, keeping the tail when a log is longer. File names are fixed by the executor (`attempt-<n>.log`). Before any write, the summary, evidence labels and text and output values pass through one filter, once in the executor with the step's secret values and again in the runner for every executor result, that removes terminal control sequences, redacts `sk-`, `sk-ant-`, `ghp_`, `github_pat_` and `xox*` tokens that do not continue a word, Bearer values and `key|token|password|secret` assignments, and, in the executor, replaces the value of every secret-named variable passed through `needs` when it has at least eight characters. `read-workflow-evidence` accepts only a recorded file name inside the step folder, refuses links and special files, answers `missing` for an absent file and returns a text preview of at most 256 KiB, the tail of a longer file marked `too-large`, or `binary`, with at most eight reads in flight. `run-workflow-steps` validates the directory, reads the task spec (relative paths resolve against the directory) and its workflow, refuses invalid definitions with their issues and a phase without steps, records the directory as the project root and answers with the `pending` run while the first pass runs in the background. `get-workflow-run`, `list-workflow-runs` and `stop-workflow-run` answer from the store. Evidence folders of pruned runs remain until a later cleanup removes them.

### Workflow definitions

`apps/host/src/workflows/definitions.ts` reads definitions from the filesystem of the host that serves the request, so a remote computer reads its own files. The global root is `~/.agents/workflows` of the host user; the project root is `<project>/.agents/workflows`, where the project is the nearest ancestor of the request directory that contains `.git`, or the directory itself when none does. Definitions above a directory without `.git` are never read. Each root holds `steps/*.md` and `workflows/*.md`; task specs are any Markdown file inside the project, and the catalog also lists `<project>/.agents/tasks/*.md`. When the project root resolves to the global folder it is read once. `NESVO_WORKFLOWS_HOME` replaces the global root only when `NESVO_TEST_MODE=1` is also set.

Names resolve project over global: a project step or workflow with a global name replaces it and carries a note naming the overridden file, which is not an issue. A workflow step name always resolves through the same merged step set. An invalid project file still shadows the global definition, so a workflow using that name reports the step as invalid instead of silently falling back. Two files with one name inside a root keep the first file by name and report the second.

Files are read only when they are regular files: the folder is canonicalized, the file itself must not be a symbolic link, it is opened without following links, and its identity is compared before and after the read. A file is at most 64 KiB of UTF-8 and its frontmatter at most 32 KiB through the same bounded YAML parser as the skill library (no anchors, aliases or tags, depth 12, 512 nodes). The anchor check is textual, so a frontmatter value containing `&`, `*` or `!` after a space must be quoted. A root reads at most 200 step and 100 workflow files, the project at most 100 task specs, with eight concurrent reads and one 3 s deadline for the whole inventory; reaching the deadline or Stop fails the request instead of returning a partial catalog. Every file problem becomes an issue with the canonical path, the frontmatter line when it is known and a plain message, for example an unknown field with a suggested name, an enum value outside its options or a missing referenced step; issues beyond 200 collapse into one summary issue.

Each definition source carries `contentHash`, the SHA-256 of the raw file bytes. It is stable while the bytes are unchanged and is what later stages pin into runs and compare before writing a file. Validation adds warnings for a workflow without a gate, for a `fix` step with no retries, for a `command` or `action` step that declares `effect: external` (an optional field, default `local`, valid only on those two types) and, whatever a step declares, one whose body mentions `git push`, `gh pr`, `curl` or `wget` with no `human` step before it in phase order. `list-workflow-definitions` and `validate-workflow-definitions` return the same catalog, run beside the other inspections with at most two in flight and are cancelled by host shutdown. `loadSpec` reads one task spec that must lie inside the project, and `resolveWorkflow` picks a workflow from a catalog for a later run.

A workflow file may also carry two optional fields. `edges` is a list of at most 64 strings of 3 to 160 characters, each `<from> -> <to>` with an optional `on success`, `on failure` or `on any`; `on success` is the default and whitespace around the arrow is free. One string per edge keeps a full graph far below the YAML node limit. `layout` maps a step name to `[x, y]` integers between -100000 and 100000, at most 32 entries; it is presentation for the editor and nothing that runs steps reads it, and `layout: {}` is valid. Without `edges` the workflow is the implicit chain: inside each phase, consecutive steps in `steps` order are joined by `on success` edges, so every workflow written before graphs keeps its meaning without an edit. With `edges`, even `[]`, the graph is explicit and a step without an incoming edge starts when its phase begins. Edges stay inside one phase; phases keep their order and a step with several incoming edges waits for all of them. Every resolved workflow carries `graph: { explicit, edges: [{ from, to, when }] }` next to the original `edges` and `layout`. A stored run whose pinned workflow predates graphs has no `graph`; parsing it fills in the implicit chain of its pinned steps rather than an empty edge list, so an older unfinished run keeps its step order. The runner records a step that a dead path skips as `unreached`, with its reason in `skip`, as described under Workflow runner.

`packages/contracts/src/workflows/graph.ts` holds the graph rules once for the host loader and writer, the definition commands and the desktop editor. It performs no I/O and imports nothing from the host. `resolveGraph` takes the workflow name, `steps`, `edges` and `layout` with the step definitions by name and returns the resolved graph and issues that carry a rule ID, severity, field, message, the steps involved and the edge position; the caller adds the file path and the line of `edges:` or `layout:`. The module also exports `parseEdge`, `formatEdge`, `implicitEdges`, `incoming`, `outgoing`, `ancestors`, `topologicalOrder` and `phaseSources` for the engine and the editor, and `checkGraphList` for the checks that need no step definitions. The gate script that runs the same files outside Nesvo mirrors the error rules E1 to E9 and the layout warning W1 with the same messages; the other warnings exist only in Nesvo.

Graph errors exclude the workflow from the catalog like a missing step and refuse a save: an entry outside the grammar (E1), an edge naming a step that is not in `steps` (E2), a step connected to itself (E3), an edge listed twice, where `on success` written or omitted is the same edge (E4), an edge between phases (E5), a cycle, reported with its steps in `steps` order (E6), an `on failure` edge leaving a `human` step, whose decisions are not routed (E7; `on any` from a `human` step is allowed), a step whose incoming paths require both outcomes of one step and can therefore never start, reported at the first such step and not again for the steps after it (E8), and more than 64 edges (E9). The checks run in stages: more than 64 edges is the only issue reported; otherwise the grammar, names, self edges and duplicates come first and, with the layout warning, are reported for the file itself, even when a listed step is missing; only a clean list of a workflow whose steps all resolve is checked for phases, routing from `human` steps, cycles and impossible joins, the last only when there is no cycle. A malformed field reads `Field "edges" must be a list of text entries` or `Field "layout" must be a mapping of step name to [x, y]`.

Graph warnings are saved and listed: a `layout` key that is not a step, which the editor drops on save (W1); an external step that a path reaches without a `human` step (W2); the workflow without a gate (W3, unchanged); and, once per workflow, two `agent` steps of one phase that could start together because neither precedes the other and their edge conditions do not exclude each other, while a run drives one author session at a time (W4). The external check is path based: a step is guarded when every path to it inside its phase passes a `human` step through an `on success` edge, or when an earlier phase holds a `human` step that runs whenever that phase passes, that is one reached from the phase start through `on success` and `on any` edges only. The `git push`, `gh pr`, `curl` and `wget` heuristic uses the same check. On an implicit chain this is the earlier walk in phase order and keeps its messages; on an explicit graph the warning reads `Step "<name>" has an external effect and a path reaches it without a human step`, or `looks like an external action (git push, gh pr, curl or wget) and a path reaches it without a human step` for the heuristic. The warning for a `fix` step with no retries stays a step warning.

### Definition writes

`apps/host/src/workflows/writer.ts` saves and deletes `steps/<name>.md` and `workflows/<name>.md` in the global or project root of the host that serves the request. The client sends the whole file text; the host never composes frontmatter. The document goes through the loader's strict parser, must carry the same `name` as the file, may not exceed the read limit and must be valid text. Errors return `workflow-definition-refused` with the issues, capped like the catalog, and write nothing and create no folder; warnings, such as an external step with no earlier `human` step, ride along in the catalog returned after the write. A workflow may only list steps that exist in the catalog merged for the request directory, so a global workflow is checked against the requesting project's view, and a step used by a workflow is not deleted. A `human` step with retries and an `effect: external` on an `agent` or `human` step are errors.

Every write names the `contentHash` the writer read: `expectedHash` is `null` when the file must not exist yet. Inside one critical section per root the host reads the file, compares hashes and writes. A mismatch returns `workflow-definition-conflict` with the current path, hash and text and changes nothing; the host never merges, the client reads the current version and decides. The write goes to a unique temporary file with mode 0600 in the target folder, then either a hard link (no file expected, so an outside creator cannot be overwritten) or a rename after a second hash check. The temporary file is removed on every failure path. The global root and its folders are created on first save with mode 0700; symbolic-link folders, a project root outside the project and a project root equal to the global one are refused. A workflow with a run in progress is `busy` for save and delete, and the message names the run; the run itself keeps the snapshot it pinned. Edits made outside the host between the check and the rename are not locked out, so the hash check is a safeguard against lost updates rather than a file lock.

A workflow save also resolves the document's graph against the steps of the catalog merged for the request directory. A graph error, such as an edge between phases, refuses the save with the errors and the line of `edges:`; graph warnings ride along in the catalog returned after the write.

### Definition commands

`node dist/main.js workflows <command>` (`apps/host/src/workflows/cli.ts`) applies the same loader and writer as the editor from a terminal, so an agent session and the editor produce the same files. It works on files only: it opens no database, needs no running host and ships in the same bundle as the host. `--directory` selects the project (default: the current directory) and `--scope project|global` selects the root of a write. `validate` prints the catalog issues as `severity path:line: message` and exits 1 when any is an error; `list` prints each step and workflow with its scope and `contentHash`. `--json` prints the catalog, the issues, the refusal or the conflict as JSON.

`add-step --file <step.md>` reads the file text, takes its `name` and saves it with `expectedHash` `null`, or with `--expected-hash` to replace an existing step. `add-to-workflow --workflow <name> --step <name> [--after <name>]` and `remove-from-workflow` read the workflow file, edit only its `steps` list as text (a one-line `[a, b]` list or a block list; the rest of the file, including line endings, stays byte for byte) and save with the hash they read, so every rule of the writer applies, including the check that each listed step exists. A list layout the command cannot edit is refused with a pointer to edit the file directly and run `validate`. A conflict prints the current path and hash and "The file changed since it was read. Read it again." and exits 2; the command never retries or merges. Exit codes: 0 success, 1 validation errors or refusals, 2 conflict, 3 run session, 64 usage.

When `NESVO_RUN_ID` is set, which the runner sets for every `command` and `action` step and an author session will carry once it exists, `add-step`, `add-to-workflow` and `remove-from-workflow` exit 3 before reading any file: "Workflow definitions cannot be changed from inside workflow run <id>. Ask the operator." `validate` and `list` stay available. This is a cooperative guard against a session steered by outside content, not a security boundary: the definitions a run uses are protected by its pinned snapshot, while a session that writes the files directly is not stopped by the command. The command has no database, so it cannot see active runs the way the host's save does; a workflow with a run in progress is still protected by that run's snapshot. `--expected-hash` on `add-to-workflow` and `remove-from-workflow` is compared with the file as it is on disk, so a hash older than the file is a conflict.

When a workflow file has an `edges` list in one of the two layouts the commands edit, a one-line `[a -> b, c -> d]` list or a block list, `remove-from-workflow` also removes every entry that names the step and prints, for example, `Removed 2 edges that named "lint"`; removing the last entries of a block list writes `edges: []`. `add-to-workflow --after <name>` on such a file keeps the chain meaning of `--after`: it adds `<after> -> <step>` and moves each `on success` edge that leaves `<after>` to start at the new step, printing each rewired and added edge, while `on failure` and `on any` edges stay on `<after>`. When the new step belongs to another phase than `<after>`, or without `--after`, no edge is added and the command says that the step starts when its phase begins. A removal that leaves a step without incoming edges names that step too. With `--json` these notes go to stderr and stdout stays the catalog. An `edges` list in any other layout is refused with "The edges list uses a layout this command cannot edit. Edit the file directly, then run validate." and nothing is written. A workflow without `edges` is edited as before. `validate` prints graph issues like any other issue, and `list --json` includes each workflow's `graph`.

### Workspace isolation

`apps/host/src/workspace/isolation.ts` gives a task its own Git worktree and branch so that a writable author session never edits the operator's checkout and a later push action can only push the task branch. `createTaskWorktree` requires an absolute, existing project directory that is the top level of a Git work tree; a subdirectory is refused rather than silently widened to the whole repository. It refuses a project inside `<dataDir>/worktrees/` (`nested-worktree`), a data directory inside the project (`data-inside-project`), a folder outside Git (`not-a-repository`), a repository without a commit, and an existing branch or path. The worktree is `<dataDir>/worktrees/<runId8>-<slug>` on branch `nesvo/<slug>-<runId8>`, where `runId8` is the first eight characters of the run ID and the slug is lowercase letters, digits and inner hyphens, at most 40 characters. The base is the project's `HEAD` commit hash, read first and then passed to `git worktree add`, so the branch starts at the recorded commit even if `HEAD` moves meanwhile.

The module stores nothing. The caller records the operator's project as the run's `projectRoot` and the returned path as the run's `directory`; the run record, not the worktree, says where a worktree came from. A session started for the run uses the worktree as its stored directory through the internal `isolatedDirectory` option of session creation. `listTaskWorktrees` reads `git worktree list --porcelain` and keeps entries under `<dataDir>/worktrees/`. `removeTaskWorktree` removes only such an entry and never deletes the branch. It runs `git worktree remove` from the project directory and lets Git refuse a worktree with uncommitted or untracked changes unless forced; no Git process starts inside the worktree, because a writable session controls its `.git` pointer and could otherwise redirect Git to a repository whose configuration runs commands as the host user. A worktree whose pointer no longer leads back to the project is refused. If `git worktree add` times out or is stopped, the error names the path and branch that may be partly created; they too are removed only on request. Nothing is removed automatically. The module never pushes, fetches, merges, commits or deletes a branch.

Git runs from an absolute path found on `PATH` (`git.exe` on Windows), never from the project directory, with `shell: false` and an environment limited to `PATH`, `HOME`, `USERPROFILE`, `SystemRoot`, the temporary directory and locale variables plus `GIT_TERMINAL_PROMPT=0`, so an inherited `GIT_DIR` or `GIT_WORK_TREE` cannot redirect it. Queries are bounded to 10 s and worktree changes and status to 60 s, with output capped at 64 KiB. A missing Git is `git-unavailable`. Repository hooks that Git itself runs, such as `post-checkout`, run inside the same bound. `NESVO_GIT_EXECUTABLE` replaces Git with an absolute path for tests.

Every Git call goes through `apps/host/src/process/owned-process.ts`. `runOwnedProcess` starts the command in its own process group (Windows: a tree ended with `taskkill /T /F`), tracks descendants on Linux, caps stdout and stderr separately, reports `timedOut` and `outputTruncated`, and on deadline or Stop sends `SIGTERM`, then `SIGKILL` to the group and recorded descendants. It resolves only after the process has closed; a start failure, a cancellation and an unconfirmed close reject with `OwnedProcessError` (`spawn-failed`, `cancelled`, `unconfirmed-close`). The helper is shared so that workflow command steps run under the same rules; the provider adapters keep their own copy of the pattern for now.

### Workflow tasks

`start-workflow-task` (`apps/host/src/workflows/tasks.ts`) creates one ordinary session bound to a new run. The host validates the directory, resolves the project root the same way the definition reader does, reads the task spec (relative paths resolve against the directory) and the requested workflow, and refuses invalid definitions with their issues. It answers `busy` while a run is active for that project root or while another task is starting, and confirms a Codex reasoning effort before anything is written. With `isolation: 'worktree'` it creates the task worktree and branch first and uses the worktree as the run directory and session directory, recording `worktree`, `branch` and `base` on the run; otherwise the run directory is the project root. The spec body is saved as a private snapshot in `<dataDir>/workflow-specs/<runId>.md`, so later turns use the text the task started with; snapshots of runs that no longer exist are removed when a later task starts. The host then inserts the `pending` run, creates the session with the internal workflow origin (provider, model, effort and mode from the request; Claude Code only read-only; delegation off), links the run and the session in both records and calls `advanceRun`. The public `create-session` request stays strict and cannot carry an origin.

The runner owns every move; the author port only reports and sends turns. A `pending` run with an `agent` or `human` step in `plan` becomes `planning` and sends a planning turn: the spec followed by "Produce a plan for this task. Do not change files.". On Codex that turn passes a read-only sandbox and the `never` approval policy in `turn/start`, which the installed app-server documents as a per-turn override; the next turn sends the session's own policy again. Claude Code is read-only anyway. A `pending` run without such steps begins its `plan` steps directly, or goes straight to the implementation turn when the phase has none. When the planning turn completes, the `plan` steps run; when they pass, the run becomes `implementing` and sends the spec, the plan reply when a planning turn ran, and "Implement the task as planned.". When that turn completes, `pre-done` steps run, then `pre-push` steps, then the run passes. A turn that ends `failed` makes the run need attention, `stopped` makes it `stopped` and `interrupted` makes it `interrupted`, each with a short reason. A message ID that is already used by a message without the workflow origin is refused, and the run needs attention. Every completed turn creates its review version as for any session; later stages bind gates to it.

Each turn carries `origin: 'workflow'` and a deterministic message ID derived from the run ID, the turn kind and the attempt. The session service treats an existing ID as already sent and returns without starting anything, so repeated passes never send a turn twice. A turn is sent only when the run status requires it and its ID is unused. When the session's folder is claimed by another session or operation (see Folder locks), nothing is written and the runner starts a single 60-second timer for that run; it is the engine's only timer and there is no polling loop. The next folder release calls `advanceRun`, which sends the turn once. If the timer fires first, the run needs attention with "The session folder stayed in use by another session".

Session events reach the runner in one place: the session service notifies run-finished listeners after a turn is finalized, its result and review are saved and the session no longer counts as active. For a bound session the listener calls `advanceRun`; it also wakes runs waiting for an idle host. While the turn is still active, its state reads as running, so checks never start before the diff is captured. Stop on a bound session while one of the run's own turns is active stops the run through the runner; Stop on an operator message in that session stops only that message. `stop-workflow-run` stops the run and the session's active turn. After startup recovery the host calls `advanceRun` for every unfinished run, which only reconciles: recovery has already made runs that were planning, implementing, checking or fixing `interrupted`, and a `pending` run that never began becomes `interrupted` too, so no turn is replayed.

`resume-workflow-run` accepts an `interrupted` run or one that needs attention. It is refused with "Step `<name>` may already have run. Mark it done or run it again." while any step is `uncertain`, with `busy` while another run is active for the project, and when the awaited planning or implementation turn ended before it finished, because resume never repeats a turn; such a run can only be stopped and the task started again. Otherwise it writes the intent in one transaction (a new `pending` attempt for every `interrupted`, `failed`, `error` or `blocked` step of the current phase, the status the run had in that phase, no attention) and calls `advanceRun`. The pass then evaluates the dead paths again: an `unreached` step whose dead edge came from a retried step gets a new `pending` attempt and runs if its edges fire, while one cut off by a step that keeps its outcome, such as an `on failure` branch of a step that passed, stays as it is without a new attempt. Only one active run per project root exists; tasks in different project roots or worktrees run at the same time, and a task's turns wait only for the folder of its session.

The author session's provider process inherits the host environment plus `NESVO_RUN_ID` and `NESVO_PROJECT_ROOT` (the operator's project, which differs from the session directory in a worktree), so a tool started inside the session can tell it belongs to a run. Command and action steps receive the same variables from the runner.

### Workflow view

The renderer keeps workflow runs and step records next to sessions in `use-sessions.ts`, keyed by host and ID and merged by revision from `workflow-run-changed` and `workflow-step-changed`. A connected computer with the `workflows` capability loads its first run page on connection, and every session with `workflowRunId` loads its run detail once per synchronization; a host snapshot clears that memory so a reconnect reloads it. Workflow methods take the host ID explicitly, so they need no host-bound wrapper.

`entities/workflow` holds the labels and tones: phases read Plan, Before done and Before push; run statuses map to text such as Checking, Waiting for you, Passed and Needs attention; tones use the existing success, error, warning and info foreground tokens, with pending, skipped, stopped and interrupted muted. A step shows its latest attempt, and the step list is built from the pinned workflow in the run, so steps without a record still appear as pending.

The conversation stays free of workflow content. Workflow state lives in the session card, a floating 232 px card anchored at the top right of the session view. A session with `workflowRunId` shows a compact status button in the header (the workflow glyph and the run status in its tone, icon only on narrow windows) that opens and closes the card; other sessions, the inbox and the new-thread screen open it from the details button. Opening the card focuses it, the arrow, Home and End keys move between its rows, and Escape closes it and returns focus to the button that opened it, or to the header button when the opener was replaced. ### Graph editor

The desktop edits a workflow on a canvas opened from the Workflows view (Edit on a row, or New workflow). The editor in `widgets/workflow-graph-editor` is a client of `save-workflow-definition` and `list-workflow-definitions`: it never asks the host to compose YAML. `entities/workflow-graph` turns a resolved workflow into an editor document (nodes with positions, edges with their condition, the original body) and back into file text with the frontmatter in a fixed order: `name`, `description`, `steps` in topological order by phase and then by canvas x, `edges` as one string per edge with `on success` omitted, `layout` as integer pairs, then the body unchanged. A workflow opened without `edges` shows the implicit chain and is written with explicit `edges` and `layout` on its first save. The canvas is free and flows from left to right: a Start node, then the steps as cards, with a dashed frame computed around the steps of each phase and the author turn drawn between the Plan frame and the next one. Positions are the saved `layout`; the tidy-up action places steps by phase and then by depth in the graph. A card's `phase` lives in the step file and other workflows may use the step, so the inspector changes it and shows how many other workflows use the step. Every free output carries an add button that opens the node picker (catalog steps by type, or a new step of that type) and connects the pick to its source; a hovered connection offers to insert a step between its ends or to remove it; a card offers Duplicate and Remove on hover. The editor keeps an undo history of the document in memory. Validation happens twice: live on the client with the shared `resolveGraph` (badges on nodes, Save disabled while an error exists, a refused connection shows the shared message inline), and on the host at save, whose issues come back inline by step name. Save writes each new or changed step file first and then the workflow, each through `save-workflow-definition` with the `expectedHash` the editor opened; a `workflow-definition-conflict` opens a dialog with the current file text and the choice to reload or to keep the edits on top of the newer hash, and nothing merges. A run of the open workflow can colour the nodes by their latest attempt state and open the step result in the inspector; the editor starts no run. The Start node reads the scheduled jobs whose `workflow.name` is this workflow and only lists them. The canvas uses an MIT-licensed library pinned exactly at 12.12.1 in `apps/desktop/package.json` and listed in `THIRD_PARTY_NOTICES.md`; the library supplies panning, zooming, dragging and connection gestures, and every colour it draws comes from the application tokens. The inspector forms render through the props contract in `widgets/workflow-graph-editor/inspector/index.ts`, and `data-slot="editor-dock"` at the bottom right of the canvas, of the Workflows list and of the Automations list is the mount point for the shared workflow assistant in `widgets/workflow-assistant`, which takes its subject from the view (the open workflow, the Workflows list or the Automations list), keeps one conversation per computer, folder and subject with a local history of earlier conversations, and renders the host's `workflow-assistant-change` and `workflow-assistant-change-refused` events as cards with Undo through `workflow-assistant-undo`; the renderer marks the steps, workflows and automations those changes created as added by the assistant and refreshes the catalog and the automations when a change arrives.

The inspector forms in `widgets/workflow-graph-editor/inspector/` compose step, workflow, connection and schedule values on the client, check them live with the contract schemas so the messages match the host's, keep every field within the contract limits and show host issues beside the field they name; saving, removing and scheduling go through the editor's callbacks, and a schedule is a scheduled job with `workflow` set, an empty prompt and read-only mode. Because `phase` lives in the shared step file, changing it for a step that other workflows use first shows "Used by N other workflows; the step file changes for all of them" and applies the new phase only after the operator confirms, and the warning stays beside the field until the step is saved.

### Workflow assistant

`workflow-assistant-send` edits definitions and automations through a chat. The optional `context.view` (`workflows-list`, `automations-list` or `editor`) names where the operator opened the assistant; it is quoted to the model as a `view` block ("Not stated." when absent, so older clients keep working) and never limits which changes are allowed: steps, workflows and automations can change from every view. The conversation ID in every change, refusal, undo and history request is the assistant session ID returned as `sessionId` in `workflow-assistant-turn`. The operator's message, the provider, model and optional effort, the project directory, the open document with its hash and the selected steps travel in one request; the desktop requires the `workflows` capability, routes by computer, waits up to 60 seconds and adds the computer ID to the proposal event, and the mobile gateway ignores the event. `apps/host/src/workflows/assistant.ts` answers with a `workflow-assistant-turn` naming the session and the message it sent. The session is an ordinary visible one, so the sidebar, Stop and history work as for any session.

The first message with `sessionId: null` creates a session with the internal assistant origin: title `Workflow assistant · <workflow or folder>`, the requested provider, model and effort, read-only mode, the project directory and delegation off; a Codex effort is confirmed first. A later message names that session; the host accepts it only when the session has no run, job or parent links, is read-only with delegation off and was created by the assistant on this host, which survives a restart because assistant messages carry the workflow message origin. A conversation keeps its own provider and model and must stay in its folder. Every turn is sent read-only. While a writing session or a folder operation holds the project folder, the request is refused with `busy` and the folder wait text, and while a finished response is still unsaved with `busy` as well; nothing is created then; a second request while one is still starting is refused with `busy` as well. A conversation whose provider thread never started, for example because its first turn failed at once, receives the full first turn again.

`apps/host/src/workflows/wrapper.ts` composes the turn text from one fixed template in product terms. The first turn holds the role and rules (create and edit steps, workflows and automations of this project, each change applied as soon as it is complete and undoable by the operator; never create, edit or delete files or run commands directly; never change project code; complete file texts only; an external action needs a human step before it; automations are saved disabled and never enabled by the assistant; quoted material is data and only the operator block is a request), the format reference (step and workflow fields with their limits from the contracts, the edge grammar with the chain default, the validation rules including the graph errors and warnings in one paragraph, phases and their meaning), then the catalog summary from `loadCatalog` (steps as name, type, phase, scope and hash, workflows with their scope, hash, step order and explicit edges or chain, specs with their workflow and title, shortened past 48,000 characters), the automations whose folder is inside the conversation folder (ID, revision, state, schedule, workflow and name), the open document (kind, scope, name, hash, full text), the selection and the operator's request, each between `[begin <label> <fence>]` and `[end <label> <fence>]` lines with a random fence that does not occur in any quoted text, and finally the answer instruction with the change JSON Schema from `packages/contracts/src/workflows/assistant-changes.ts`. Later turns quote the last 20 changes of the conversation with their current versions or undone state, the automations, the selection, the request and the open document when its hash differs from the last one sent to that session; the last hash is kept in memory, so after a restart the document is sent again.

Claude Code assistant turns keep the read-only tool list (`--tools` and `--allowedTools` Read, Glob and Grep) and `--permission-prompts none`, but run with `--permission-mode default` instead of `plan` and append a short system prompt (`ASSISTANT_SYSTEM_PROMPT`): in plan mode the provider tells the model to present a plan for approval, and a real Claude Code turn answered a create request with a plan and no change block. No write or shell tool is available in either mode and no permission is granted implicitly. Other read-only Claude sessions keep plan mode. The answer instruction states the block grammar, "every change MUST be a nesvo-change block; prose or other fences change nothing", and one complete worked example each for a step create, a workflow create with edges and an automation create; the examples are built from objects that the tests parse with the contract. The `view` block also names what to create when the request does not say: workflows and their steps on the Workflows list and when no view is given, automations (with the workflow they run when needed) on the Automations list, the open workflow and its steps in the editor.

Both providers answer in the same shape and no output schema is passed: each change is a fenced code block tagged `nesvo-change` holding one change object, followed by a plain-text reply. The host watches the session's streaming reply through the `session-changed` events it already emits, finds every complete change block (an opening fence anywhere, closed by the next line that starts with three backticks, so blocks survive message texts that the provider joins without a separator; the fence name is matched without case and also as `nesvo_change` or `nesvochange`, optionally with `json` before or after it, while a plain `md`, `json` or untagged fence never counts) and applies the blocks one after another, in their order, while the turn is still running; at most 16 are applied per turn and the rest are refused once. A block that is not valid JSON or does not match the change schema is refused with the reason `invalid`. When the turn ends, blocks not seen yet are taken from the final reply, an opening without a closing fence is refused, and when the reply held no valid change block although the request asks for a change (an English or Polish change verb such as create, add, change, delete or schedule) or the reply has fenced text that looks like a definition (frontmatter with `name` and `type` or `steps`, or a `steps: [` line), the host sends exactly one repair turn in the same session: "Your reply changed nothing. Re-emit the intended changes as nesvo-change blocks only." with the grammar and the examples again. Its blocks are applied and announced under the original message ID; when it again holds no valid block, the turn ends with a `workflow-assistant-change-refused` event (reason `invalid`, "The assistant wrote no change block, even after it was asked again, so nothing changed. Ask again and name the change you want.") and an `invalid` end-of-turn event. The repair request stays visible in the session history. Then the host waits until every change of the conversation is settled, and `workflow-assistant-proposal` is emitted with status `ok`, the reply text without the change blocks and an empty `changes` list; a turn that ends `failed`, `stopped` or `interrupted` emits status `invalid`, and the changes it applied before stay applied. The reply passes through the result secret filter; so do change summaries.

`apps/host/src/workflows/assistant-changes.ts` applies a change and never writes by itself. A step or workflow goes through `saveDefinition` or `deleteDefinition` with the conversation folder, the change scope and name, and `basedOnHash` as the expected hash (null for a create), so the writer's path confinement (the name rule, the project or global definitions root, no symbolic link and no project folder resolving outside the project), its expected-hash conflict, full validation, the active-run refusal and the step-in-use refusal all apply unchanged. The assistant write adds `guardExternal`: for a workflow, the graph warning that an external step is reachable without a human step becomes an error and the file is not written; for a step, the check runs for every workflow file in the project and global roots that lists the step, including workflows the catalog leaves out because another step is still missing (a missing step counts as a non-human step in the written step's phase), and refuses any such warning that involves the written step or that the write introduces. A global step write is also refused when the step alone is an unguarded external action or when it stops being a human step, because workflows in other projects may use it. The writer reports the file it replaces under its lock, after the hash check, and that text is stored with the change. An automation goes through the automation service: a create gets a new ID, the conversation folder and `active: false`; an update or delete needs the automation ID and `basedOnRevision`, must name an automation whose folder resolves inside the conversation folder, and an update is saved disabled whatever its previous state; a change that sets `active: true` is refused as `unsafe`. The previous automation record is stored as JSON.

Each applied change is written to `assistant_changes` (schema version 11: ID, conversation, sequence, status, the change document, the previous content and, for a step or workflow, the resolved definitions folder the writer used, as an absolute real path) and then announced as `workflow-assistant-change`; for an automation, the service's own `scheduled-job-changed` event comes first. A refused change is announced as `workflow-assistant-change-refused` with the reason `invalid`, `conflict`, `unsafe` or `unavailable` and up to 50 issues, and nothing is stored; a change that was written but could not be recorded is reported as `unavailable` with that explanation. Changes of a conversation are serialized, including undo, a new turn waits until the previous turn is settled, and host shutdown waits for changes in progress. `workflow-assistant-changes` returns the last 500 changes of a conversation in sequence order, from the database, so the history survives a restart. `workflow-assistant-undo` restores the previous content through the same writer, only in the recorded definitions folder: the writer receives it as the expected root and refuses, under its lock, when the folder no longer exists or the project or global root now resolves to another real path (for example after a `.git` was added above the folder or the folder was replaced by a link), so an undo never lands in a different `.agents/workflows`. The file is the recorded relative path (`steps/<name>.md` or `workflows/<name>.md`) inside it. A create is deleted with its resulting hash or revision as the expected one, an update is saved back with the resulting version as the expected one, and a delete is saved again as a new file or as an automation with the same ID. A different current version returns `conflict` with that version and changes nothing; a writer refusal such as a step still used by a workflow returns `refused` with its issues. Undo is an operator action, so the restored content is not subject to the assistant guard and a restored automation keeps its previous enabled state. A successful undo marks the change `undone` and announces it again.

What reaches the provider is the same as for any read-only session: Claude Code keeps its read-only tools, and Codex runs the turn in a read-only sandbox, so neither provider can write through the assistant session itself. The only writes are the host's, from change blocks it validated; the answer's shape is a request to the model, not a guarantee.

The graph editor carries the assistant dock (`apps/desktop/src/renderer/src/widgets/workflow-assistant/`) in its bottom-right slot: a collapsible chat with the provider and model picker that keeps one session per computer, folder and workflow, shows the operator's own text instead of the wrapper, and shows the reply of each turn; it sends the open workflow only while the editor has no unsaved edits, and the full conversation stays in the visible session behind Open session. The preload API exposes `workflows.assistantChanges(hostId, conversationId)` and `workflows.assistantUndo(hostId, { conversationId, changeId })`, and the workspace events `workflow-assistant-change` and `workflow-assistant-change-refused` carry the computer ID.

### Agent steps

An `agent` step (`apps/host/src/workflows/steps/agent.ts`) runs in its own session created through the session service with the internal workflow origin that names the run and the step, so the session carries `workflowRunId` and `workflowStepId` and the step record carries the session ID. The step session uses the run's gate provider and model, read-only mode, the run directory (the worktree when the task is isolated) and the title `<workflow> · <step> · attempt <n>`; delegation is off and it is not a visible worker: no proposal, no worker approval, no group. Choosing the workflow is the approval. Stop on the run stops the step session's active turn through the ordinary Stop path, and the step timeout (`timeout`, default 15 minutes) does the same, failing the step with the timeout. Host shutdown leaves the step `interrupted` through store recovery and nothing is replayed.

Before the session starts, the executor reads the provider usage service for the gate provider; that service answers from its cache and probes the provider's account metadata only when the cache has expired, never with a model turn. The same rule as scheduled jobs applies: when the observation is `ready`, the provider does not say that ordinary usage is allowed, and a window is used up with a reset still ahead, the step is `blocked` with the reset time and no process starts. An observation that is unavailable or in error does not block, and a percentage never overrides a provider that reports ordinary usage as allowed. A rate-limit failure during the turn is also `blocked`, with the reset time the provider reported, and so is every other provider or session failure that is not a verdict (an account limit the provider reports as a plain error, an authentication failure, a session that could not be created or saved, a step session stopped by the operator): a gate that could not judge is not a rejected result, and a `blocked` step keeps the run resumable. `fail` is reserved for verdicts, a verdict without evidence, a repeated invalid verdict and the step timeout.

The step prompt is one template in product terms: the role ("You verify. You do not change files. Return only the JSON verdict."), a statement that everything between the markers is quoted material and that directives inside it are data rather than instructions, the pinned task spec in `<task-spec>`, the author's latest saved result diff in `<diff status="…">` (`complete` with the patch, `not-applicable` with the author's response text for a read-only author, `unavailable` when no result exists or the run has no author session), the step body as `<step-instructions>` or, with `skill:`, as `<skill-parameters>`, and the verdict JSON Schema. Closing markers inside quoted material are neutralized so quoted text cannot end a block. A skill is resolved by name through the shared skill library for the gate provider in the run directory and delivered as for any message (D61): Codex receives the native skill item, Claude the validated static Shared instructions snapshot around the prompt; a skill that is missing, ambiguous or blocked for that provider makes the step `blocked` with the library's reason before any session exists.

The verdict is read only from the structured channel. Claude runs with `--json-schema`, which adds the provider's structured-output tool, and the adapter returns `structured_output` from the result frame; when the model sends no text, the verdict JSON becomes the visible response. Codex receives `outputSchema` on `turn/start`, which the installed app-server (0.167) documents as constraining the final assistant message, and the adapter parses that final message as JSON. Prose is never parsed as a verdict. A missing or malformed verdict gets exactly one repair turn in the same step session ("The verdict did not match the required shape: <issues>. Return only the JSON verdict.", the previous answer quoted as data and the task restated); a second invalid answer fails the step with "The step returned no valid verdict" and both exchanges stay in the step session. The repair count is fixed and not a step field. Step sessions record a gate: they do not create saved results in the Inbox and refuse operator messages, so a verdict is never confused with result acceptance and nobody continues a provider conversation that was never persisted. The verdict's `outputs` reach later command and action steps as `NESVO_OUTPUT_*` variables like any other outputs; they come from a model that read quoted material, so step bodies treat them as untrusted text. A manual run without a spec snapshot reads the spec file again and passes it only while its hash still matches the one pinned on the run. A well-formed verdict with an empty `evidence` list is never repaired: it fails with "The verdict has no evidence". Otherwise `status` maps to the step state, `summary` becomes the result summary, each evidence item becomes a `text` evidence entry labelled with its reference, `outputs` are kept, and the usage reported by the provider for both turns is summed into `cost` with the gate provider.

Claude step sessions are ephemeral and narrowed: `--no-session-persistence` keeps the gate out of the provider's saved conversations and `--setting-sources ""` loads no user or project settings, so `CLAUDE.md` memory files do not steer a gate. Because nothing is persisted, every turn of a Claude step session is a new provider conversation with a fresh provider session ID; that is why the repair turn restates the task. `--bare` is not used: it would restrict authentication to an API key. The tool set stays Read, Glob and Grep in plan mode, so a Claude gate structurally cannot write. A Codex gate relies on the read-only sandbox and the `never` approval policy for the thread and the turn; the sandbox is enforced by the provider, not by Nesvo, and read commands may run inside it. Its thread configuration sets the project instruction file size to zero, so the project's agent instructions in a directory the author can write to do not steer the gate either; the fixture records that setting on every verdict thread. The quota check reads cached account metadata and never infers permission from a percentage. The fixtures assert the argument set (tools, plan mode, no persistence, empty setting sources, the parsed schema) on every verdict launch and the read-only sandbox with the output schema on every Codex verdict turn.

### Human gates

A `human` step (`apps/host/src/workflows/steps/human.ts`) binds to the latest review version of the run's session, which is the result of the implementation, planning or correction turn that preceded it. The step becomes `awaiting-human` with `reviewId` and `reviewVersion`, and the run becomes `awaiting-human`, in one transaction; then the pass waits. A session without a review binds the gate to no review and the decision rests on the spec alone. When the latest result was already decided outside the gate (changes requested or rejected), the step is `blocked` and the run needs attention instead of waiting on a result nobody can decide. A manual run has no session, so its `human` steps are `skipped` with "Runs without a task session do not wait for a human decision", which keeps manual runs and the portability check unattended; a `human` step followed by an `effect: external` step in the same phase is `blocked` instead, so an external step never runs without a decision. Host shutdown and restart keep a waiting gate as it is and never resolve it. The binding is per step, so it does not depend on the order or shape of the workflow around it.

The gate also records `definitionChanges`: the paths of the bound diff under `.agents/workflows/` or `.agents/tasks/`, compared without regard to case because case-insensitive filesystems read those folders under any spelling, at most 64. A running task is protected by the definitions it pinned at start, but accepting such a diff changes what later runs of the project execute, so this flag is the one place where a session can change the definitions of future runs, and the operator decides with it in view.

`decide-workflow-gate` names the run, the step, the bound review ID and version (both `null` for a gate without a review), an idempotent decision ID, the decision and a comment. A repeated decision ID with the same payload returns the current run, also while the first request is still running; a different payload is refused. The host refuses a step that is not the latest attempt or not `awaiting-human`, a run that is not `awaiting-human`, a different review ID and a stale version. The decision is stored on the step as `decision` (`decisionId`, `kind`, `comment`, `at`) and written in one transaction with the step result, the run status and the review decision:

- `accept` performs the review acceptance exactly as `decide-review` does: the host must be idle, the version current, and the directory is captured again and compared with the recorded fingerprint, so an outside edit refuses the decision and changes nothing. The step passes with "Accepted by the operator" and the comment (or "Accepted") as the operator note, the run returns to `checking` and the pass starts the next step. A review already accepted at an earlier gate of the same run stays accepted and is only checked again.
- `reject` needs a comment. The step fails with the comment, the review becomes `rejected` with a `reject` decision and the run `rejected`. No turn starts.
- `fix` needs a comment and a task session. The review records `request-changes`, the step fails with the comment and the run becomes `fixing`. The runner's `fixing` move sends the comment as a correction turn through the author port, with the message ID derived from the run, the step and its attempt, so repeated passes send it once. When the correction completes, a `plan` gate re-runs the `plan` phase; any later gate restarts from `pre-done`, because the change can invalidate earlier checks. Every step gets a new attempt row and the gate binds to the new version. A correction that ends `failed`, `stopped` or `interrupted` makes the run need attention, `stopped` or `interrupted`. Corrections from a human are not counted.

While a gate waits on a version, and while the run of the result's session is in progress at all, `decide-review` answers `busy` with "This result is waiting for its workflow gate", checked again after the fingerprint capture, so the Inbox result row and the gate cannot diverge and no Inbox correction starts while checks run. A finished, failed, stopped or interrupted run leaves its result to the Inbox.

`skip-workflow-step` records an operator's decision to skip a `pending`, `awaiting-human`, `failed`, `error` or `blocked` step of the phase the run is in, while the run is `checking`, `awaiting-human` or needs attention. The step keeps `skip` (`reason`, `at`) in its record for good, its result stays empty, and the run returns to `checking` unless another gate still waits. Skipping a `human` step is refused when a later step declares `effect: external` and no other unskipped `human` step precedes that step, so the validation warning about external steps becomes a hard refusal at the gate. Skipping is refused while any step is `uncertain`, and like resume it answers `busy` while another run is active for the project.

`resolve-workflow-step` is the only command that changes an `uncertain` step, and only while its run needs attention. `mark-done` needs a comment saying what the operator verified; the attempt becomes `done` with "Marked done by the operator. Later steps receive no outputs from it." and the note, and no outputs. `run-again` leaves the `uncertain` row as it is with the decision recorded and inserts a `pending` attempt with the next number. Both are idempotent by decision ID and return the run to `checking` without attention. Resolving also answers `busy` while another run is active for the project. `resume-workflow-run` keeps refusing a run with an `uncertain` step and still gives a failed or blocked step a new attempt when nothing is uncertain. A run whose phase holds a gate sent back to fix resumes in `fixing` without new attempts: an unsent correction is sent, a completed one re-runs the checks, and one that ended `failed`, `stopped` or `interrupted` is refused, because a run never repeats a turn.

Every decision writes its intent and then calls `advanceRun`; no gate command drives a phase itself.

## Agent pull request reviews

A host that advertises `pull-request-reviews` can run an agent review of an open pull request and keep the result as a draft review. The capability sits at the end of the capability list and current desktops gate every reviewer command on it. As with earlier capability additions, an older desktop with strict capability parsing needs an update before it connects to such a host. The scheduled job field and the pull request action it adds are optional additions, so stored jobs and requests without them still parse.

Reviewer profiles and conventions are host-owned and stored per computer in SQLite, never in the repository. Schema version 19 adds `reviewer_profiles` (a revisioned JSON document per profile), `review_conventions` (layer, scope and text) and `review_drafts` (one row per review with a unique request ID, the pull request reference, the session link that becomes null if the session row disappears, an optional automation link and the JSON draft). A profile names the provider, model and effort with the same rules as session creation, the allowed finding types (comment, code suggestion, question, nit), the minimum severity (info, minor, major, critical), the maximum number of findings, the tone, the comment language and whether to add a summary. Conventions have three layers: global, language (a file extension matched against the changed files) and project (a GitHub repository `owner/name` or an absolute project folder).

`start-pull-request-review` reads the pull request head and title through the GitHub CLI, refuses a closed pull request, snapshots the profile into the draft and queues it. The request ID makes a retried start return the same draft. The host runs one review at a time, so a bulk start of up to 20 pull requests is a queue, not parallel work. A review waits only for its own worktree folder, for up to ten minutes before the checkout and before the turn, and not for other sessions. Each review then:

1. creates an ordinary read-only session with the profile's provider, model and effort in a session worktree of the chosen checkout on a `nesvo/review-<number>-<id8>` branch, links the session to the pull request and shows it in the sidebar;
2. runs `gh pr checkout <number> --repo <owner/name> --detach` in that worktree under the existing pull request checkout lock, after checking that the folder is a checkout of the pull request base repository, and records the checked out commit; if it differs from the head reported by the files request the review fails instead of reviewing a moving target;
3. sends one prompt with the profile settings, the matching conventions, the pull request description quoted as author-written context, and the changed files with their patches up to 160 KiB, asking the agent to read `AGENTS.md` and `CLAUDE.md` in the checkout as project conventions. Closing tags inside quoted material are neutralized;
4. constrains the answer with a JSON Schema generated from the Zod contract (`--json-schema` for Claude Code, the turn output schema for Codex) and starts the turn with `--setting-sources ''` for Claude Code and `project_doc_max_bytes = 0` for Codex. Project settings, hooks and automatically loaded instructions from the pull request head therefore never apply; the agent reads the instruction files only as context. Claude Code hooks stay disabled as in every session without the operator's hooks choice.

When the turn completes the host validates the structured output with `agentReviewOutputSchema` at the host boundary. Missing or invalid output marks the draft `invalid` with the first validation issues; nothing is parsed from the reply text. Valid output is filtered by the profile's types and minimum severity, sorted by severity and capped at the maximum; the number left out is recorded. A failed, stopped or interrupted turn marks the draft `failed`. Every completed review session also produces an ordinary result in the Inbox, labelled `Agent review · #<number>`.

Draft findings start undecided. `update-review-finding` keeps, discards or edits one finding against the draft revision; an edit keeps the finding and marks it edited. `discard-pull-request-review` hides a draft that is not running or published. Nothing is published automatically.

`publish-pull-request-review` takes an action ID, the expected draft revision, the GitHub review event (Comment, Request changes or Approve) and an optional overall comment. The host reads the current pull request files first. When the head moved since the review, it returns `head-moved` with the new head and publishes nothing unless the operator confirms. A confirmed publish stays bound to the reviewed commit and moves every finding into the review body. Otherwise each kept finding whose line range lies inside one diff hunk on the right side becomes a line or range comment, a code suggestion becomes a GitHub `suggestion` block, and the remaining kept findings are listed in the review body with their location. The review goes out as one `POST repos/<owner>/<name>/pulls/<number>/reviews` with `commit_id` set to the reviewed head through the existing `act-on-pull-request` path (`submit-review`), so the in-memory action ID cache applies. The draft records `publishing` before the call and `published` with the action ID, event and comment counts afterwards; repeating the same action ID returns the published draft, and another action ID is refused. A host restart turns queued and running drafts into `interrupted` and a draft caught while publishing back into `ready` with a note to check GitHub first; nothing is started or published again on restart or reconnect.

An automation can review new pull requests instead of sending a prompt. Its definition carries `pullRequestReview: { profileId }` (column `pull_request_review`) and requires a folder, which must be a checkout of the repository. The editor preselects a change check that lists open pull requests with their head commits, ask-first and the daily run cap. A run lists up to 100 open pull requests and queues a review for at most five whose latest draft does not cover the current head commit, then records the run as completed; the drafts reach the Inbox as their sessions complete. Pull request descriptions and diffs come from the pull request author, including forks. The read-only mode, the ignored project settings and the operator's publish decision bound what such content can do, but a draft can still contain text an author steered; review it before publishing.

Draft changes are published to clients as `pull-request-review-changed` events. The mobile gateway does not forward them.

## Importing CLI conversations

D73 adds **Import conversation…** to the new-thread screen. It lists conversations from the selected Local or SSH computer. Electron routes `list-conversations` and `adopt-conversation` only to connected hosts advertising `conversation-import`. The picker filters by title, folder and provider and previews a short excerpt before adoption.

On the selected host, Claude Code transcripts are read from the per-project JSONL files in `CLAUDE_CONFIG_DIR/projects` (default `~/.claude/projects`). Conversation rows carry `sessionId`, `cwd` and a timestamp, with string or typed-block message content. Codex reads dated rollout files in `CODEX_HOME/sessions` (default `~/.codex/sessions`). A `session_meta` record supplies the thread ID and working directory, and `response_item` message blocks supply text. The formats were inspected using files from Claude Code 2.1.327 and Codex CLI 0.167.0 on Windows.

Discovery reports the newest readable candidates by file modification time. Each provider scan examines up to 8,192 directory entries, reads up to 64 candidate files and caps reads at 8 MiB per file and 48 MiB per provider. The catalog counts skipped transcripts and reports when limits reduce the result set. It exposes a title and a short prompt excerpt. The parser selects user and assistant text and omits provider context, tool calls and outputs, attachments, thinking and account metadata. Recognizable credential patterns in selected text are masked. Provider IDs already bound to Nesvo-created sessions are excluded. Imported IDs that remain discoverable show an Adopted badge.

Adoption resolves the selected provider ID again on the host, checks the recorded working directory and writes one session with up to 48 text messages of 6,000 characters each. It labels these messages Imported, starts in read-only mode with default model selection and records the provider thread as initialized. Reusing the same request ID returns the existing session. Another request for the same provider ID is refused. The operator's next message uses the existing Claude `--resume` or Codex `thread/resume` path. Discovery and adoption open provider transcripts for reading, and the provider controls its own history when a later turn runs.

## Running apps

Settings › General › Show running apps is a local view preference, off by default. While it is on, the desktop asks every connected computer that advertises `running-apps` for `list-running-apps` every 10 seconds, only while the window is visible, and shows the result beside each session: a mono `:port` chip after the branch in the header, whose popover lists the address, process name and how the port was matched, with an Open button for a local port, and the same `:port` label (with `+N` for more) in the sidebar row. A disconnected computer simply drops its ports from the view.

The host answers from `apps/host/src/running-apps`. Provider processes run with `NESVO_SESSION_ID` in their environment, and both provider adapters record the process ID of every CLI they spawn with that variable. A scan reads the listening sockets and the process table: Windows through one PowerShell call (`Get-NetTCPConnection -State Listen` and `Win32_Process` with parent IDs and creation times), Linux through `ss -ltnpH` and `/proc`, macOS through `lsof` and `ps`. A port belongs to a session when one of its process ancestors is a recorded provider process; when that ancestor has already exited, the listening process must have started after it was recorded, which keeps a reused process ID from matching. On Linux a background server whose parent already exited is reparented and loses that chain, so the scan also reads the inherited `NESVO_SESSION_ID` from `/proc/<pid>/environ` and attributes the port to that session when it is listed. Otherwise the process working directory is compared with session folders and a single deepest match wins (Linux and macOS only; Windows does not expose another process's directory). Only attributed ports are returned, at most 256, with `match` `process` or `folder`. Scans run one at a time, are cached for three seconds, time out after ten seconds and are cancelled with the host. The records live in memory, so after a host restart only folder matching applies until the next turn. Nesvo never stops or restarts these processes. macOS and Linux paths are configured but were checked on Windows only.

## Opening a session in a terminal

**Open in terminal** in the session actions menu and the command palette hands a session to the operator's own terminal. It needs a recorded provider thread, so a session without a first turn, a running session, a worker and a workflow gate cannot use it. Electron main reads the session from the host again instead of trusting the renderer, checks that the thread ID is a UUID and builds an argument array: `claude --resume <id>` for Claude Code and `codex resume <id>` for Codex, verified with Claude Code 2.1.327 and Codex CLI 0.167.0. Nothing is passed through a shell string. Windows opens Windows Terminal (`wt.exe -d <folder> cmd.exe /k …`) when its app execution alias exists and the folder contains no `;`, otherwise a new `cmd.exe /k` console. macOS writes a private temporary `.command` script that removes itself and opens it with `open -a Terminal`. Linux tries `x-terminal-emulator`, GNOME Terminal, Konsole, Xfce Terminal and XTerm in that order. Development builds can record the planned launch to `NESVO_TERMINAL_LAUNCH_LOG` instead of spawning it; packaged builds ignore that variable. A session bound to a provider profile other than the default is refused with the command and the variable to set (`CLAUDE_CONFIG_DIR` or `CODEX_HOME`): Windows Terminal can open the tab in an already running process that does not inherit an environment Nesvo would pass, and resuming the thread under the wrong account is worse than asking the operator to start it.

Before launching, the host records `externalAttachment` with a timestamp on the session through `set-session-terminal` (capability `terminal-handoff`). While it is set, `send-message` and `queue-message` are refused with a busy error, so Nesvo never runs a turn in parallel with the terminal. A failed launch clears the flag again. The conversation shows the terminal state in place of the composer with **Return to Nesvo**, which clears the flag. Turns made in the terminal are not copied into Nesvo history; the provider resumes the same thread from its latest state on the next Nesvo turn. Restarting a session starts a new provider thread and clears the flag. For an SSH computer Nesvo does not launch anything: it shows the exact `cd '<folder>' && <command>` line, and **Copy and hand off** copies it and sets the flag on that host.

## Searching CLI transcripts

The history search dialog has an **Include CLI transcripts not yet imported** scope, remembered per device. With it, the desktop also sends `search-transcripts` to each connected computer advertising `transcript-search` and lists the matches in a separate group per computer. Choosing one opens the import dialog with that conversation preselected; `list-conversations` accepts an optional `include` identity so a conversation outside the newest import candidates is still listed. Adoption stays an explicit operator action and starts read-only.

The host builds the index lazily when a search arrives and refreshes it at most every two seconds. It reuses the import scanner and parser, so the same text selection and credential masking apply. Each refresh lists both providers, keeps the newest 300 transcripts per provider by modification time, reads only files whose size or modification time changed, skips files over 8 MiB, reads at most 64 MiB per provider and stops after 20 seconds; the remainder is indexed by later searches and the page reports `truncated`. Each transcript contributes its most recent messages up to 32,768 characters, each message clipped to 4,000. Rows for transcripts that disappear or leave the window are removed. Unreadable transcripts are recorded once and counted as skipped until they change. Transcripts are opened read-only and never modified.

Schema version 17 adds `transcript_files` and `transcript_entries` with an external-content FTS5 table when the runtime supports it; otherwise matching falls back to case-folded LIKE over the stored entries. The tables are a cache: a change of index mode drops and rebuilds them. Results exclude every provider thread already bound to a Nesvo session, adopted or created by Nesvo, and return at most 50 transcripts, ranked by BM25 with one snippet per transcript.
