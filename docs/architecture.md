# Architecture

## Workspace shell

The desktop shell is one resizable sidebar and a conversation column. The sidebar carries the sidebar toggle and product name in the title row, a search row with the new-session action, the Inbox entry, the session list and a footer. The footer holds Settings and one usage ring per provider on the left, and the selected computer (opening Settings › Computers) on the right. Sessions are grouped by computer when more than one computer is known; each row shows a project chip, the working-directory basename, the status or relative time of the last update, the title, a cloud mark for remote sessions and the provider mark, with workers nested under their parent. Provider marks are small inline SVG drawings in the current text colour, a ray burst for Claude Code and an interlaced knot for Codex, used wherever the app identifies a provider: session rows, usage rings and bars, the model picker, the composer and the session card. The header shows a breadcrumb of project chip, directory and session title and keeps the pipeline status or session details button and the skills, files and context toggles at the right.

The native title bar is hidden. The sidebar title row and the main header form one borderless 40 px drag region; buttons, inputs, popovers, dialogs and the sidebar resize handle opt out of dragging. Windows and Linux keep the operating system's window controls through a transparent title bar overlay whose symbol colour follows the colour scheme, and the header reserves the overlay width from the `titlebar-area-*` environment values. macOS keeps inset traffic lights and the first row gains a left inset. Double-click maximize and snap behaviour stay native. The preload API is unchanged; macOS and Linux behaviour is configured but has not been verified on those systems.

Each usage ring shows the remaining share of the provider's most used reported window, coloured by level (at least 50% left, at least 20%, below 20%), with a tooltip that lists every window with its reset time and says when the limits were last checked. Stale observations fade with a warning dot, offline computers show the last observation in grey with an offline dot, a pending first read pulses, and unavailable data shows only a dashed track; none of these is drawn as zero. The session card, opened from the header and described under Pipeline view, repeats the weekly limits as bars so they stay reachable while the sidebar is collapsed. Rows only appear when Nesvo has the data: the inbox and the new-thread screen show the computer and usage only, and there is no context bar because hosts do not report a context window. The card offers no push or pull request actions.

Settings is one large modal with a searchable left navigation, a breadcrumb and a close button. General shows the selected computer's connection and each provider's status with refresh and sign-in hints (moved from the Context sheet, which now keeps only session details). Appearance chooses the colour scheme: System (the default), Light or Dark. Electron main stores the choice in `appearance.json` in the user data folder and sets `nativeTheme.themeSource` before the window opens, so the window background and the caption symbols follow it. The renderer does not rely on `prefers-color-scheme`, which Chromium does not derive from `themeSource` on every Linux setup: main resolves the applied scheme from `nativeTheme.shouldUseDarkColors`, passes it to the preload as a launch argument and sends changes when the theme updates or the choice changes, and the renderer toggles a `dark` class on the root element before React renders (dark until told otherwise). The preload API gains `colorScheme`, `setColorScheme` and `onAppliedColorScheme`, validated by the shared contract. Computers, Phone access and Account and limits are the former dialogs and footer popover as pages; the usage rings keep their own popover.

The conversation is a 38 rem column. Operator messages are right-aligned bubbles and agent text has no frame; fenced code blocks in either are rendered as bordered blocks with the language and a wrap toggle, while the rest of the text stays plain. The docked composer reuses the new-thread composer's glass surface, model chip and round send button, with the computer, project and permission mode as chips below it. Side panels (files, saved diff and skills) share a 40 px header and borderless search on the app background, and inbox rows keep their decisions inline with rounded hover fills.

The sidebar defaults to 256 px and can be dragged, moved with the arrow, Home and End keys, or reset by double-clicking its edge, between 208 px and the window width minus 640 px. Collapsing hides it completely, moves focus to the header toggle and is available from either toggle or Ctrl+B. The open state and width are local view preferences stored in the renderer, like the last session and saved-diff location; the host remains authoritative for all session data. Compact widths keep the existing sheet navigation. The window follows the colour scheme chosen in Settings, by default the operating system's.
Colours, surfaces, the glass composer and popovers, spacing and status colours are CSS custom properties in `styles.css`, consumed through Tailwind theme tokens rather than literal colours in components, and the interface uses the Inter variable font. The compact dark theme, glass surfaces and sidebar density are built from base shadcn components.

## New thread

New session opens a screen in the main area instead of a dialog: a heading with the chosen project folder (or "No project") below it, one composer and a row of chips. The chips are popovers for the provider and model (a provider rail built from the per-host status and a searchable list from each provider's reported catalog), the computer to run on (Local and connected SSH computers, with the existing Computers flow for adding one), the working directory (the existing input and host validation; an empty value means the host's isolated folder) and permissions (a segmented control limited to Read-only and Workspace edits, with Workspace edits disabled for Claude because Claude runs read-only analysis in Nesvo). Enter sends and Shift+Enter inserts a newline.

The first message creates the session through the existing create and send APIs with exactly the chosen provider, model, host, directory and mode; the trimmed first line of the message becomes the title, capped at 100 characters. No role is sent. A creation failure, such as an invalid directory, stays on the screen with the draft; a send failure after creation appears inside the new thread and never re-creates it. The composer offers the same `/` skill menu as a session. Its catalog comes from `discover-skills` with the chosen provider and folder on the chosen computer, resolved like `create-session` (an empty folder uses the host's shared workspaces root), so no session is created to list skills. The first message carries the selected skill ID and hash; `send-message` revalidates it against the created session before any provider turn, and a mismatch leaves the draft and selection inside the new thread with the error. Changing provider, computer or folder clears the selection. Attachments are not shown because the contracts and host do not provide them.

The model picker has a Reasoning column. Provider status reports effort support: Codex reports it per model from the `supportedReasoningEfforts` and `defaultReasoningEffort` fields of its `model/list` catalog, and the column lists exactly those values with the catalog default marked. The Codex default entry carries no efforts because Nesvo does not pass a model for it and the effective model depends on the user's Codex configuration. Claude Code reports `unsupported` with a reason, because Nesvo runs it without an effort setting; the column shows that reason and no choices. A Codex model with efforts always sends an explicit effort, starting from the catalog default. `create-session` accepts an optional effort only for a specific Codex model, and the host confirms it against a fresh catalog read before saving the session and again before every turn, because the app-server accepts and echoes arbitrary effort strings. A withdrawn effort fails the run before any thread or turn starts. The session stores the effort; every turn passes it as `model_reasoning_effort` on `thread/start` or `thread/resume` and as `effort` on `turn/start`, and a thread response that reports a different effort fails the run before the turn starts.

The new-thread screen shows no Git branch. A host-only reader module (`apps/host/src/workspace/git-branch.ts`) reads the current branch in a short-lived Node child process with non-blocking, regular-file-only reads capped at 4 KiB, killed after two seconds or on cancellation. No request, preload method or renderer path reaches it: the folder validation and `realpath` it would need still run synchronously in the host before the child starts, so a hung network filesystem could block the host. The branch chip moves to its own stage, UI1f, which moves that validation and resolution into the child process before the read is exposed again.

Host health lists the capabilities `scheduled-jobs` and `reasoning-effort`. Electron records them per computer at synchronization and refuses a scheduled job command or an effort request locally for a host that does not list the matching capability, because an older host rejects unknown fields without a request ID and the SSH client treats that as a protocol failure. Status from such a host defaults to Claude-style `unsupported` effort with an update reason and models without efforts, so the picker offers no effort.

## Mobile companion

D66 adds an Expo React Native client in `apps/mobile-client` and a narrow opt-in HTTP/WebSocket gateway. The reusable gateway belongs to `apps/host/src/mobile`; Electron supplies its lifetime and an adapter to the existing ComputerManager. It routes to Local or an already-connected SSH host without creating another host runtime or database. Mobile and desktop share Zod contracts, session revisions and action identities; native views remain separate from the desktop component library.

The gateway is off at startup. Short-lived one-use pairing grants create revocable device tokens whose hashes are persisted atomically. HTTP uses Bearer authentication; an alternative WebSocket endpoint authenticates in a bounded first frame. The mobile app uses a bounded NDJSON HTTP event stream with redirects rejected because native WebSockets can follow redirects before exposing the connection to JavaScript. Public connections require TLS. Snapshot/event delivery subscribes before reading state and buffers intervening events; reconnect replaces the client view with authoritative state. The phone stores credentials in SecureStore, rejects external plaintext, suspends streams in the background and never replays mutations. [Mobile setup](mobile.md) describes the execution model, limits and deployment options.

## Idle provider inspection shutdown

Completed Codex metadata and bootstrap inspections close stdin and allow up to 300 ms for the actual process close event before the existing forced cleanup. This applies only to healthy RPC peers without pending requests. Active cancellation, Stop and run finalization keep their process-tree cleanup. Neither a successful termination command nor a missing PID substitutes for confirmed closure.

## Provider account usage

D65 adds a host-scoped, read-only `provider-usage` request with shared Zod contracts. A dedicated service coalesces concurrent requests and caches successful Claude observations for four minutes and Codex observations for 30 seconds. Unsuccessful reads back off from five minutes to one hour, report their next eligible check and reset the delay after success. Manual and post-turn refreshes share this host gate. It runs independently of session execution and joins the host's existing bounded probe lifecycle. Account metadata and quota observations stay in memory; they are not written to session history or offline computer snapshots.

Codex uses an owned app-server process for `initialize`, `account/read` with token refresh disabled, and `account/rateLimits/read`. Claude uses an owned, non-persistent control connection for `initialize` and `get_usage` with `skip_behaviors: true`, disabled hooks, strict empty MCP configuration and no tools. Neither path sends a user message or starts a model turn. Nesvo uses each installed provider's existing login without reading credential stores directly. Deadlines, bounded output, cancellation and confirmed process cleanup apply to both readers. Claude's usage command is experimental; unsupported versions return an explicit unavailable result.

Only reported windows become percentages. Native durations, reset timestamps, account labels and plans are preserved; malformed or unavailable data never becomes zero usage. Provider permission is retained only when explicitly reported and never inferred from a percentage or reset time. Usage data does not grant or block session permissions. Additional billing/credit balances are outside this stage.

Electron validates and routes the request to Local or the selected connected computer. An offline request fails without reconnecting automatically. Renderer observations are keyed by host, with generation checks against late responses. The visible application refreshes the selected computer every two minutes, after a finished turn and on demand, subject to the host cache. The rail shows remaining allowance in the most-used reported window. Details show every window, last check and reset time; observations become stale after five minutes, disconnection or a passed reset. Expiry never fabricates a refreshed allowance. The account icon opens both providers and remains available in compact layouts.

## Turn usage

Each agent message carries `usage`, a `turnUsage` record with input, output and cached input tokens, cost in US dollars, `durationMs` and `source`. Every field is `null` when the provider did not report it and `source` is `provider-report` only when at least one field was reported; nothing is estimated and an unreported value is never zero. Messages saved before this record existed read back as `null`. The host copies the value from the adapter result onto the agent message when the run is finalized, so it is stored in the session document and survives restarts. A failed or stopped run keeps the usage only when the provider delivered its final result frame (Claude) or turn completion (Codex); a run that ended without one keeps `null`, including tokens received earlier in the turn.

`inputTokens` counts all input tokens of the turn and `cachedInputTokens` the part served from cache. Claude Code reports cache reads and cache writes separately from `input_tokens`, so the adapter adds them to form `inputTokens`. Claude's final `result` frame supplies `usage`, `total_cost_usd` and `duration_ms`; the dollar amount is the provider's own estimate of API-equivalent cost and is not a billed amount on a subscription account.

Codex app-server 0.167.0 sends `thread/tokenUsage/updated` notifications during a turn with a `last` and a cumulative `total` breakdown, and `turn/completed` carries the turn's `durationMs`. The adapter takes the change in `total` from just before the turn's first update to its last update, which is the turn's own consumption even on a resumed thread. The protocol reports no dollar cost for a turn, so Codex `costUsd` stays `null`; a separate thread usage request with credit and dollar estimates exists but is not used.

## Process boundaries

```text
React renderer (plain TypeScript, base shadcn)
  |
  | window.nesvo: session commands, health, subscriptions
  v
Sandboxed preload (narrow typed API)
  |
  | Electron IPC, caller checked by main
  v
Electron main (window and host process lifetime)
  |
  | utilityProcess messages, Zod commands/responses/events
  v
Node host (Effect scope and services)
  |
  v
SQLite (identity and versioned conversation snapshots)

Node host -> owned Claude Code CLI -> normalized text/activity/result
Node host -> owned Codex app-server over stdio -> text/activity/approval/result

Standalone Node entry -> JSONL transport -> the same host service
```

Bun installs dependencies, runs scripts and builds the standalone host. It is not a runtime requirement for a packaged desktop.
Electron provides its own embedded Node for the utility process. The standalone host uses Node 24.
The host imports no Electron code; its desktop transport adapter belongs to the desktop main process.

Effect owns the database, session service, capability probes and request stream lifetime. Finalizers cancel owned provider work before closing SQLite. In the embedded/stdio host, they run on normal shutdown and owner transport completion. The independent host below supplies a process-owned request stream instead of an individual client's stream.
SQLite uses a versioned bootstrap and transaction, WAL, foreign keys and a busy timeout. An unsupported newer schema is rejected before migration.
Schema v4 preserves host identity, provider threads and conversation snapshots. Earlier migrations retain provider modes and pending approvals; v4 adds parent/run relationships, worker scopes, delegation capability and proposals. Existing conversations default to delegation disabled. A snapshot atomically contains the user message, agent message, run ID, provider ID, state and revision. Accepting a worker commits both parent and child snapshots in one transaction before launch. Text is flushed in short batches and at termination. If final persistence fails, a bounded retry and unsaved snapshots prevent new messages from overwriting results. Restart marks unfinished runs and proposals interrupted and invalidates pending operation approvals.
SQLite remains on Node's built-in driver. Drizzle integration waits for stable support for this driver; no release candidate is installed. Database types would not replace public Zod request validation.

Schema v6 adds durable tool activity to session snapshots. Each item is identified by its run and native provider item ID, with normalized kind, title, paths, status and timestamps. Output and details are bounded; private reasoning and raw provider payloads are not persisted as activity. Text and activity updates share the existing batched persistence path. Terminal updates cannot regress to running. Stop and restart finalize unfinished items without inventing successful completion, and older sessions default to empty activity and unknown completion timestamps.

Activity retains the latest 100 entries per run and 300 per session. Run-specific markers identify omitted history, including wholly evicted runs; late updates cannot reinsert evicted entries during an active run. Output is limited to its last 4,000 characters, details to 2,000, and paths to ten. Known credential patterns and terminal control sequences are filtered; this is not a guarantee that arbitrary tool output contains no sensitive data.

## Independent host connections

D63/R1 adds a Linux daemon with one existing host runtime behind a process-owned request queue. Clients attach through a private Unix socket and a version/identity handshake. Client EOF removes reply routing and subscriptions; only daemon shutdown ends the owner queue and triggers provider cleanup. Transport request IDs are mapped per connection; semantic message/decision IDs are preserved. Pending operations keep their runtime budget after their client disconnects.

The same OS user owns the private socket, repositories, provider logins and data. No TCP port is opened. The bridge uses JSONL and never reconnects or replays commands automatically. The stable instance ID detects a mismatched database; it is not an authentication credential. Full startup, reconnect and resource-limit behavior is documented in [independent-host.md](independent-host.md).

D64/R2 and R3 add Computers in Electron main. Local keeps its owned utility process; each remote connection owns an OpenSSH child attached to the Linux bridge. OpenSSH requires an existing verified host key and public-key authentication. The renderer cannot supply shell commands. The daemon instance ID is pinned after its first verified handshake and persisted before the connection becomes available. [Linux host setup](ssh-host.md) describes installation and the generated systemd user unit.

Every desktop session and review carries a host ID separately from its native record ID. IPC validates that target, and command routing never depends on the selected conversation. Sidebar and Inbox aggregate all computers; workers, files, skills and decisions remain on the originating host. Local is the default for a new session. Provider availability is inspected independently per connected host.

Connection setup subscribes before fetching both authoritative snapshots, buffers intervening events and merges by revision before enabling commands. Generation checks reject late responses from replaced connections. Disconnect invalidates that connection without rewriting run statuses or replaying requests. The UI labels offline work as last known and disables mutations and live reads while retaining saved conversations and diffs.

Remote configuration and the bounded offline cache use separate atomic files under the desktop profile. Configuration records connection parameters and the host identity, never private key bytes or provider credentials. Cache save failures are visible but cannot prevent disconnection or removal. Reopening restores saved remote histories as disconnected; explicit Connect reloads the host's current state. Removing a computer deletes its desktop registration and cache, not its remote data or running service. App shutdown terminates Local work and closes remote SSH children only.

## Restart and recovery

D62 adds an exclusive owner for each host data directory. Electron takes its single-instance lock before creating a host. The host independently holds an exclusive transaction on a separate ownership.sqlite connection before opening the application database or reconciling sessions. The operating system releases this ownership when the process closes or dies; no stale PID file is deleted and no unknown process is killed. Effect keeps ownership until provider cleanup and database closure finish.

Reloading the renderer does not stop the host or replay requests. The renderer subscribes before loading authoritative history and merges by revision; review actions remain disabled while session or result loading failed or remains pending. Local navigation preferences restore the last session/Inbox and saved review ID/file. Missing or invalid preferences fall back safely. They do not store run status, permissions, commands or review decisions. Unsent drafts remain transient.

Optional interruption metadata records the run ID, reason and time on the session and agent message. Controlled host shutdown, unfinished records found at startup and unexpected provider disconnection have distinct reasons. Explicit provider errors remain failures, and operator Stop remains stopped. Partial output and prior interruption causes remain in history after a new turn. Incomplete outcomes never create successful reviews.

Startup reconciles unfinished sessions, activities, expired operation approvals and parent/worker proposals in one transaction. New proposals preserve the exact child run ID; legacy matching is conservative. A durably completed worker remains completed even when its parent did not receive the terminal event before shutdown. A resumed parent references saved reviews from its latest delegation group with actual children, even if that parent run never produced a review. Older parent dependencies are a fallback only when the latest group created no child. Current child review versions and writable fingerprints still participate in acceptance checks.

Continuation requires a new operator message and keeps the existing provider thread. The prompt explains the previous unconfirmed outcome and available worker state so that the provider can inspect current files before doing more work. Opening the app or pressing Continue conversation never sends a provider task. Already committed messages, worker decisions and review decisions are not replayed. Stable IDs and transactional correction preparation make retries idempotent, including after restart.

## Scheduled jobs

D68 adds host-owned scheduled jobs. Schema version 7 stores definitions in `scheduled_jobs` and their history in `scheduled_job_runs`, inside the same bootstrap transaction as earlier migrations; a failed migration rolls back completely and keeps the previous version. Runs are unique per job and scheduled time, manual runs per request ID, and deleting a job removes only its runs. Sessions gain nullable `scheduled_job_id` and `scheduled_job_run_id` links that become null when the job or run disappears, so sessions and reviews remain ordinary history. Each job keeps its latest 100 finished runs, ordered by recording time. A host accepts at most 20 jobs.

`ScheduledJobService` runs in the host scope, including the Linux daemon. One timer is armed for the earliest next run and capped at 2^31−1 ms; every change re-arms it, and the clock is injectable. A tick collapses every missed occurrence of a due job into a single decision with the shared schedule module. An occurrence more than two minutes late becomes one `skipped/missed` record; there is no catch-up. Otherwise an active run of the same job records `skipped/overlap`, and a busy host records `skipped/busy`. The host is busy when the session service would refuse a new message (closing, an active group or a review decision in progress) or when an operator command arrived in the last ten minutes. Otherwise the run is claimed as `starting` in the same transaction that advances the next run time, and the launcher port is called only after commit. A launch refused as busy becomes `skipped/busy`.

Startup marks `starting` and `running` runs `interrupted` with reason `restart` inside the session recovery transaction and never relaunches them; the first tick then records anything missed while the host was down. Saving a changed schedule or time zone, or reactivating a job, computes the next run from the current time, so a paused job never accumulates missed runs. Saves, activation changes and deletions compare the expected revision. Run now records a manual run only when the host is not busy and the job has no active run; otherwise it returns a busy error without a record. Health reports the `scheduled-jobs` capability.

The session launcher in `apps/host/src/scheduled-jobs/launcher.ts` turns a claimed run into one ordinary session on the same host, through the session service rather than IPC. It first resolves a set folder in a short-lived child process with a five-second bound, so a hung network folder cannot block the host at an unattended time, and applies the create-session rules: an empty folder gets a fresh workspace, a missing or inaccessible one fails the run as `failed/folder` without a provider process. Settings that the create-session schema rejects, such as an unsupported Claude model, fail the run as `failed/catalog`. A Codex effort is confirmed against the reported catalog as for an interactive session; a withdrawn effort fails the run as `failed/catalog` before any thread or turn, while a Codex that is not ready fails it as `failed`. A Codex model without an effort is not checked in advance, as in an interactive session, so a withdrawn model fails during the turn. If the host became busy during these checks, or an operator command arrived within the idle window before a scheduled start, the run is `skipped/busy`. The session uses exactly the job's provider, model, effort and read-only mode, and the title is the job name followed by the local date and time of the scheduled occurrence (or of the manual start) in the job's time zone.

The session service takes an internal `origin` that is not part of the public create-session request, so Electron IPC, SSH and the mobile gateway still reject an `origin` field through the strict schema. The origin is a discriminated union: `operator` for interactive sessions and `scheduled-job` with the job and run IDs, which are stored in the session links and exposed as `scheduledJobId` and `scheduledJobRunId` in the session projection. The link columns are authoritative on read, so a deleted job or run also clears the projection. A scheduled-job origin always disables delegation, so Codex registers no worker tool. Provider arguments, permission modes, sandbox and approval policy are those of an interactive read-only session; no new flags reach either adapter.

The prompt is sent as the first message with a message ID derived from the run ID, so a repeated send in the same process returns the existing run. The run records its session and session run as `running`, then follows the session: a completed turn records `completed` with its review, which reaches the Inbox as an ordinary result acceptance; operator Stop records `stopped`; a host shutdown records `interrupted/restart`; a failed turn records `failed`. Operation approvals during a Codex run use the existing rows and count against the deadline. Each run has a host-owned deadline of `timeoutMinutes` from its start that calls the same Stop path as the operator and records `failed/timeout`; process-tree cleanup is the session's own, so on Windows descendants already orphaned from the provider's tree are not covered. A crash between session creation and the first message leaves the empty session, and startup marks the run `interrupted`; it is never sent later. If the first message is refused after the session was created, the empty session also stays and the run records `failed` or `skipped/busy` without a session link. If recording the started run fails, the deadline and the outcome tracking still apply. Manual Run now uses the same path. Sessions created by scheduled jobs are kept; deleting them together with old runs is not implemented yet.

The launcher checks the provider account limit before it resolves a folder or creates a session. It calls `ProviderUsageService.read()` for the job's provider on this host, so the existing cache and failure back-off apply, no new probe exists and no model turn is started. Only an observation with status `ready` that reports a window at or above 100% used with a reset time in the future stops a run. The run is recorded `unavailable/limit` with `resetAt` set to the latest reset among such windows, never has a session and does not count as a failure. Unavailable, stale, unsupported or failed observations, such as Claude Code's experimental usage read, launch the run: the host does not guess an allowance from any other percentage and never infers recovery from one (D65). A reset time already in the past does not stop a run, and neither does an observation whose provider reports `ordinaryUsageAllowed: true`, because that explicit signal outranks any percentage. The observation is the one the usage service cached, so it can be up to four minutes old for Claude Code and thirty seconds for Codex. Codex reports limits per group and the host does not map a job's model to a group, so an exhausted window in any reported group holds every Codex job until its reset; Claude Code limit windows are handled the same way.

A known reset time is remembered per provider in the launcher until it passes. Further runs of any job on that provider before then are recorded `unavailable/limit` with the same `resetAt` without another usage read. The memory is in-process only, so after a restart the first run reads usage again. During a run, Claude Code's stream event `rate_limit_event` with status `rejected` marks the run outcome as a limit: the session keeps its failed state and failure text, the scheduled run becomes `unavailable/limit` with the event's reset time when it reports one, and no review is created because only completed results reach the Inbox. Codex has no recognised in-run limit error shape, so for Codex only the pre-start check applies and an in-run limit still shows as `failed`. The repository holds no captured real Claude limit rejection; the `rejected` event shape is the one the adapter already parsed and is exercised only by a fixture, so it needs confirmation against a real account limit.

A scheduled job definition carries an optional `pipeline` of `{ name, specPath }`, null by default so stored definitions and cached projections still parse, and a run records an optional `pipelineRunId`. When a pipeline is set the prompt may stay empty because the spec supplies the task; a job without a pipeline still needs a prompt. When a pipeline is set the launcher keeps the limit gate, the folder check, the busy refusal and the operator-idle rule, then starts a pipeline task in process through the same path as `start-pipeline-task` instead of creating a session and sending the prompt, which is ignored. The task uses the job's provider, model and effort in `read-only` mode, `worktree` isolation when the folder is the top level of a Git repository and no isolation otherwise, and the other provider with its default model as the gate. A missing pipeline, spec or invalid definition ends the run as `failed` with the `catalog` reason, and a busy project root or host ends it as `skipped` with the `busy` reason. The run row records the author `sessionId` and the `pipelineRunId`; `runId` stays empty because the session turns belong to the pipeline run. The run finishes when the pipeline run settles: `passed` is `completed`, `stopped` is `stopped`, `interrupted` is `interrupted`, and a failed or rejected run is `failed`. The launcher reads the stored pipeline run once a second for that. The job timeout stops the pipeline run, which ends the author turn, and records `failed` with the `timeout` reason. A pipeline run interrupted while the host is running leaves the job run `interrupted` without a reason, because the operator can still resume it. A scheduled pipeline checks the provider limit gate only before the start; a limit reached during the run is not remembered. The pipeline's command and action steps run unattended with the repository's definitions, in the task worktree when the folder is a Git repository and in the project folder otherwise. Schema version 9 adds the nullable `pipeline` JSON column to `scheduled_jobs` and the nullable `pipeline_run_id` column to `scheduled_job_runs`, which becomes null when the pipeline run is pruned.

## Ownership

| Area                 | Owns                                                 | Must not own                                           |
| -------------------- | ---------------------------------------------------- | ------------------------------------------------------ |
| contracts            | Zod schemas, inferred data types, narrow desktop API | Runtime services, UI state, provider implementations   |
| desktop main/preload | Window, IPC boundary, child process lifetime         | Domain decisions or credentials in renderer            |
| renderer             | Presentation and operator interaction                | Effect, filesystem, process control or database access |
| host                 | Authoritative state, resources and provider adapters | UI components or Electron dependency                   |

Requests carry unique correlation IDs. Session events are separate from responses and carry monotonically increasing revisions. The renderer subscribes before loading history and merges only newer snapshots. Send acknowledges promptly; the main request loop never waits for model completion, so health, Stop and shutdown remain responsive. Duplicate message IDs do not launch a second turn.
The renderer cannot send arbitrary host requests. It can only call the API exposed by preload.
Main denies external window creation, renderer navigation and permission requests.

## Growth by domain

Introduce sessions, delegation, review and skills modules as their stages are accepted.
Each host module keeps its domain rules, application service and adapters close together. Simple rules remain plain TypeScript; Effect composes I/O and lifetime.
Do not create a second schema system: public messages use the shared Zod contracts.

The renderer grows with a light feature-sliced structure:

```text
app -> pages/widgets -> features -> entities -> shared
```

The workspace composes the activity and result widgets through conversation slots. A lazy-loaded saved-diff widget renders the selected review ID with @pierre/diffs. Its virtualized viewer receives only the saved patch, never current filesystem content. File selection, line wrapping, raw-patch fallback and metadata-only changes stay within that exact version. On wide windows it docks beside the conversation; compact windows hide the covered conversation from keyboard navigation until the panel closes. Accept/correct commands remain in the result and inbox, bound to their existing review revisions. No live working-tree diff or merge is introduced.

Create only the layers needed by actual features. Imports move downward; cross-slice imports use public entry points.

## Visible delegation

New root Codex sessions register the native `nesvo_delegate` dynamic tool at thread creation regardless of read-only or supervised permissions. Creation accepts the legacy role field for compatibility but always starts a standalone session; the first valid worker proposal makes its role orchestrator. Intent is expressed through the task and tool use, not keyword detection or a role picker. Its input schema is generated from the shared Zod contract. Existing threads retain their identity and recorded capability without silent upgrades. Workers receive no delegation tool.

```text
Codex parent -> native tool call -> validated worker proposals
                                    |
React decisions -> typed preload -> host decide-delegation
                                    |
                             persist parent + child
                                    |
                             launch owned worker
                                    |
                         child status/text/error -> parent tool result
```

The adapter validates the tool, namespace, call ID, thread and turn. The service limits all calls within one parent run to two proposals. Each proposal shows task, scope, relative directory, provider, model and mode. Only a matching session/run/proposal decision can accept or decline it. Acceptance creates and launches the visible child; stale decisions fail. Child results remain associated with their proposal and session IDs, including declined, stopped and failed outcomes.

Delegation never changes the parent's selected permissions. Workers use the existing Codex modes or Claude's read-only capabilities and cannot create children. Directories are canonicalized, checked inside the parent's root and revalidated at acceptance. If either worker can write, its directory must not overlap another worker's directory. A supervised parent can delegate read-only workers only; proposed writable children are rejected before publication and rechecked at acceptance. This avoids mixing parent and child edits in the parent's review snapshot before workspace isolation exists. Assignment text is not a security boundary; provider sandboxes still define actual permissions. Read-only workers can share a directory.

Stopping a child leaves its sibling and parent active. Stopping the parent cancels pending proposals and active children. Parent termination waits for child cleanup; shutdown cancels the whole group. Restart retains relationships and marks unfinished work interrupted without launching it. Only one group may be active globally. A ten-minute native parent deadline includes operator waiting and child work; each conversation retains at most 100 proposals. Worker summaries passed back to the parent are capped at 12,000 characters with explicit truncation, while complete conversations stay available in the UI.

The workspace page composes conversation and delegation widgets through a React slot. Sidebar rows expose the parent/child tree, child views link back to their parent, and session details explain the actual delegation capability. No Effect or process API enters the renderer.

## Pipelines

Pipelines run a task through ordered steps whose definitions live in files on the computer that runs the task; the host database will hold only run state, results and metrics. `packages/contracts/src/pipelines/` owns the shared shapes: step definitions (`command`, `agent`, `human`, `action`; phases `plan`, `pre-done`, `pre-push`; timeouts from 1 s to 4 h; at most five retries; `needs` limited to `browser` and `env:NAME`), pipeline definitions with 1–32 unique step names, task specs, definition sources with content hashes, catalog issues, step results and evidence, the structured agent verdict, run and step records, run pages and metrics. Human steps never retry and only agent steps name a skill; an agent step may omit instructions only when it names one. Gate results report `pass`, `fail` or `blocked`; actions report `done`, `error` or `blocked`. The agent verdict needs at least one evidence reference and converts to a JSON Schema without references for provider structured output.

Sixteen host commands cover definitions (list, validate, save, delete), task start and manual step runs, run history and detail, gate decisions (`accept`, `reject`, `fix`), recorded skips, the resolution of an `uncertain` step (`mark-done`, `run-again`), resume, Stop, worktree removal, bounded evidence reads and metrics. `pipeline-run-changed` and `pipeline-step-changed` carry revisioned records; main drops a record whose revision is not newer than the last one seen and resets that memory on every synchronization. Renderer access goes through `window.nesvo.pipelines`, each method taking the desktop host ID first; preload and main validate with the shared schemas and main adds the host ID. `start-pipeline-task` waits up to 60 seconds, the other commands 15 seconds.

Sessions gain nullable `pipelineRunId` and `pipelineStepId`, messages a nullable `origin`, and reviews a `reject` decision with a `rejected` status. The defaults keep stored sessions and the offline computer cache readable, but a newer host sends the new fields, so an SSH host, the desktop and the mobile client must be updated together. `create-session` accepts an optional worktree isolation request.

Schema version 8 adds `pipeline_runs` and `pipeline_steps` in the same bootstrap transaction as earlier migrations; a failed migration rolls back completely and keeps version 7. Each row keeps the validated JSON record in `document` next to the columns used for lookup, and both tables use a revision compare-and-swap, so a stale writer changes nothing. A run records its working directory and, separately, the source project root of the operator, which differs when the run is isolated in a worktree. Step rows are unique per run, step index and attempt, and deleting a run removes its steps. Sessions gain nullable `pipeline_run_id` and `pipeline_step_id` columns that become null when the run or step disappears; the session store writes them from the session document and drops a link whose target no longer exists. Runs page by update time, a project keeps its latest 100 finished runs, and interrupted or `needs-attention` runs are never pruned.

A pending step moves to `running` through a store helper that commits the state and its start time in its own transaction, and refuses to run inside another transaction or for a finished run, before the runner starts the process, so a crash leaves a record of the intent. A retry is a new attempt row, never a rewrite of an earlier attempt. At startup, inside the session recovery transaction and with plain SQL updates that do not parse stored documents, every `running` step is closed and runs in `planning`, `implementing`, `checking` or `fixing` become `interrupted`. A `running` action step becomes `uncertain` instead of `interrupted`, because its external effect may have happened, and its run becomes `needs-attention` with the reason "External action may have run." Runs waiting for a human keep their state. Nothing is replayed.

The host advertises the `pipelines` capability. Until the engine is complete, it answers every pipeline command it does not serve yet (worktree removal and metrics), and any isolated `create-session`, with `unavailable`. Main refuses pipeline calls locally for computers whose host does not advertise the capability, except the two definition reads, which every host with the definition loader answers. The mobile gateway ignores pipeline events.

### Pipeline runner

`apps/host/src/pipelines/runner.ts` is a host service with ports for the run store, the definition reader, a clock, event emission, the evidence store, a step executor per step type and an optional author port that a later stage implements for session-bound runs. `advanceRun(runId)` is the only operation that moves a run. Every caller first writes its intent to the store (a manual start inserts a `pending` run, Stop records the run as `stopped`, a finished step records its result, startup records a `pending` manual run that never began as `interrupted`) and then calls `advanceRun`. A pass reads the run and its steps from the database, decides one move, performs it and repeats until the move is to wait; nothing about the progress of a run is kept in memory between passes. Passes for one run are serialized: a call that arrives while a pass is scheduled or running only marks the run for one more pass, so any number of calls collapses into at most one extra pass, while different runs never wait for each other. The decision is a pure function of the run and step records.

The moves follow the run status. A `pending` manual run enters `checking` for its requested phase, and one `pending` step row per step of that phase is written in the same transaction. In `checking`, the pass evaluates the graph of the phase (`nextMove`, exported and pure). The outcome of a step comes from its latest attempt: `passed`, `done` and `skipped` are success, so a `human` or `agent` step skipped in a manual run routes as passed; `failed` and `error` are failure; `unreached` means the step will not run; any other state is no outcome yet. An edge has fired when its source has an outcome that matches its condition (`on any` matches both), is dead when the source has the other outcome or is `unreached`, and is open otherwise. A `pending` step is ready when every incoming edge has fired and every step that precedes it through any chain of edges has an outcome, so a step with several incoming edges waits for all of them, a step after an operator-skipped step still waits for the steps before that one, and a step without incoming edges is ready as soon as its phase begins. The moves are, in this order: a `blocked` step needs attention with its reason at once, while running steps finish and record their results; the first ready step in pipeline order that the concurrency rule allows starts, and the pass repeats, so several steps can start in one pass; in an explicit graph a `pending` step with a dead incoming edge becomes `unreached` with a reason taken from the first dead edge in the pipeline order of its source, `Not reached: "<step>" failed`, `Not reached: "<step>" passed` (an `on failure` edge from a step that succeeded) or `Not reached: "<step>" was not reached`, and its own outgoing edges die in turn; an `unreached` step none of whose incoming edges is dead any more, because resume retries its failed source or the operator skipped that source, gets a new `pending` attempt; a step that is `running`, `awaiting-human` or `uncertain`, or a ready step held back, means wait; an `interrupted` step needs attention so that resume can run it again, which only a restart during parallel steps can leave behind while the run is `checking`. When nothing is left to do the phase has settled: if any step is `failed` or `error`, the first one in pipeline order applies its failure (`on_fail: stop` fails the run, `fix` needs attention with the failure), otherwise the phase passed and a manual run is `passed`. An `on failure` branch therefore runs before the failure takes effect and never turns it into a pass. The concurrency rule lets at most four `command` and `action` steps of a run run at once and starts an `agent` or `human` step only while no other `agent` or `human` step of the run is `running` or `awaiting-human`, because the host runs one session at a time and a gate binds to one result version. A `human` step and an `action` step never run at the same time either: a restart leaves a running action `uncertain` and keeps a run that waits for a human as it is, so an action in flight beside a gate could neither be resolved nor safely run again. While the run waits for a human decision, running steps finish but no new step starts. A pipeline without `edges` is the implicit chain and behaves as before graphs: any active step means wait, one step runs at a time in pipeline order, and the first failure ends the phase without starting later steps and without `unreached` rows. A phase is never begun and an author turn is never sent while a step of the run is still `running`, so a gate sent back to fix while a parallel command still runs sends its correction and re-runs the phase only after that command ended, and when a run reaches a terminal status, including `rejected`, the runner aborts its steps that are still running. `currentStepIndex` is set when a step starts, to the lowest index among the steps then running or waiting for a human. A session-bound run in `pending`, `planning`, `implementing` or `fixing` moves through the author port described under Pipeline tasks and needs attention with "No author session on this host" while none is registered. `awaiting-human`, `needs-attention` and terminal runs wait. A pass never starts an `uncertain`, `interrupted`, `blocked`, `failed` or `error` step.

Before a step starts, its `needs` are checked: a missing `env:NAME` variable or a `browser` need makes the step `blocked` with a readable reason and no process. Otherwise the store commits the step as `running` with its start time in its own transaction, and only then does the executor start, so a crash always leaves the intent recorded. The executor's result is written to the step record in one transaction as soon as it ends, with the step state mirroring the verdict, and every write emits `pipeline-run-changed` or `pipeline-step-changed` with the incremented revision. Executors are registered per step type when the host composes the runner; `agent` steps follow Agent steps and `human` steps Human gates below. Only one manual run per project root is active at a time; a second start answers `busy`. Each running step has its own abort signal. Stop records the run as `stopped`, aborts every running process and records those steps as `interrupted`; shutdown waits for all of them. Host shutdown aborts running processes without writing a result, so the next startup closes those steps through the same store recovery as a crash: a command step becomes `interrupted` and an action step `uncertain`. Each running step process records its process ID, its spawn time and, on Linux, its kernel start time in its evidence folder until it ends; after a crash the next startup stops the process group of every record whose identity still matches, so a step that outlived its host cannot keep editing the project. Linux compares the exact start time; macOS and other POSIX systems compare the creation time reported by `ps` with the recorded spawn time within 3 seconds, so a reused process ID is skipped; `ps` reports local time, so a process started during the repeated hour of a daylight-saving change can be missed and is then left alone. On Windows the host's process job ends the step shell together with a crashed host, but processes the shell started leave that job and no record reaches them; containing them needs a native job object, so startup leaves them alone. After that recovery the host calls `advanceRun` for every unfinished run; the pass reconciles and starts nothing.

`command` and `action` steps run their body in the run directory through `sh -c` on POSIX and, on Windows, as a temporary batch script started with `cmd.exe /d /s /c` that begins with `@echo off` and `chcp 65001`, so every line of a multi-line body runs and the shell's own output is UTF-8 (other programs keep their own encoding); bodies follow batch-file rules, so `%%` is a literal `%`, an undefined `%NAME%` expands to nothing and loop variables are written `%%i`; the script folder is removed when the process ends and a crash can leave it in the temporary directory. They run in their own process group with the step timeout, descendant tracking on Linux and a bounded tail of 4 MiB for the combined output. The process uses the host environment without any variable whose name ends in `KEY`, `TOKEN`, `SECRET` or `PASSWORD` (alone or after `_`) and without inherited `NESVO_` variables, except variables the step names in `needs: [env:NAME]`. The runner adds `NESVO_RUN_ID`, `NESVO_STEP_NAME`, `NESVO_PHASE`, `NESVO_SPEC_PATH`, `NESVO_PROJECT_ROOT` (the operator's project, which differs from the working directory when the run is isolated), `CI=1`, `GIT_TERMINAL_PROMPT=0` and `NESVO_OUTPUT_<STEP>_<KEY>` in upper snake case for every output of a step that precedes it in the phase graph through any chain of edges, and of every step of an earlier phase, using their latest attempts; a step running in parallel never contributes, so the variables do not depend on timing. On the implicit chain of a pipeline that lists its steps in phase order this is every earlier step as before; earlier phases now count by phase rather than by list position. When two outputs map to the same name, the step listed first wins. A command passes with exit code 0 and otherwise fails with the exit code, signal or timeout and the last part of its output in the summary. An action reports `done` or `error` the same way, and the last stdout line that is a JSON object becomes its outputs when it has at most 16 keys with valid names that the secret filter leaves unchanged and text values of at most 4000 characters; otherwise the outputs stay empty and the summary says why. The step executors still use their own process helper with the same rules (`apps/host/src/pipelines/steps/process.ts`, which also reports the process ID for crash cleanup); moving them onto the shared owned-process helper is a separate change.

`apps/host/src/pipelines/evidence.ts` keeps evidence in `<dataDir>/pipeline-evidence/<runId>/<stepIndex>-<name>/` with folders created as 0700 and files as 0600, at most 4 MiB per step attempt, keeping the tail when a log is longer. File names are fixed by the executor (`attempt-<n>.log`). Before any write, the summary, evidence labels and text and output values pass through one filter, once in the executor with the step's secret values and again in the runner for every executor result, that removes terminal control sequences, redacts `sk-`, `sk-ant-`, `ghp_`, `github_pat_` and `xox*` tokens that do not continue a word, Bearer values and `key|token|password|secret` assignments, and, in the executor, replaces the value of every secret-named variable passed through `needs` when it has at least eight characters. `read-pipeline-evidence` accepts only a recorded file name inside the step folder, refuses links and special files, answers `missing` for an absent file and returns a text preview of at most 256 KiB, the tail of a longer file marked `too-large`, or `binary`, with at most eight reads in flight. `run-pipeline-steps` validates the directory, reads the task spec (relative paths resolve against the directory) and its pipeline, refuses invalid definitions with their issues and a phase without steps, records the directory as the project root and answers with the `pending` run while the first pass runs in the background. `get-pipeline-run`, `list-pipeline-runs` and `stop-pipeline-run` answer from the store. Evidence folders of pruned runs remain until a later cleanup removes them.

### Pipeline definitions

`apps/host/src/pipelines/definitions.ts` reads definitions from the filesystem of the host that serves the request, so a remote computer reads its own files. The global root is `~/.agents/pipelines` of the host user; the project root is `<project>/.agents/pipelines`, where the project is the nearest ancestor of the request directory that contains `.git`, or the directory itself when none does. Definitions above a directory without `.git` are never read. Each root holds `steps/*.md` and `pipelines/*.md`; task specs are any Markdown file inside the project, and the catalog also lists `<project>/.agents/tasks/*.md`. When the project root resolves to the global folder it is read once. `NESVO_PIPELINES_HOME` replaces the global root only when `NESVO_TEST_MODE=1` is also set.

Names resolve project over global: a project step or pipeline with a global name replaces it and carries a note naming the overridden file, which is not an issue. A pipeline step name always resolves through the same merged step set. An invalid project file still shadows the global definition, so a pipeline using that name reports the step as invalid instead of silently falling back. Two files with one name inside a root keep the first file by name and report the second.

Files are read only when they are regular files: the folder is canonicalized, the file itself must not be a symbolic link, it is opened without following links, and its identity is compared before and after the read. A file is at most 64 KiB of UTF-8 and its frontmatter at most 32 KiB through the same bounded YAML parser as the skill library (no anchors, aliases or tags, depth 12, 512 nodes). The anchor check is textual, so a frontmatter value containing `&`, `*` or `!` after a space must be quoted. A root reads at most 200 step and 100 pipeline files, the project at most 100 task specs, with eight concurrent reads and one 3 s deadline for the whole inventory; reaching the deadline or Stop fails the request instead of returning a partial catalog. Every file problem becomes an issue with the canonical path, the frontmatter line when it is known and a plain message, for example an unknown field with a suggested name, an enum value outside its options or a missing referenced step; issues beyond 200 collapse into one summary issue.

Each definition source carries `contentHash`, the SHA-256 of the raw file bytes. It is stable while the bytes are unchanged and is what later stages pin into runs and compare before writing a file. Validation adds warnings for a pipeline without a gate, for a `fix` step with no retries, for a `command` or `action` step that declares `effect: external` (an optional field, default `local`, valid only on those two types) and, whatever a step declares, one whose body mentions `git push`, `gh pr`, `curl` or `wget` with no `human` step before it in phase order. `list-pipeline-definitions` and `validate-pipeline-definitions` return the same catalog, run beside the other inspections with at most two in flight and are cancelled by host shutdown. `loadSpec` reads one task spec that must lie inside the project, and `resolvePipeline` picks a pipeline from a catalog for a later run.

A pipeline file may also carry two optional fields. `edges` is a list of at most 64 strings of 3 to 160 characters, each `<from> -> <to>` with an optional `on success`, `on failure` or `on any`; `on success` is the default and whitespace around the arrow is free. One string per edge keeps a full graph far below the YAML node limit. `layout` maps a step name to `[x, y]` integers between -100000 and 100000, at most 32 entries; it is presentation for the editor and nothing that runs steps reads it, and `layout: {}` is valid. Without `edges` the pipeline is the implicit chain: inside each phase, consecutive steps in `steps` order are joined by `on success` edges, so every pipeline written before graphs keeps its meaning without an edit. With `edges`, even `[]`, the graph is explicit and a step without an incoming edge starts when its phase begins. Edges stay inside one phase; phases keep their order and a step with several incoming edges waits for all of them. Every resolved pipeline carries `graph: { explicit, edges: [{ from, to, when }] }` next to the original `edges` and `layout`. A stored run whose pinned pipeline predates graphs has no `graph`; parsing it fills in the implicit chain of its pinned steps rather than an empty edge list, so an older unfinished run keeps its step order. The runner records a step that a dead path skips as `unreached`, with its reason in `skip`, as described under Pipeline runner.

`packages/contracts/src/pipelines/graph.ts` holds the graph rules once for the host loader and writer, the definition commands and the desktop editor. It performs no I/O and imports nothing from the host. `resolveGraph` takes the pipeline name, `steps`, `edges` and `layout` with the step definitions by name and returns the resolved graph and issues that carry a rule ID, severity, field, message, the steps involved and the edge position; the caller adds the file path and the line of `edges:` or `layout:`. The module also exports `parseEdge`, `formatEdge`, `implicitEdges`, `incoming`, `outgoing`, `ancestors`, `topologicalOrder` and `phaseSources` for the engine and the editor, and `checkGraphList` for the checks that need no step definitions. The gate script that runs the same files outside Nesvo mirrors the error rules E1 to E9 and the layout warning W1 with the same messages; the other warnings exist only in Nesvo.

Graph errors exclude the pipeline from the catalog like a missing step and refuse a save: an entry outside the grammar (E1), an edge naming a step that is not in `steps` (E2), a step connected to itself (E3), an edge listed twice, where `on success` written or omitted is the same edge (E4), an edge between phases (E5), a cycle, reported with its steps in `steps` order (E6), an `on failure` edge leaving a `human` step, whose decisions are not routed (E7; `on any` from a `human` step is allowed), a step whose incoming paths require both outcomes of one step and can therefore never start, reported at the first such step and not again for the steps after it (E8), and more than 64 edges (E9). The checks run in stages: more than 64 edges is the only issue reported; otherwise the grammar, names, self edges and duplicates come first and, with the layout warning, are reported for the file itself, even when a listed step is missing; only a clean list of a pipeline whose steps all resolve is checked for phases, routing from `human` steps, cycles and impossible joins, the last only when there is no cycle. A malformed field reads `Field "edges" must be a list of text entries` or `Field "layout" must be a mapping of step name to [x, y]`.

Graph warnings are saved and listed: a `layout` key that is not a step, which the editor drops on save (W1); an external step that a path reaches without a `human` step (W2); the pipeline without a gate (W3, unchanged); and, once per pipeline, two `agent` steps of one phase that could start together because neither precedes the other and their edge conditions do not exclude each other, while the host runs one session at a time (W4). The external check is path based: a step is guarded when every path to it inside its phase passes a `human` step through an `on success` edge, or when an earlier phase holds a `human` step that runs whenever that phase passes, that is one reached from the phase start through `on success` and `on any` edges only. The `git push`, `gh pr`, `curl` and `wget` heuristic uses the same check. On an implicit chain this is the earlier walk in phase order and keeps its messages; on an explicit graph the warning reads `Step "<name>" has an external effect and a path reaches it without a human step`, or `looks like an external action (git push, gh pr, curl or wget) and a path reaches it without a human step` for the heuristic. The warning for a `fix` step with no retries stays a step warning.

### Definition writes

`apps/host/src/pipelines/writer.ts` saves and deletes `steps/<name>.md` and `pipelines/<name>.md` in the global or project root of the host that serves the request. The client sends the whole file text; the host never composes frontmatter. The document goes through the loader's strict parser, must carry the same `name` as the file, may not exceed the read limit and must be valid text. Errors return `pipeline-definition-refused` with the issues, capped like the catalog, and write nothing and create no folder; warnings, such as an external step with no earlier `human` step, ride along in the catalog returned after the write. A pipeline may only list steps that exist in the catalog merged for the request directory, so a global pipeline is checked against the requesting project's view, and a step used by a pipeline is not deleted. A `human` step with retries and an `effect: external` on an `agent` or `human` step are errors.

Every write names the `contentHash` the writer read: `expectedHash` is `null` when the file must not exist yet. Inside one critical section per root the host reads the file, compares hashes and writes. A mismatch returns `pipeline-definition-conflict` with the current path, hash and text and changes nothing; the host never merges, the client reads the current version and decides. The write goes to a unique temporary file with mode 0600 in the target folder, then either a hard link (no file expected, so an outside creator cannot be overwritten) or a rename after a second hash check. The temporary file is removed on every failure path. The global root and its folders are created on first save with mode 0700; symbolic-link folders, a project root outside the project and a project root equal to the global one are refused. A pipeline with a run in progress is `busy` for save and delete, and the message names the run; the run itself keeps the snapshot it pinned. Edits made outside the host between the check and the rename are not locked out, so the hash check is a safeguard against lost updates rather than a file lock.

A pipeline save also resolves the document's graph against the steps of the catalog merged for the request directory. A graph error, such as an edge between phases, refuses the save with the errors and the line of `edges:`; graph warnings ride along in the catalog returned after the write.

### Definition commands

`node dist/main.js pipelines <command>` (`apps/host/src/pipelines/cli.ts`) applies the same loader and writer as the editor from a terminal, so an agent session and the editor produce the same files. It works on files only: it opens no database, needs no running host and ships in the same bundle as the host. `--directory` selects the project (default: the current directory) and `--scope project|global` selects the root of a write. `validate` prints the catalog issues as `severity path:line: message` and exits 1 when any is an error; `list` prints each step and pipeline with its scope and `contentHash`. `--json` prints the catalog, the issues, the refusal or the conflict as JSON.

`add-step --file <step.md>` reads the file text, takes its `name` and saves it with `expectedHash` `null`, or with `--expected-hash` to replace an existing step. `add-to-pipeline --pipeline <name> --step <name> [--after <name>]` and `remove-from-pipeline` read the pipeline file, edit only its `steps` list as text (a one-line `[a, b]` list or a block list; the rest of the file, including line endings, stays byte for byte) and save with the hash they read, so every rule of the writer applies, including the check that each listed step exists. A list layout the command cannot edit is refused with a pointer to edit the file directly and run `validate`. A conflict prints the current path and hash and "The file changed since it was read. Read it again." and exits 2; the command never retries or merges. Exit codes: 0 success, 1 validation errors or refusals, 2 conflict, 3 run session, 64 usage.

When `NESVO_RUN_ID` is set, which the runner sets for every `command` and `action` step and an author session will carry once it exists, `add-step`, `add-to-pipeline` and `remove-from-pipeline` exit 3 before reading any file: "Pipeline definitions cannot be changed from inside pipeline run <id>. Ask the operator." `validate` and `list` stay available. This is a cooperative guard against a session steered by outside content, not a security boundary: the definitions a run uses are protected by its pinned snapshot, while a session that writes the files directly is not stopped by the command. The command has no database, so it cannot see active runs the way the host's save does; a pipeline with a run in progress is still protected by that run's snapshot. `--expected-hash` on `add-to-pipeline` and `remove-from-pipeline` is compared with the file as it is on disk, so a hash older than the file is a conflict.

When a pipeline file has an `edges` list in one of the two layouts the commands edit, a one-line `[a -> b, c -> d]` list or a block list, `remove-from-pipeline` also removes every entry that names the step and prints, for example, `Removed 2 edges that named "lint"`; removing the last entries of a block list writes `edges: []`. `add-to-pipeline --after <name>` on such a file keeps the chain meaning of `--after`: it adds `<after> -> <step>` and moves each `on success` edge that leaves `<after>` to start at the new step, printing each rewired and added edge, while `on failure` and `on any` edges stay on `<after>`. When the new step belongs to another phase than `<after>`, or without `--after`, no edge is added and the command says that the step starts when its phase begins. A removal that leaves a step without incoming edges names that step too. With `--json` these notes go to stderr and stdout stays the catalog. An `edges` list in any other layout is refused with "The edges list uses a layout this command cannot edit. Edit the file directly, then run validate." and nothing is written. A pipeline without `edges` is edited as before. `validate` prints graph issues like any other issue, and `list --json` includes each pipeline's `graph`.

### Workspace isolation

`apps/host/src/workspace/isolation.ts` gives a task its own Git worktree and branch so that a writable author session never edits the operator's checkout and a later push action can only push the task branch. `createTaskWorktree` requires an absolute, existing project directory that is the top level of a Git work tree; a subdirectory is refused rather than silently widened to the whole repository. It refuses a project inside `<dataDir>/worktrees/` (`nested-worktree`), a data directory inside the project (`data-inside-project`), a folder outside Git (`not-a-repository`), a repository without a commit, and an existing branch or path. The worktree is `<dataDir>/worktrees/<runId8>-<slug>` on branch `nesvo/<slug>-<runId8>`, where `runId8` is the first eight characters of the run ID and the slug is lowercase letters, digits and inner hyphens, at most 40 characters. The base is the project's `HEAD` commit hash, read first and then passed to `git worktree add`, so the branch starts at the recorded commit even if `HEAD` moves meanwhile.

The module stores nothing. The caller records the operator's project as the run's `projectRoot` and the returned path as the run's `directory`; the run record, not the worktree, says where a worktree came from. A session started for the run uses the worktree as its stored directory through the internal `isolatedDirectory` option of session creation. `listTaskWorktrees` reads `git worktree list --porcelain` and keeps entries under `<dataDir>/worktrees/`. `removeTaskWorktree` removes only such an entry and never deletes the branch. It runs `git worktree remove` from the project directory and lets Git refuse a worktree with uncommitted or untracked changes unless forced; no Git process starts inside the worktree, because a writable session controls its `.git` pointer and could otherwise redirect Git to a repository whose configuration runs commands as the host user. A worktree whose pointer no longer leads back to the project is refused. If `git worktree add` times out or is stopped, the error names the path and branch that may be partly created; they too are removed only on request. Nothing is removed automatically. The module never pushes, fetches, merges, commits or deletes a branch.

Git runs from an absolute path found on `PATH` (`git.exe` on Windows), never from the project directory, with `shell: false` and an environment limited to `PATH`, `HOME`, `USERPROFILE`, `SystemRoot`, the temporary directory and locale variables plus `GIT_TERMINAL_PROMPT=0`, so an inherited `GIT_DIR` or `GIT_WORK_TREE` cannot redirect it. Queries are bounded to 10 s and worktree changes and status to 60 s, with output capped at 64 KiB. A missing Git is `git-unavailable`. Repository hooks that Git itself runs, such as `post-checkout`, run inside the same bound. `NESVO_GIT_EXECUTABLE` replaces Git with an absolute path for tests.

Every Git call goes through `apps/host/src/process/owned-process.ts`. `runOwnedProcess` starts the command in its own process group (Windows: a tree ended with `taskkill /T /F`), tracks descendants on Linux, caps stdout and stderr separately, reports `timedOut` and `outputTruncated`, and on deadline or Stop sends `SIGTERM`, then `SIGKILL` to the group and recorded descendants. It resolves only after the process has closed; a start failure, a cancellation and an unconfirmed close reject with `OwnedProcessError` (`spawn-failed`, `cancelled`, `unconfirmed-close`). The helper is shared so that pipeline command steps run under the same rules; the provider adapters keep their own copy of the pattern for now.

### Pipeline tasks

`start-pipeline-task` (`apps/host/src/pipelines/tasks.ts`) creates one ordinary session bound to a new run. The host validates the directory, resolves the project root the same way the definition reader does, reads the task spec (relative paths resolve against the directory) and the requested pipeline, and refuses invalid definitions with their issues. It answers `busy` while a run is active for that project root, while the host is busy with a session or while another task is starting, and confirms a Codex reasoning effort before anything is written. With `isolation: 'worktree'` it creates the task worktree and branch first and uses the worktree as the run directory and session directory, recording `worktree`, `branch` and `base` on the run; otherwise the run directory is the project root. The spec body is saved as a private snapshot in `<dataDir>/pipeline-specs/<runId>.md`, so later turns use the text the task started with; snapshots of runs that no longer exist are removed when a later task starts. The host then inserts the `pending` run, creates the session with the internal pipeline origin (provider, model, effort and mode from the request; Claude Code only read-only; delegation off), links the run and the session in both records and calls `advanceRun`. The public `create-session` request stays strict and cannot carry an origin.

The runner owns every move; the author port only reports and sends turns. A `pending` run with an `agent` or `human` step in `plan` becomes `planning` and sends a planning turn: the spec followed by "Produce a plan for this task. Do not change files.". On Codex that turn passes a read-only sandbox and the `never` approval policy in `turn/start`, which the installed app-server documents as a per-turn override; the next turn sends the session's own policy again. Claude Code is read-only anyway. A `pending` run without such steps begins its `plan` steps directly, or goes straight to the implementation turn when the phase has none. When the planning turn completes, the `plan` steps run; when they pass, the run becomes `implementing` and sends the spec, the plan reply when a planning turn ran, and "Implement the task as planned.". When that turn completes, `pre-done` steps run, then `pre-push` steps, then the run passes. A turn that ends `failed` makes the run need attention, `stopped` makes it `stopped` and `interrupted` makes it `interrupted`, each with a short reason. A message ID that is already used by a message without the pipeline origin is refused, and the run needs attention. Every completed turn creates its review version as for any session; later stages bind gates to it.

Each turn carries `origin: 'pipeline'` and a deterministic message ID derived from the run ID, the turn kind and the attempt. The session service treats an existing ID as already sent and returns without starting anything, so repeated passes never send a turn twice. A turn is sent only when the run status requires it and its ID is unused. When the host is busy with another session, nothing is written and the runner starts a single 60-second timer for that run; it is the engine's only timer and there is no polling loop. The next `session-changed` event or finished turn that leaves the host idle calls `advanceRun`, which sends the turn once. If the timer fires first, the run needs attention with "The computer was busy with another session".

Session events reach the runner in one place: the session service notifies run-finished listeners after a turn is finalized, its result and review are saved and the session no longer counts as active. For a bound session the listener calls `advanceRun`; it also wakes runs waiting for an idle host. While the turn is still active, its state reads as running, so checks never start before the diff is captured. Stop on a bound session while one of the run's own turns is active stops the run through the runner; Stop on an operator message in that session stops only that message. `stop-pipeline-run` stops the run and the session's active turn. After startup recovery the host calls `advanceRun` for every unfinished run, which only reconciles: recovery has already made runs that were planning, implementing, checking or fixing `interrupted`, and a `pending` run that never began becomes `interrupted` too, so no turn is replayed.

`resume-pipeline-run` accepts an `interrupted` run or one that needs attention. It is refused with "Step `<name>` may already have run. Mark it done or run it again." while any step is `uncertain`, with `busy` while another run is active for the project, and when the awaited planning or implementation turn ended before it finished, because resume never repeats a turn; such a run can only be stopped and the task started again. Otherwise it writes the intent in one transaction (a new `pending` attempt for every `interrupted`, `failed`, `error` or `blocked` step of the current phase, the status the run had in that phase, no attention) and calls `advanceRun`. The pass then evaluates the dead paths again: an `unreached` step whose dead edge came from a retried step gets a new `pending` attempt and runs if its edges fire, while one cut off by a step that keeps its outcome, such as an `on failure` branch of a step that passed, stays as it is without a new attempt. Only one active run per project root and one active session group per host exist; two pipeline tasks on one host take turns for the session.

The author session's provider process inherits the host environment plus `NESVO_RUN_ID` and `NESVO_PROJECT_ROOT` (the operator's project, which differs from the session directory in a worktree), so a tool started inside the session can tell it belongs to a run. Command and action steps receive the same variables from the runner.

### Pipeline view

The renderer keeps pipeline runs and step records next to sessions in `use-sessions.ts`, keyed by host and ID and merged by revision from `pipeline-run-changed` and `pipeline-step-changed`. A connected computer with the `pipelines` capability loads its first run page on connection, and every session with `pipelineRunId` loads its run detail once per synchronization; a host snapshot clears that memory so a reconnect reloads it. Pipeline methods take the host ID explicitly, so they need no host-bound wrapper.

`entities/pipeline` holds the labels and tones: phases read Plan, Before done and Before push; run statuses map to text such as Checking, Waiting for you, Passed and Needs attention; tones use the existing success, error, warning and info foreground tokens, with pending, skipped, stopped and interrupted muted. A step shows its latest attempt, and the step list is built from the pinned pipeline in the run, so steps without a record still appear as pending.

The conversation stays free of pipeline content. Pipeline state lives in the session card, a floating 232 px card anchored at the top right of the session view. A session with `pipelineRunId` shows a compact status button in the header (the pipeline glyph and the run status in its tone, icon only on narrow windows) that opens and closes the card; other sessions, the inbox and the new-thread screen open it from the details button. Opening the card focuses it, the arrow, Home and End keys move between its rows, and Escape closes it and returns focus to the button that opened it, or to the header button when the opener was replaced. The card stays open while the operator switches sessions and does not take focus again. The card is built from compact 28 px rows separated by thin dividers, and a row only appears when Nesvo has its data. Computer shows the host and its connection (opening Computers) with a button that browses the session's files. Git shows the task branch when the run is isolated in a worktree. Pipeline has a section header with the run status and, when an action applies, a menu with Stop pipeline while the run is active, Resume when it needs attention or was interrupted, and, while the run can resume after an action step whose outcome is uncertain, It already ran (a recorded skip with that reason) and Run it again (resume). The attention reason and any control error follow the header; while an action step is uncertain, a note names it and points to the two choices in the menu. Each phase row shows the phase state icon, the number of completed steps out of all and a chevron that expands its steps; the phase of the current step starts expanded. A step row shows its state icon, name, the attempt out of retries plus one above the first attempt and its duration, live while running. A step row opens its result in a popover beside the card with the same surface: state, duration, attempt, an attempt switch, the summary, an outputs table and the evidence list; Escape closes it and returns focus to the row. Log and text evidence with a path loads a bounded preview through `read-pipeline-evidence` on request; links are shown as text because the renderer has no external-open route. A human gate or a step with a review offers Open in Inbox, which today opens the Inbox; the target carries host, run, step and review for the later gate row. An agent step with a session links to it. Workers lists the session's delegated workers with their status and opens them. Usage shows one weekly bar per provider that reports a seven-day window, with the provider mark and the remaining share as in the footer rings; stale and offline observations fade, and focusing or hovering a row shows every window with its reset time and when the limits were checked. Providers without that window are left out. Opening files, skills or a saved diff closes the card and returns focus to the button that opened it when that panel closes.

The sidebar shows a pipeline glyph and the run status instead of the session status for an author session, unless the session itself needs an approval or failed, and nests sessions with `pipelineStepId` under the run's author session like workers.

The sidebar's top group has a Pipelines row next to Search and Inbox. It opens a read-only main-area view of the definitions on one computer and folder, starting from the new-thread choice when opened from the new-thread screen and otherwise from the selected session's computer and folder, both changeable there. It lists valid pipelines with their origin (global or project), description and step count per phase, the chosen pipeline's steps with type, phase, skill, timeout, retries, failure behaviour, needs, body and origin, override notes, and every validation issue with its severity, message, origin, file and line. Pipelines that fail validation appear only through their issues. Nothing is edited there; the files remain the source of truth.

The new-thread screen has a Pipeline chip. It reads `list-pipeline-definitions` for the chosen computer and folder when opened and lists valid pipelines with their step count and the number of catalog issues that name the pipeline, one of its steps or the spec. Choosing a pipeline picks its first spec from `.agents/tasks`; a spec from the list or any path can be chosen instead. Isolate in a worktree is on by default when a folder is chosen and unavailable without one; the catalog does not report whether the folder is a Git top level or whether the host has Git, so those refusals come from the host when the task starts. The gate provider defaults to the provider that is not the author's, with that provider's reported models; gate sessions are read-only. With a pipeline chosen, the composer text is an optional title, skills are off, and sending calls `start-pipeline-task` instead of creating a session; the spec title is the default title. A failure keeps every choice and shows the error with the matching validation issues.

### Graph editor

The desktop edits a pipeline on a canvas opened from the Pipelines view (Edit on a row, or New pipeline). The editor in `widgets/pipeline-graph-editor` is a client of `save-pipeline-definition` and `list-pipeline-definitions`: it never asks the host to compose YAML. `entities/pipeline-graph` turns a resolved pipeline into an editor document (nodes with positions, edges with their condition, the original body) and back into file text with the frontmatter in a fixed order: `name`, `description`, `steps` in topological order by phase and then by canvas x, `edges` as one string per edge with `on success` omitted, `layout` as integer pairs, then the body unchanged. A pipeline opened without `edges` shows the implicit chain and is written with explicit `edges` and `layout` on its first save. The three horizontal lanes are the phases; a step cannot be dragged into another lane because `phase` lives in the step file and other pipelines may use the step, so the inspector changes it and shows how many other pipelines use the step. Validation happens twice: live on the client with the shared `resolveGraph` (badges on nodes, Save disabled while an error exists, a refused connection shows the shared message inline), and on the host at save, whose issues come back inline by step name. Save writes each new or changed step file first and then the pipeline, each through `save-pipeline-definition` with the `expectedHash` the editor opened; a `pipeline-definition-conflict` opens a dialog with the current file text and the choice to reload or to keep the edits on top of the newer hash, and nothing merges. A run of the open pipeline can colour the nodes by their latest attempt state and open the step result in the inspector; the editor starts no run. The Start node reads the scheduled jobs whose `pipeline.name` is this pipeline and only lists them. The canvas uses `@xyflow/react` 12.12.1, pinned exactly and listed in `THIRD_PARTY_NOTICES.md`; the library supplies panning, zooming, dragging and connection gestures, and every colour it draws comes from the application tokens. The inspector forms render through the props contract in `widgets/pipeline-graph-editor/inspector/index.ts`, and `data-slot="editor-dock"` at the bottom right of the canvas is the mount point for the pipeline assistant.

The inspector forms in `widgets/pipeline-graph-editor/inspector/` compose step, pipeline, connection and schedule values on the client, check them live with the contract schemas so the messages match the host's, keep every field within the contract limits and show host issues beside the field they name; saving, removing and scheduling go through the editor's callbacks, and a schedule is a scheduled job with `pipeline` set, an empty prompt and read-only mode. Because `phase` lives in the shared step file, changing it for a step that other pipelines use first shows "Used by N other pipelines; the step file changes for all of them" and applies the new phase only after the operator confirms, and the warning stays beside the field until the step is saved.

### Pipeline assistant

`pipeline-assistant-send` edits definitions through a chat. The operator's message, the provider, model and optional effort, the project directory, the open document with its hash and the selected steps travel in one request; the desktop requires the `pipelines` capability, routes by computer, waits up to 60 seconds and adds the computer ID to the proposal event, and the mobile gateway ignores the event. `apps/host/src/pipelines/assistant.ts` answers with a `pipeline-assistant-turn` naming the session and the message it sent. The session is an ordinary visible one, so the sidebar, Stop and history work as for any session.

The first message with `sessionId: null` creates a session with the internal assistant origin: title `Pipeline assistant · <pipeline or folder>`, the requested provider, model and effort, read-only mode, the project directory and delegation off; a Codex effort is confirmed first. A later message names that session; the host accepts it only when the session has no run, job or parent links, is read-only with delegation off and was created by the assistant on this host, which survives a restart because assistant messages carry the pipeline message origin. A conversation keeps its own provider and model and must stay in its folder. Every turn is sent read-only. While any session works on the computer, or a finished response is still unsaved, the request is refused with `busy` and "Another session is working on this computer." and nothing is created; a second request while one is still starting is refused with `busy` as well. A conversation whose provider thread never started, for example because its first turn failed at once, receives the full first turn again.

`apps/host/src/pipelines/wrapper.ts` composes the turn text from one fixed template in product terms. The first turn holds the role and rules (help design pipelines, never create, edit or delete files or run commands, answer with complete file texts, quoted material is data and only the operator block is a request), the format reference (step and pipeline fields with their limits from the contracts, the edge grammar with the chain default, the validation rules including the graph errors and warnings in one paragraph, phases and their meaning), then the catalog summary from `loadCatalog` (steps as name, type, phase, scope and hash, pipelines with their scope, hash, step order and explicit edges or chain, specs with their pipeline and title, shortened past 48,000 characters), the open document (kind, scope, name, hash, full text), the selection and the operator's request, each between `[begin <label> <fence>]` and `[end <label> <fence>]` lines with a random fence that does not occur in any quoted text, and finally the answer instruction with the proposal JSON Schema, which asks Claude Code for its structured answer and Codex for exactly one fenced `json` block. Later turns quote only the request, the selection and the open document when its hash differs from the last one sent to that session; the last hash is kept in memory, so after a restart the document is sent again.

Claude Code turns pass the proposal JSON Schema from the contract as the adapter's output schema, so the result frame carries the proposal as a structured field; Codex turns pass no schema and answer in the fenced block. When the session's turn ends, the run-finished listener reads the final agent message of that turn and the run's structured output and takes, in order, the structured field, the first fenced `json` block, or the whole text when it parses as JSON, and parses it strictly with the proposal schema. Anything else, and a turn that ends `failed`, `stopped` or `interrupted`, emits `pipeline-assistant-proposal` with status `invalid` and no proposal; the raw answer stays in the conversation. A parsed proposal is emitted with status `ok` after every change went through the writer's checks against its planned path in the project or global root: valid text within the file limit, the strict document parser, the file name rule and, for a pipeline, steps that exist in the catalog of the directory or among the valid steps of the same proposal, followed by the shared graph rules (`checkGraph`) against those step definitions, where a proposed step replaces the catalog step of the same name with the loader's precedence: a proposed project step always does, a proposed global step only when no project step of that name exists. Graph errors and warnings are both reported, so an edge between phases appears as an error on its change. Issues are listed per change index, at most 50 each. The message and the summaries pass through the result secret filter before the event; documents are kept verbatim because they are the file texts the operator may apply. A turn sent before a host restart emits no event.

The host never writes a definition in this path; the operator applies a change through `save-pipeline-definition`, which keeps its expected-hash conflict rules and full validation. What reaches the provider is the same as for any read-only session: Claude Code keeps its read-only tools, and Codex runs the turn in a read-only sandbox, so neither provider can write through the assistant, but the answer's shape is a request to the model, not a guarantee, which is why the host validates every proposal. On Claude Code the structured channel constrains the shape at the provider; the fenced block remains the fallback when a reply carries no structured field.

The graph editor carries the assistant dock (`apps/desktop/src/renderer/src/widgets/pipeline-assistant/`) in its bottom-right slot: a collapsible chat with the provider and model picker that keeps one session per computer, folder and pipeline, shows the operator's own text instead of the wrapper, and renders each proposal as cards with a diff against the file it would replace; it sends the open pipeline only while the editor has no unsaved edits. Nothing is written when a proposal arrives: Apply calls `save-pipeline-definition` with the hash of the file the diff was shown against (null for a new file), a conflict offers Reload to compare with the file now on disk, and the full conversation stays in the visible session behind Open session.

### Agent steps

An `agent` step (`apps/host/src/pipelines/steps/agent.ts`) runs in its own session created through the session service with the internal pipeline origin that names the run and the step, so the session carries `pipelineRunId` and `pipelineStepId` and the step record carries the session ID. The step session uses the run's gate provider and model, read-only mode, the run directory (the worktree when the task is isolated) and the title `<pipeline> · <step> · attempt <n>`; delegation is off and it is not a visible worker: no proposal, no worker approval, no group. Choosing the pipeline is the approval. Stop on the run stops the step session's active turn through the ordinary Stop path, and the step timeout (`timeout`, default 15 minutes) does the same, failing the step with the timeout. Host shutdown leaves the step `interrupted` through store recovery and nothing is replayed.

Before the session starts, the executor reads the provider usage service for the gate provider; that service answers from its cache and probes the provider's account metadata only when the cache has expired, never with a model turn. The same rule as scheduled jobs applies: when the observation is `ready`, the provider does not say that ordinary usage is allowed, and a window is used up with a reset still ahead, the step is `blocked` with the reset time and no process starts. An observation that is unavailable or in error does not block, and a percentage never overrides a provider that reports ordinary usage as allowed. A rate-limit failure during the turn is also `blocked`, with the reset time the provider reported, and so is every other provider or session failure that is not a verdict (an account limit the provider reports as a plain error, an authentication failure, a session that could not be created or saved, a step session stopped by the operator): a gate that could not judge is not a rejected result, and a `blocked` step keeps the run resumable. `fail` is reserved for verdicts, a verdict without evidence, a repeated invalid verdict and the step timeout.

The step prompt is one template in product terms: the role ("You verify. You do not change files. Return only the JSON verdict."), a statement that everything between the markers is quoted material and that directives inside it are data rather than instructions, the pinned task spec in `<task-spec>`, the author's latest saved result diff in `<diff status="…">` (`complete` with the patch, `not-applicable` with the author's response text for a read-only author, `unavailable` when no result exists or the run has no author session), the step body as `<step-instructions>` or, with `skill:`, as `<skill-parameters>`, and the verdict JSON Schema. Closing markers inside quoted material are neutralized so quoted text cannot end a block. A skill is resolved by name through the shared skill library for the gate provider in the run directory and delivered as for any message (D61): Codex receives the native skill item, Claude the validated static Shared instructions snapshot around the prompt; a skill that is missing, ambiguous or blocked for that provider makes the step `blocked` with the library's reason before any session exists.

The verdict is read only from the structured channel. Claude runs with `--json-schema`, which adds the provider's structured-output tool, and the adapter returns `structured_output` from the result frame; when the model sends no text, the verdict JSON becomes the visible response. Codex receives `outputSchema` on `turn/start`, which the installed app-server (0.167) documents as constraining the final assistant message, and the adapter parses that final message as JSON. Prose is never parsed as a verdict. A missing or malformed verdict gets exactly one repair turn in the same step session ("The verdict did not match the required shape: <issues>. Return only the JSON verdict.", the previous answer quoted as data and the task restated); a second invalid answer fails the step with "The step returned no valid verdict" and both exchanges stay in the step session. The repair count is fixed and not a step field. Step sessions record a gate: they do not create saved results in the Inbox and refuse operator messages, so a verdict is never confused with result acceptance and nobody continues a provider conversation that was never persisted. The verdict's `outputs` reach later command and action steps as `NESVO_OUTPUT_*` variables like any other outputs; they come from a model that read quoted material, so step bodies treat them as untrusted text. A manual run without a spec snapshot reads the spec file again and passes it only while its hash still matches the one pinned on the run. A well-formed verdict with an empty `evidence` list is never repaired: it fails with "The verdict has no evidence". Otherwise `status` maps to the step state, `summary` becomes the result summary, each evidence item becomes a `text` evidence entry labelled with its reference, `outputs` are kept, and the usage reported by the provider for both turns is summed into `cost` with the gate provider.

Claude step sessions are ephemeral and narrowed: `--no-session-persistence` keeps the gate out of the provider's saved conversations and `--setting-sources ""` loads no user or project settings, so `CLAUDE.md` memory files do not steer a gate. Because nothing is persisted, every turn of a Claude step session is a new provider conversation with a fresh provider session ID; that is why the repair turn restates the task. `--bare` is not used: it would restrict authentication to an API key. The tool set stays Read, Glob and Grep in plan mode, so a Claude gate structurally cannot write. A Codex gate relies on the read-only sandbox and the `never` approval policy for the thread and the turn; the sandbox is enforced by the provider, not by Nesvo, and read commands may run inside it. Its thread configuration sets the project instruction file size to zero, so the project's agent instructions in a directory the author can write to do not steer the gate either; the fixture records that setting on every verdict thread. The quota check reads cached account metadata and never infers permission from a percentage. The fixtures assert the argument set (tools, plan mode, no persistence, empty setting sources, the parsed schema) on every verdict launch and the read-only sandbox with the output schema on every Codex verdict turn.

### Human gates

A `human` step (`apps/host/src/pipelines/steps/human.ts`) binds to the latest review version of the run's session, which is the result of the implementation, planning or correction turn that preceded it. The step becomes `awaiting-human` with `reviewId` and `reviewVersion`, and the run becomes `awaiting-human`, in one transaction; then the pass waits. A session without a review binds the gate to no review and the decision rests on the spec alone. When the latest result was already decided outside the gate (changes requested or rejected), the step is `blocked` and the run needs attention instead of waiting on a result nobody can decide. A manual run has no session, so its `human` steps are `skipped` with "Runs without a task session do not wait for a human decision", which keeps manual runs and the portability check unattended; a `human` step followed by an `effect: external` step in the same phase is `blocked` instead, so an external step never runs without a decision. Host shutdown and restart keep a waiting gate as it is and never resolve it. The binding is per step, so it does not depend on the order or shape of the pipeline around it.

The gate also records `definitionChanges`: the paths of the bound diff under `.agents/pipelines/` or `.agents/tasks/`, compared without regard to case because case-insensitive filesystems read those folders under any spelling, at most 64. A running task is protected by the definitions it pinned at start, but accepting such a diff changes what later runs of the project execute, so this flag is the one place where a session can change the definitions of future runs, and the operator decides with it in view.

`decide-pipeline-gate` names the run, the step, the bound review ID and version (both `null` for a gate without a review), an idempotent decision ID, the decision and a comment. A repeated decision ID with the same payload returns the current run, also while the first request is still running; a different payload is refused. The host refuses a step that is not the latest attempt or not `awaiting-human`, a run that is not `awaiting-human`, a different review ID and a stale version. The decision is stored on the step as `decision` (`decisionId`, `kind`, `comment`, `at`) and written in one transaction with the step result, the run status and the review decision:

- `accept` performs the review acceptance exactly as `decide-review` does: the host must be idle, the version current, and the directory is captured again and compared with the recorded fingerprint, so an outside edit refuses the decision and changes nothing. The step passes with "Accepted by the operator" and the comment (or "Accepted") as the operator note, the run returns to `checking` and the pass starts the next step. A review already accepted at an earlier gate of the same run stays accepted and is only checked again.
- `reject` needs a comment. The step fails with the comment, the review becomes `rejected` with a `reject` decision and the run `rejected`. No turn starts.
- `fix` needs a comment and a task session. The review records `request-changes`, the step fails with the comment and the run becomes `fixing`. The runner's `fixing` move sends the comment as a correction turn through the author port, with the message ID derived from the run, the step and its attempt, so repeated passes send it once. When the correction completes, a `plan` gate re-runs the `plan` phase; any later gate restarts from `pre-done`, because the change can invalidate earlier checks. Every step gets a new attempt row and the gate binds to the new version. A correction that ends `failed`, `stopped` or `interrupted` makes the run need attention, `stopped` or `interrupted`. Corrections from a human are not counted.

While a gate waits on a version, and while the run of the result's session is in progress at all, `decide-review` answers `busy` with "This result is waiting for its pipeline gate", checked again after the fingerprint capture, so the Inbox result row and the gate cannot diverge and no Inbox correction starts while checks run. A finished, failed, stopped or interrupted run leaves its result to the Inbox.

`skip-pipeline-step` records an operator's decision to skip a `pending`, `awaiting-human`, `failed`, `error` or `blocked` step of the phase the run is in, while the run is `checking`, `awaiting-human` or needs attention. The step keeps `skip` (`reason`, `at`) in its record for good, its result stays empty, and the run returns to `checking` unless another gate still waits. Skipping a `human` step is refused when a later step declares `effect: external` and no other unskipped `human` step precedes that step, so the validation warning about external steps becomes a hard refusal at the gate. Skipping is refused while any step is `uncertain`, and like resume it answers `busy` while another run is active for the project.

`resolve-pipeline-step` is the only command that changes an `uncertain` step, and only while its run needs attention. `mark-done` needs a comment saying what the operator verified; the attempt becomes `done` with "Marked done by the operator. Later steps receive no outputs from it." and the note, and no outputs. `run-again` leaves the `uncertain` row as it is with the decision recorded and inserts a `pending` attempt with the next number. Both are idempotent by decision ID and return the run to `checking` without attention. Resolving also answers `busy` while another run is active for the project. `resume-pipeline-run` keeps refusing a run with an `uncertain` step and still gives a failed or blocked step a new attempt when nothing is uncertain. A run whose phase holds a gate sent back to fix resumes in `fixing` without new attempts: an unsent correction is sent, a completed one re-runs the checks, and one that ended `failed`, `stopped` or `interrupted` is refused, because a run never repeats a turn.

Every decision writes its intent and then calls `advanceRun`; no gate command drives a phase itself.
