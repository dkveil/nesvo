# Mobile product priorities

This is a proposed sequence for nesvo, not a promise to implement every capability. Reassess each stage after testing the preceding one on a physical phone. The baseline below was checked against the code on 2026-10-22.

## Product boundaries

- The terminal is the default session view. An optional structured view may complement it later without adding permanent conversation tabs or taking space away from the terminal.
- The app ships English-only, without a localization library; a locale layer is a later iteration.
- Keep Sessions and Computers as primary navigation. Put attention items behind an inbox action with a count; keep settings secondary. An open terminal needs a session switcher and a compact input toolbar, not the entire dashboard navigation.
- Retain the Ultraviolet identity, quiet surfaces and compact rows. Application appearance and terminal content colors are separate settings. Motion communicates state and feedback; it must not animate the terminal grid.
- Processes and agent integrations run on the host. Keep the original CLI subscription login; do not add model API keys, extract provider credentials or use a model to interpret terminal output.
- Prefer useful, complete vertical slices over empty controls for planned features. A feature is available only when its host, protocol, client and required device behavior work together.

## Current baseline

The app has a real xterm terminal, a small command field, Escape/Ctrl+C/Tab/arrows, keyboard dismissal, QR pairing, nested groups, session search and status filters. The switcher shows program, status, group and working directory. Native storage currently remembers one host; there is one active host connection.

Status combines terminal activity, conservative interpretation of recognized screen text and process exit. It is not a structured stream of agent tasks or permission requests. Status timestamps exist in the host data but are not shown as elapsed times in the mobile list. The mobile font size and palette are fixed. Mobile fullscreen, a key modifier palette, files/Git, attachments, SSH, native permission approvals and structured conversation interfaces are not implemented. The attention inbox, decisions, opt-in pushes, read-only jobs and child sessions are described in the table below.

The native TUI already has fullscreen and a saved default. That does not imply that the mobile client has the same presentation feature. Host restart does not preserve running shells.

## Recommended delivery order

1. **Comfortable terminal:** toolbar, display preferences, in-session switcher and physical-device input tests. Acceptance: the user can enter, edit, paste, dismiss the keyboard and switch sessions without losing input or control context.
2. **Several machines:** saved profiles, explicit connection state and scoped identities; then concurrent observation. Evaluate direct SSH as its own transport milestone, preserving the existing host path.
3. **Reliable supervision:** prototype one agent adapter, build an attention inbox, then add validated approval actions and notifications. Acceptance includes disconnect, stale requests, duplicate delivery and decisions made from another client.
4. **Useful context:** attachments and read-only files/Git. Add optional conversation presentation and quoted comments only where the adapter provides sufficient information.
5. **Optional native extensions:** Live Activities and selected gestures. Keep Watch, hardware keys, Mosh and key synchronization outside the initial commitment.

A stage can ship in smaller increments. Priority can change after actual use; no calendar estimate is implied.

## Implementation constraints

Keep presentation preferences and view state in the mobile client. Put new filesystem, Git and agent adapters behind host application commands, with validated, versioned protocol boundaries. Existing control leases remain authoritative for terminal input. A future permission decision is a distinct operation with its own request identity; it must not become arbitrary terminal keystrokes or silently take over another client.

Expo remains suitable for the shared mobile UI. Custom native libraries use development builds rather than Expo Go; this does not require rewriting the app. [Expo development builds](https://docs.expo.dev/develop/development-builds/introduction/)

SDK 57 provides an iOS widget/Live Activity path through `expo-widgets`, which is unavailable in Expo Go. Remote Live Activity updates use APNs. Design and test this extension separately from the main app's always-open terminal connection. [SDK 57 widgets](https://docs.expo.dev/versions/v57.0.0/sdk/widgets/)

Remote notification behavior and native configuration require their own validation; Android push notifications are unavailable in Expo Go. Do not equate local foreground banners with delivery to a locked phone. [SDK 57 notifications](https://docs.expo.dev/versions/v57.0.0/sdk/notifications/)

Claude Code's documented hooks provide a starting point for an adapter, including permission-related events. This is not evidence that every CLI exposes identical events or that every displayed prompt supports an external response. Verify each supported CLI version and authentication path before promising parity. [Claude Code hooks](https://code.claude.com/docs/en/hooks)

Mosh bootstraps through an authenticated connection and then communicates with its server over UDP. Its network behavior needs separate server setup and client integration. [Mosh protocol paper](https://mosh.org/mosh-paper.pdf)
