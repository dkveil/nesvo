# Selective testing policy

Damian explicitly chose limited testing for prototype delivery. Protect meaningful behavior without filling the repository with repetitive tests.

## Required checks

- TypeScript strict, ESLint and Prettier are the routine baseline.
- Test critical boundaries when their behavior changes: process lifecycle, validated messages, persistence, cancellation, permissions and revision-bound review.
- Prefer integration tests with real local resources over mocks of implementation details.
- Keep one principal desktop scenario and extend it only when the accepted product flow requires it.
- Review visual and low-risk copy changes manually. Do not add unit tests solely for JSX, styles, wrappers or getters.
- No coverage percentage, mandatory unit-test count, one-test-per-function policy or large component snapshots.

Current checks:

| Check                            | Evidence                                                                                     |
| -------------------------------- | -------------------------------------------------------------------------------------------- |
| Host lifecycle integration       | Migration, identity, persistence, streaming, resume, approvals, delegation, Stop and cleanup |
| Schema compatibility integration | Newer database refused and version preserved                                                 |
| Desktop scenario                 | Electron/preload/host/database path, decisions, worker tree, reload and group shutdown       |

Tests use dedicated temporary directories and no provider accounts. They must not operate real project data or existing agent processes.
The desktop smoke scenario can run against either build output or an unpacked package.

D65 extends the existing host cases and principal desktop scenario with metadata-only usage reads. Provider fixtures reject user/model/thread/turn calls from inspection, record the exact account/usage protocol, and check confirmed process cleanup. Assertions cover shared concurrent reads, cache reuse, unchanged session history, real reported percentages/reset timestamps, account metadata and unavailable windows without invented zero usage. Desktop checks cover provider/account entry points, refresh, focus return and unavailable data after restart. The same remote scenario compares different Local and SSH-host usage states and rejects offline reads without reconnect. Actual installed-provider reads are recorded separately without model tasks; fixtures do not prove subscription access. No new suite or component snapshot baseline is added.

D63/R1 adds one focused Linux-only integration scenario at the independent-host transport boundary. A real daemon and private Unix sockets exercise client detach during worker execution, reconnect with stable identities, pending approvals and reviews, per-client response correlation, invalid frames/identity/protocol, exclusive data/runtime ownership and explicit process shutdown. The same existing provider fixtures supply controlled output. The case is skipped on Windows/macOS because R1's standalone daemon targets Linux; existing local host and desktop evidence remains separate. There is no unit-test matrix or coverage target.

D64/R2 and R3 add one opt-in remote boundary scenario, `bun run smoke:remote`, after building the application. It requires Docker with Linux containers and a native OpenSSH client/key generator. The helper owns an isolated Linux SSH server, daemon, ephemeral keys, private known-hosts file and desktop profile. It mounts repository files read-only and binds a random localhost port. It checks strict unknown/changed key rejection, host-specific commands and Inbox decisions, Local defaults, detached remote work, snapshot recovery and removal without daemon shutdown. The same provider fixtures avoid account or model calls. Static service-unit verification is distinct from running a persistent systemd service on a real VPS. The helper cleans only its own resources. It does not alter global SSH configuration or existing runtimes.

P2 extends the same two host cases and the same desktop scenario. A local CLI fixture checks analysis flags and stdin, streams text, retains a resume marker, emits provider errors and spawns an owned child for cancellation checks. The host scenario verifies that partial text precedes completion, repeated message IDs do not start another turn, Stop stays responsive, failed results never become completed, restart restores history, unfinished runs recover as interrupted, and shutdown cleans the process tree.
The desktop scenario covers model selection, default and invalid directories, session-specific drafts, real IPC streaming, history after reload, continuation, Stop, visible provider failures, empty inbox, search and compact panels. It runs against both build output and unpacked packages. No unit-test suite or visual snapshot baseline was added.
Real CLI evidence is recorded separately. The fixture is not proof of subscription availability, successful model output or provider resume behavior. A provider account limit leaves real task acceptance pending even when all automated checks pass.

P3 extends these same checks with an explicit Codex app-server fixture: dynamic models, streaming and resume, provider-specific sandbox policies, session/run/request-bound approval and denial, stale decision rejection, and cleanup while waiting for approval. Denial must leave the fixture's operation marker absent; acceptance must create it only for the intended request. A version-two Claude snapshot must retain its history after migration. The desktop scenario exercises provider selection and real approval UI through the same preload/host boundary.

P4 extends the same two host cases and one desktop scenario. The fixture validates native dynamic-tool metadata and resume, returns actual child results to the parent, and runs two independently tracked worker processes with streaming output. Checks cover absence of children before approval, accept/decline, stale decisions, proposal limits, directory and symlink escape, overlapping writes, recursive tool rejection, correct success/failure attribution, child Stop with a live sibling, parent/pending cancellation, group shutdown and persisted relationships. Migration keeps existing Claude and Codex conversations without silently enabling delegation. The desktop flow exercises proposal buttons, child navigation, two live workers, Stop and compact layouts. Once an owned process is confirmed gone, its PID is retired from later cleanup checks to avoid confusing Windows PID reuse with a leak.

Real P4 evidence separately uses installed Codex through Electron, including two concurrent workers and parent continuation after one worker is stopped. Fixture success is not real-provider evidence. Native tool execution on Windows does not certify real account access on macOS or Linux.

P5 keeps the same two host cases and one desktop scenario. Focused additions exercise immutable result versions, human-only decision commands, idempotent correction, stale acceptance, parent dependency invalidation and history after restart. A supervised fixture actually changes text files in an isolated non-Git directory; its before/after diff must include the intended added/modified/deleted files while preserving unrelated dirty contents. External edits and unavailable binary diffs block acceptance. The desktop flow performs correction and acceptance through the inbox and checks the historical decision. Real Codex execution is a separate deliberate run, not a routine formatting check.

D53 adapts that same desktop scenario to decisions directly on inbox rows. It exercises operation and worker decisions while a different session was selected, then verifies the intended run changed and the unrelated conversation did not. Result links open the exact saved version inside its session. Inline feedback, correction, acceptance from the list and history after reload retain their existing evidence. No new unit tests or host test cases are added for this interface refinement.

D55 extends these existing checks for intent-driven delegation. Creation omits the role field; a valid proposal promotes a new Codex root without changing its permissions. A supervised parent can run a read-only worker, while a writable-worker proposal is rejected before creating a child. Existing native threads retain their identity and recorded capabilities. The desktop scenario uses the English interface, checks the absence of the role picker, accesses diagnostics on demand and keeps the existing cross-session decision and review assertions. Visual spacing and copy receive a focused visual check, not new unit tests.

## Before reporting completion

D57 extends the same host cases and desktop scenario. Provider fixtures emit actual tool start/output/end frames; checks cover persisted timestamps, Stop/restart, late updates, bounded retention and run-specific omission markers. The desktop scenario checks visible activity IDs and statuses, unchanged terminal duration after reload, exact saved review IDs/versions, selected files, numbered additions/deletions, raw patch preservation, older v1 versus corrected v2, compact overflow and Escape/focus return. Real Codex evidence separately exercises file reads and edits through the built Electron app, followed by reload and result acceptance. The diff package's notices are included in native distributions. No additional test suite was introduced.

D58 extends these same checks for the read-only file explorer. Host assertions exercise nested directories, search, current content after an external edit, path containment, links and replaced roots, private/generated exclusions, binary/oversized files, limits and concurrent search with Stop. Desktop assertions open nested files through the real preload/host boundary, search and preview current content, return to exact historical saved diffs, and check compact layout and Escape focus. Provider responses remain fixtures, while filesystem reads use real isolated files. A focused visual check also reads the actual repository without starting a model task. No additional test case or unit-test suite is introduced.

P6.1 extends these same cases and the principal desktop scenario. Codex discovery fixtures cover enabled and disabled metadata, source scopes, unsupported methods, malformed/partial responses and a delayed inspection. They reject account/model/thread/turn calls from discovery. Host assertions cover unknown sessions, injected provider/directory fields, unchanged session data and Stop while discovery is pending. Claude checks use real temporary skill/command files and an isolated CLAUDE_CONFIG_DIR, including invalid frontmatter and unchanged configuration bytes. Desktop checks open, filter and refresh catalogs, switch providers while an older request remains pending, inspect source metadata and verify that invocation controls are absent. Actual installed Codex and local Claude metadata are checked separately through Electron without launching a model task; fixture success does not prove real skill execution.

Run bun run check and bun run build for foundation changes.
Run bun run smoke:desktop when a desktop or host transport/lifecycle change affects that path.
After packaging, run the same scenario with NESVO_PACKAGED_EXECUTABLE set to the executable.
Run a focused regression check after a fix. Do not rerun unrelated suites without a new reason.

Record OS, commit, command and result. Automated native execution, a successful build and the owner's visual acceptance are separate evidence.
No stage is Done solely because tests pass.

P6.2 extends these existing scenarios rather than adding new cases. The host fixture requires native typed skill input with the exact verified name/path and unchanged sandbox. Checks cover canonical source persistence, selected resume after restart, text-plus-skill retry identity, caller-supplied metadata rejection, disabled/missing/stale/unsupported selections, and Stop during catalog revalidation before any thread or turn starts. The desktop scenario exercises slash and button entry, keyboard selection, disabled choices, removal, per-session draft retention, source attribution, acknowledgement and reload. A deliberate real Codex task separately checks that a code available only inside the selected skill appears in the response; fixtures alone do not prove instruction delivery to a real model.

D61 extends the same two host cases and principal desktop scenario for the common library. Real temporary source files exercise physical deduplication, same-name distinct entries, origin provenance, disabled/manual-only restrictions and unsupported metadata behind aliases or shared-only roots. Fixtures require process-local Codex root registration and native typed input, and validate Claude's explicit instruction wrapper, source, hash and body marker. Tests cover modified source hashes, caller-supplied metadata rejection, retry identity, Stop during inspection, selected resume and persisted history. Fixture homes and provider configuration are isolated. They do not prove a model followed the instructions.

A separate built-Electron Windows task selects a Claude-source file in Codex and checks a unique skill-only marker in the real response. A single real Claude attempt selects a Codex-source file; account-limit failure is recorded separately from successful execution. Source/configuration bytes and history after full restart are checked without changing global provider setup.

P7 extends the same cases with exact pending/accepted/corrected review snapshots, stable parent/worker/run identities and decision re-delivery after a full host restart. A second host must fail to acquire the same live data directory without mutating its owner's state. Transport EOF performs owned cleanup. A fixture that emits partial text and exits without a final result verifies provider disconnection, retained partial output, no invented review and explicit continuation in the same thread. Seeded unfinished snapshots simulate recovery without leaving live orphan processes; a completed child must retain its exact run and review dependency when its parent was interrupted before its first review. Another interrupted group after an earlier parent review must supply the new child's result to the native prompt and saved dependencies; changing that child's writable output blocks parent acceptance.

The principal desktop scenario also refuses a second process for the same profile, closes and relaunches Electron with the same isolated data, restores an exact saved diff/file, verifies review and group identities and checks that opening the app or focusing Continue conversation starts no turn. A separate installed-Codex scenario supplies real model evidence for a completed worker, pending review across restart, review acceptance/retry and manual continuation after closing an active session. Platform fixtures and real-provider evidence remain distinct.
