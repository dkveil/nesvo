# Development

## Toolchain

Use Node.js 24.20.0 and Bun 1.4.0. Dependencies and lockfile are committed.
TypeScript 6.0.3 is pinned to the supported range of the selected ESLint integration.
Run commands from the repository root. Bun manages the workspace and scripts; Electron runs the packaged desktop and host.

```sh
bun install --frozen-lockfile
bun run dev
```

The workspace uses neutral shadcn components in the operating system's light or dark scheme. Session details open on demand, leaving the main area for the conversation. The sidebar collapses with its toggle or Ctrl+B, resizes from its edge and remembers both choices locally. A new thread starts from the main-area screen; its first message creates the session. SQLite owns session history; only selection, the sidebar state and unsent drafts remain in renderer memory.
Connection details show the host connection and separate Claude Code and Codex availability on demand. Install the native CLI and use `claude auth login` or `codex login` in a terminal. The desktop never reads or displays credentials. Missing installation, incompatible CLI behavior, missing login and provider failures are distinct states. One provider being unavailable does not block the other.

## GitHub CLI

Install GitHub CLI on each computer that serves pull requests and run `gh auth login` as the same user that runs the Nesvo host. The host locates `gh` on its PATH. Set `NESVO_GH_EXECUTABLE` to an absolute executable path to override discovery. An absolute `.js`, `.mjs` or `.cjs` fixture runs with the host's Node executable. The integration test selects its fixture this way and uses a private temporary directory.

## Pull requests in a session

When an agent reply contains a link to a pull request in the session's repository, for example after `gh pr create`, Nesvo links that pull request to the session; a worktree session is also linked once its branch has a pull request. Unlinking from the pull request menu is remembered and the same pull request is not linked again automatically. Each pull request link in a reply shows a card with its state, changed files, checks and review state. **Review** opens the pull request beside the conversation, with Summary, Code and Threads, the review submission and the viewed-files count; **Open** shows it in the Pull requests view, where checkout and merge are available. The linked pull request also appears as a chip in the session header, in the session details and under Session results. Ctrl+Shift+G or the **Review pull request** command toggles the review panel for the current session.

## Build and check

```sh
bun run check
bun run build
bun run smoke:desktop
bun run package:dir
```

On Linux without a display, use xvfb-run -a bun run smoke:desktop.
The unpacked packages are written to `apps/desktop/release`.

For a packaged Windows check in PowerShell:

```powershell
$env:NESVO_PACKAGED_EXECUTABLE = (Resolve-Path 'apps/desktop/release/win-unpacked/Nesvo.exe').Path
bun run smoke:desktop:package
Remove-Item Env:NESVO_PACKAGED_EXECUTABLE
```

The packaged check launches with a fresh temporary profile, verifies the renderer's connection to the local host, and exercises `ELECTRON_RUN_AS_NODE`. It connects to the renderer over loopback because packaged builds disable the Node inspector.

Packaging refreshes the macOS ad hoc signature after changing the Electron fuses so Apple silicon can load the modified binary. The release uses no developer signing identity.

Optional NESVO_SCREENSHOT saves the smoke scenario's visible state to an explicit path.
The scenario starts a hidden window, uses an isolated temporary directory and explicitly selects the CLI fixture. It never uses a provider account. Fixture text is test evidence, not proof of model availability.

## Releases

Set the release version in `apps/desktop/package.json` and commit the bump to `master` if the version changed. Push the release commit, then create and push a matching tag from that commit. For version `0.0.1`, run:

```sh
git tag -a v0.0.1 -m "Release v0.0.1"
git push origin refs/tags/v0.0.1
```

The Desktop release workflow checks out the tagged code and fails if the tag differs from `v` followed by the desktop package version. You can also run the workflow manually with an existing tag, for example with `gh workflow run release.yml -f tag=v0.0.1`.

Electron-builder writes these installers to `apps/desktop/release`. The workflow publishes them to the tag's GitHub Release with notes generated by GitHub and replaces assets of the same name on a rerun.

- `Nesvo-Windows-Setup.exe` installs the x64 app for the current user with desktop and Start menu shortcuts. Use Windows Installed apps to uninstall it.
- `Nesvo-macOS-arm64.dmg` contains the Apple silicon app.
- `Nesvo-macOS-x64.dmg` contains the Intel app.
- `SHA256SUMS.txt` contains the SHA-256 digest of each installer.

Download the checksum file alongside your installer. On Windows, run `Get-FileHash .\Nesvo-Windows-Setup.exe -Algorithm SHA256`. On macOS, run `shasum -a 256 Nesvo-macOS-arm64.dmg`, substituting the Intel filename if needed. Compare the output with the matching line in `SHA256SUMS.txt` before opening the installer.

Download the latest installers from the [Nesvo releases page](https://github.com/dkveil/nesvo/releases/latest). Builds are unsigned, macOS builds are not notarized, and updates require downloading a new installer.

- **Windows.** Microsoft Defender SmartScreen may warn that the installer is unrecognized. Verify the download source before continuing if Windows offers that choice. [Microsoft guidance](https://support.microsoft.com/en-us/windows/security/windows-security/app-browser-control-in-the-windows-security-app)
- **macOS.** Move Nesvo from the disk image to Applications. Gatekeeper may block the first launch because the developer cannot be verified. If you trust the download, use **System Settings → Privacy & Security → Open Anyway** after the first attempt if the option is available. [Apple guidance](https://support.apple.com/en-us/102445)

## External Inbox CLI from source

The desktop build bundles the CLI into its resources. Settings shows the local bundle and runtime paths and the command to add its launcher to the current shell's PATH. Dev builds also include the launcher and set its runtime path in the copyable command.

To use the private host package's bin independently from a repository checkout:

```bash
bun install --frozen-lockfile

```

## Standalone host

Build first. Then set NESVO_DATA_DIR to a dedicated directory and run bun run host.

The host runs SQLite `quick_check` at startup and reports the database path if it detects corruption. Before migrating an existing `nesvo.sqlite`, it takes a consistent SQLite snapshot named `nesvo.sqlite.v<oldVersion>.bak` in the same directory. It keeps the three most recent migration backups. A host that encounters a newer schema refuses to open it and lists the available backups. Use a compatible version of Nesvo to inspect a backup in a separate data directory. Backups contain session data and need the same access controls as the live database.

The host moves invalid session documents to `session_quarantine` with their session IDs, a validation summary, and a timestamp. It retains each session ID in `sessions` to preserve references from other records, and excludes quarantined documents from session lists and history search. The host reports newly quarantined rows to stderr and the stored total as `quarantinedSessionCount` in its health response. Malformed session JSON is handled by this quarantine even when SQLite reports it as a session document constraint failure. Inspect quarantined documents in a copy of the database.
Each stdin line is a JSON object validated by packages/contracts: health, claude-status, codex-status, list-sessions, list-reviews, create-session, send-message, stop-run, respond-approval, decide-delegation, decide-review or shutdown. Commands use a UUID id; send-message also has an idempotent messageId, and stop-run addresses a specific runId. Approval responses additionally identify the exact pending request and carry only accept or decline. Delegation decisions identify sessionId, runId and delegationId and carry accept or decline; they never accept renderer-supplied worker settings. Review decisions carry reviewId, version, decisionId, accept or request-changes, and required feedback for corrections.
Responses, session-changed and review-changed events are JSONL on stdout; diagnostics go to stderr. Readers must correlate responses by id instead of treating the next line as the response. Closing stdin also closes the host and its active group.

### Workflow definition commands

The same bundle validates and changes workflow definitions without a running host or a database:

```sh
node apps/host/dist/main.js workflows validate --directory <project>
node apps/host/dist/main.js workflows list --directory <project> --json
node apps/host/dist/main.js workflows add-step --directory <project> --scope project --file step.md [--expected-hash <hash>]
node apps/host/dist/main.js workflows add-to-workflow --directory <project> --scope project --workflow <name> --step <name> [--after <name>]
node apps/host/dist/main.js workflows remove-from-workflow --directory <project> --scope project --workflow <name> --step <name>
```

The command is also reachable as `pipelines`, its name before the rename. Definitions in the legacy `.agents/pipelines` folders are read with a warning and move to `.agents/workflows` when saved; see [workflows.md](workflows.md#legacy-location).

`list` prints the `contentHash` of every definition. Replacing an existing step requires the hash that was read as `--expected-hash`; a changed file answers with its current hash, exits 2 and writes nothing, so read it again. Validation errors exit 1. When `NESVO_RUN_ID` is set, the three writing commands exit 3 without touching a file; `validate` and `list` still work. Details are in the architecture notes on definition commands.

## Workflow demo runs

The header workflow status and the session card can be previewed in every run state with demo runs. Set NESVO_WORKFLOW_DEMO=1 before starting an unpackaged desktop build; optional NESVO_WORKFLOW_DEMO_DIRECTORY sets the folder the demo sessions point at. Main then adds five read-only demo sessions to Local with runs that are checking, passed, need attention after a failed command step, wait for a human gate, and stop on an uncertain action, plus one nested agent step session. Run lists, run detail, evidence reads, Stop, Resume and the skip that records an uncertain action as done for those runs are answered in memory by `apps/desktop/src/main/workflow-demo.ts`; nothing reaches the host or the database, and every other command, including starting a task, still goes to the real host. A packaged build ignores the flag and never creates the demo source. While the flag is on, the Local run list comes only from the demo, so real runs on Local are not listed. Use a dedicated NESVO_DATA_DIR, because the demo sessions appear next to real ones.

## Local data

The desktop stores its host database under Electron's userData directory, in host/nesvo.sqlite.
On Windows this normally means %APPDATA%/Nesvo/host.
NESVO_DATA_DIR overrides the desktop userData directory, or the standalone host data directory.
The desktop writes rotating logs to Electron's logs directory: `main.log` for the main process, IPC failures and renderer error reports, and `host.log` for the local host's stdout and stderr. Each keeps five files of up to 5 MB (`main.log`, `main.1.log` … `main.4.log`). On Windows and Linux the directory is `logs` under userData (for example %APPDATA%/Nesvo/logs); on macOS it is ~/Library/Logs/Nesvo. With NESVO_DATA_DIR set, logs go to `logs` inside that directory. Settings › General › Open logs opens the folder. Development builds also mirror both logs to the terminal.
Window bounds and the maximized state are kept in `window-state.json` under userData; a saved position that no longer overlaps a display falls back to a centred default size.
Use different directories for standalone and desktop development. Never point test runs at your real data.
Empty working-directory input creates a dedicated folder under the host's workspaces directory. Existing directories are resolved and validated without requiring Git. Providers retain their own resume transcripts in their configured locations; Nesvo stores separate provider session identifiers and conversation snapshots.

For an interactive thread in a Git repository with an initial commit, enable **Worktree** in the new-thread setup. A folder inside the repository resolves to its root. Nesvo creates a fresh checkout under `session-worktrees/` in that computer's data directory. Choose an unused branch name or let Nesvo generate one. The checkout starts with the files committed at HEAD. Untracked and ignored files from the source folder, including local `.env` files and installed dependencies, are absent. Prepare anything the session needs explicitly in its checkout.

Use **Session actions** → **Finish…** after the turn settles. Keep preserves the checkout, Open pull request carries the branch to the Pull requests search and Remove deletes the checkout while retaining the branch. Publish and create a pull request separately. Remove requires separate confirmation to discard uncommitted changes or local files. Session history and the branch remain available after removal. If the Git command is interrupted during creation, the error identifies the possible partial checkout and branch for manual recovery.

NESVO_CLAUDE_EXECUTABLE and NESVO_CODEX_EXECUTABLE optionally select absolute native executable paths. A JavaScript CLI entry is launched using the existing Node runtime. The test suite uses these overrides for its local fixtures. Production discovery checks PATH and common native installation locations; shell wrappers are not executed.

Isolated workflow tasks create their Git worktrees under the data directory, in `worktrees/`, on branches named `nesvo/<slug>-<runId8>`. They are removed only by an explicit removal request, which refuses a worktree with uncommitted changes unless forced and keeps the branch. A worktree holds only tracked files, so `.env`, local state and installed dependencies are absent. Nesvo copies nothing and has no file list for it; a `plan` phase step prepares the worktree from the operator's project, which every step receives as `NESVO_PROJECT_ROOT`:

```md
---
name: setup
type: command
phase: plan
---

cp "$NESVO_PROJECT_ROOT/.env" .env
bun install --frozen-lockfile
```

NESVO_GIT_EXECUTABLE optionally replaces Git with an absolute path, as the test suite does for a stand-in that never exits.

P0 has no migration from historical application data. Existing private directories and worktrees remain untouched.
Do not run git clean or delete ignored files as part of setup.

## Website

The public site at https://nesvo.dev is the Next.js application in `apps/web`, deployed as a Cloudflare Worker with a D1 database. It serves the download page, the macOS install script and shared workflows, and it is not indexed for now. Start it with `bun run --cwd apps/web dev`; local development, the share API, configuration and the deployment checklist are in [web.md](web.md).

Download buttons point at the stable asset names of the latest GitHub Release (`Nesvo-Windows-Setup.exe`, `Nesvo-macOS-arm64.dmg`, `Nesvo-macOS-x64.dmg`), so the site needs no change for a new version.

## Troubleshooting

If the initial screen reports no connection, retry once and inspect `host.log` and `main.log` (Settings › General › Open logs) or the terminal used to start development.
If the local host stops, Nesvo restarts it after 1, 2, 5 and 15 seconds and re-reads its state; after the fourth failure the computer shows an error with Retry. A restarted host marks unfinished runs interrupted and nothing is resent.
An incompatible database fails closed; do not delete it to hide the error.
If Claude reports an account limit, wait for the reset reported by Claude and retry. Nesvo does not substitute a simulated response, change billing, or automatically retry. A turn fails only after 15 minutes without any provider activity; waiting for an approval or for a parent's workers does not count as silence. Stop terminates only the owned process tree; failed cleanup is reported as failure.
New Codex sessions can delegate without selecting a role. Access permissions remain independent and unchanged by delegation. Older sessions preserve their existing provider thread and recorded tool capability. Worker directories must already exist inside the parent directory; use separate non-overlapping directories when allowing writes. A supervised parent can delegate only read-only workers until isolated workspaces exist. One group runs at a time, and workers never launch before an individual operator decision.
Quit the desktop to stop its utility host. On macOS, closing the last window alone does not quit the app.
Development IPC and the host expose no network port. The renderer development server uses an available Vite port.

Use **Import conversation…** on the new-thread screen to adopt a conversation from the selected computer’s Claude Code or Codex CLI history. See [Importing CLI conversations](architecture.md#importing-cli-conversations) for host paths and limits.
